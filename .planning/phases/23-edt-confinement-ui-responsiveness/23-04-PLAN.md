<objective>
Close the remaining teardown exits and the three scenarios that only become reachable once execution is
asynchronous.

Plan `23-01` gave the cancel button a supersede path. D-08 requires the same mechanism for the other
three exits — session delete, project change and extension unload — so that in every case the worker
finishes, its `invokeLater` body finds it has been superseded and does nothing, `onCompleted` is
discharged, and no followup turn is sent. Phase 22 spent real effort making all five teardown paths
discharge cleanly; leaving a sixth open would undo that.

**The single most likely omission in this phase, measured at source:** `deleteSession`
(`ChatPanel.kt:851-890`) calls `resolvePending(session.id, ImplicitDenyReason.SESSION_DELETED)` and
**never** `cancelInFlightRequest()`. Project change (`clearInMemorySessionState`, `:1480`) and unload
(`shutdown`, `:1455`) both go through `cancelInFlightRequest` and therefore inherit the supersede for
free. Session delete does not. Without an explicit call, scenario S-05 passes vacuously while a real
session delete leaves a worker writing into a disposed panel.

Purpose: REL-05 / D-08 / SC6 — every exit from a running tool call is accounted for, audited, and
non-blocking.
Output: an explicit supersede in `deleteSession`; teardown scenarios S-05 through S-09 and S-12; the
rewritten negative E10 dimension.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker tail → disposed panel / torn-down classloader | After a session delete, project change or unload the panel and its maps may be gone. The supersede check is the control. |
| worker → extension error stream | The only place a background-thread failure becomes visible; Burp reports nothing itself. |
| chat call site → its own `McpRequestLimiter` | Per-call construction is what keeps two user actions independent. |
