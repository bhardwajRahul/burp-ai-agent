# Phase 23 — UI Design Contract: EDT Confinement & UI Responsiveness

> Interaction contract for REL-05. Generated by `gsd-ui-researcher`. Pending verification by
> `gsd-ui-checker`.
>
> **Stack: Kotlin + Java Swing inside Burp Suite (ADR-2).** No browser, no DOM, no CSS, no Tailwind,
> no shadcn, no npm registry, no web font, no viewport. JavaFX and Compose are explicitly out of
> scope in `PROJECT.md`. `npx shadcn` was **not** run and no web component library is proposed —
> not an omission, a stack fact. Web-specific template sections are replaced with their Swing
> equivalents rather than left blank; see §"Web Sections → Swing Equivalents".
>
> **The design system already exists and is authoritative.** Spacing, typography and color are
> inherited verbatim from `09-UI-SPEC.md` / `ui/design/DesignTokens.kt` (shipped v0.8.0, Phase 9).
> This phase declares **zero new spacing values, zero new typography roles, zero new color tokens,
> zero new glyphs and zero new components.**
>
> **This phase adds no visual chrome. That is a decision, not an oversight.** The whole change is
> moving three tool-execution call sites and one Settings save off the Swing Event Dispatch Thread.
> No spinner, no progress bar, no toast, no new panel, no redesign. What *is* new — and what this
> document exists to pin — is **state transition coverage**: freeing the EDT turns a panel that
> reads idle while frozen into a panel that reads idle **and is live**, which is a state nobody has
> specified.

## The Hard Problem: Five Visual States Where There Were Effectively Two

### Why this is the whole design problem

Measured at source, 2026-08-20: in `sendMessage`'s `onComplete`, `setSendingState(false)` is queued
at `ChatPanel.kt:658` and `maybeExecuteToolCall` is queued at `ChatPanel.kt:741`. Both are
`SwingUtilities.invokeLater` from a backend thread, so the clear runs **first**. Today the panel
therefore already shows Send / enabled-input while the tool executes — and simultaneously the EDT is
blocked inside `McpToolExecutor.executeTool`, so the panel is **idle-looking and frozen**. The lie is
invisible because nothing responds.

Free the EDT and the same code becomes **idle-looking and live**. The user can type, press Send, and
start a second backend turn while a tool worker is running against Burp — a race Phase 22 D-08 cannot
absorb, because an *executing* call cannot be retired the way a *parked* card can. D-06 closes it by
making the panel busy for the tool's duration.

Two further states already exist but have never been written down together with the new one: the
Phase 22 *awaiting-decision* park (legitimately idle), and the *superseded* return (must render
nothing). Five states total.

### The state table — `ChatPanel`

`setSendingState(sending: Boolean)` (`ChatPanel.kt:941-946`) is the only busy toggle and is reused
unchanged. It sets exactly three things:

```
sendBtn.isVisible  = !sending
cancelBtn.isVisible =  sending
inputArea.isEnabled = !sending
```

| # | State | `sendBtn` | `cancelBtn` | `inputArea` | Transcript | Entered by | Left by |
|---|-------|-----------|-------------|-------------|------------|-----------|---------|
| **S0** | `idle` | visible, enabled iff `mcpAvailable` (`:317`) | hidden (`:497`) | enabled iff `mcpAvailable` (`:320`) | last completed turn | construction; any terminal exit below | user sends, or a card is approved |
| **S1** | `backend-turn` | hidden | **visible** | disabled | streaming assistant bubble | `sendMessage` dispatch | `onComplete` → `setSendingState(false)` (`:658`) when `clearIfMatches` says this connection is still current |
| **S2** | `awaiting-decision` | visible | hidden | enabled | pending `ToolApprovalCard` | Phase 22 gate returns `AWAITING_DECISION` | user resolves the card, or an implicit-deny trigger fires |
| **S3** | `tool-running` | hidden | **visible** | disabled | resolved card receipt (chain path) / echoed command (user paths) | **NEW** — `setSendingState(true)` on the EDT, immediately before worker dispatch, at all three D-01 sites | worker's `invokeLater` tail, **only if not superseded** |
| **S4** | `superseded` | — | — | — | **nothing** | worker returns after cancel / session delete / project change / unload | terminal; renders no row, sends no follow-up, discharges `onCompleted` |

**S3 is visually identical to S1 by design (D-06).** From the user's side a chain is one continuous
turn; a third visual state would be new chrome for something that usually lasts under a second.

**S2 is idle and that is correct, not a gap.** While a card is pending the user must be able to click
its buttons, and Phase 22 D-08 lets a new typed message act as an implicit denial. Do not make the
panel busy while a card is pending.

**S4 renders nothing.** Precedent and exact shape: `InFlightConnectionTracker.take()` /
`clearIfMatches()` (`ChatPanel.kt:69`, instance `:108`), already covered by
`ChatPanelConcurrencyTest.kt:20-60`.

### Rule S-1 — busy is global to the panel, never per session

`sendBtn` (`:104`), `cancelBtn` (`:105`), `inputArea` and `isSending` (`:110`) are `ChatPanel`
fields, so a backend turn already locks every session. A tool run behaving identically needs no new
rule (D-09). Do **not** make `setSendingState` session-aware in this phase — that would necessarily
change backend-turn behaviour, which REL-05 did not scope.

### Rule S-2 — busy is entered on the EDT, before dispatch, at all three sites

All three D-01 call sites enter S3, not only the chain:

| Site | Origin | Today's busy state | Required |
|------|--------|--------------------|----------|
| `ChatPanel.kt:1010` | `ToolCallOrigin.UserDialog` | **none** — panel reads idle, freezes | S3 |
| `ChatPanel.kt:2319` | `ToolCallOrigin.UserSlashCommand` | **none** — panel reads idle, freezes | S3 |
| `ChatPanel.kt:2856` | `approved.origin` (SEC-06 chain) | cleared at `:658` before the tool runs | S3 |

The two user-originated sites currently never call `setSendingState` at all —
`sendFromInput` returns at `:526` before `sendMessage` is reached, and `openToolDialog` never enters
the send path. Leaving them idle-and-live would let a user fire `/tool` and then immediately press
Send, producing exactly the concurrent-worker case D-05 accepts only as "one chain plus one manual
invocation" rather than as fan-out.

### Rule S-3 — no idle flash between a chain step and its tool

`setSendingState(true)` for S3 must be the **first statement inside the same `invokeLater` block
that dispatches the worker** — the block already at `ChatPanel.kt:741`. Do **not** attempt to make
`:658`'s clear conditional: at `:658` the response has not been parsed and the code cannot yet know
whether a tool call follows.

Two EDT events posted back to back can be separated by a repaint, so a sub-frame Send↔Cancel flicker
remains possible on the **auto-approved / session-approved** path (where no card intervenes). This is
the residual and it is accepted, because the alternative — hoisting parse-and-decide into `:658` —
restructures `maybeExecuteToolCall` in a file this phase is forbidden to restructure. On the
`CONFIRM` path there is no flicker at all: S2 sits between S1 and S3 legitimately.

Record the residual in the plan. Do not "fix" it with a timer or a deferred repaint.

### Rule S-4 — the `/tool` path must echo its command before going async

Measured at source: `handleToolCommand`'s `/tool` branch (`ChatPanel.kt:2307-2324`) calls **no**
`panel.addMessage("You", …)` and adds no user `ChatMessage`, and `sendFromInput` clears
`inputArea.text` and returns at `:525-526` without echoing. Today the typed command survives on
screen only because the EDT is frozen mid-execution.

Once the input is cleared and execution goes async, the transcript shows **nothing at all** until
`"Tool result: {tool}"` appears — a result with no visible request, in a tool whose users must be able
to answer "what did I just run?".

**Required:** echo the command in the existing `"You"` channel before dispatch, exactly as the dialog
path already does at `ChatPanel.kt:1004` with its `commandPreview` (`"/tool {id} {args}"`). This adds
no widget, no string template and no styling — it reuses `SessionPanel.addMessage` and makes the two
user-originated paths symmetric. Whether the corresponding `session.messages.add(ChatMessage("user", …))`
is also added is the planner's call: that changes model context, not pixels, and is out of UI scope.
See FLAG-23-03.

### Rule S-5 — Cancel must not be inert in S3

`cancelBtn` (`:498`) calls `cancelInFlightRequest()` (`:956`), whose first act is
`inFlightConnection.take() ?: return false`. `inFlightConnection` was already cleared by `clearIfMatches` at `:655`
before the tool started, so a busy panel with no backend connection would present a Cancel button
that does **nothing and says nothing** — the worst possible affordance on a security tool.

In S3, pressing Cancel must:

1. return the panel to **S0** immediately (not after the worker finishes);
2. append the tool-cancel transcript line from §Copywriting — **not** `"Request cancelled."`;
3. leave the resolved `ToolApprovalCard` receipt untouched (it records a decision the user really made);
4. mark the worker superseded so its return lands in **S4**;
5. suppress the follow-up turn without refunding a chain iteration (Phase 22 D-13's monotone counter).

Which string is appended is selected by **whether a tool worker was taken**, not by which button was
pressed. When both a backend connection and a tool worker are absent, `cancelInFlightRequest()`
returns `false` and appends nothing — unchanged.

### Rule S-6 — disabled input drops keystrokes, and that is the honest option

Today, typing during a frozen `/tool` queues keystrokes that appear when the EDT thaws. Under S3 the
input is disabled and keystrokes are discarded. Neither is pleasant; disabled is honest, matches S1's
existing behaviour, and is what D-06 buys. Do not add a queue.

### The state table — Settings

| # | State | `Save settings` | `Restore defaults` | Every other field | Banner (`saveFeedbackLabel`) |
|---|-------|-----------------|--------------------|-------------------|------------------------------|
| **T0** | `settings-idle` | enabled, `primary` bg | enabled | editable | `"No recent save activity."` on `borderSubtle` (`SettingsPanelActions.kt:333-335`) |
| **T1** | `settings-saving` | **disabled** | **disabled** | **editable — unchanged** (D-10) | `"Saving settings..."` / `"Restoring defaults..."` on `statusWarning` |
| **T1→T0 ok** | — | re-enabled | re-enabled | editable | `"Saved and applied."` / `"Defaults restored and applied."` on `statusSuccess`, `resetMs = 3000` |
| **T1→T0 fail** | — | re-enabled | re-enabled | editable | `"Save failed: {message}"` / `"Restore failed: {message}"` on `statusError`, `resetMs = 5000` **plus** the modal (D-12) |

**Both buttons disable, not just Save.** D-13 puts `saveSettings()` and
`restoreDefaultsWithConfirmation()` on one async path, and D-10's disabled state is what stops the
two from overlapping. Disabling only Save would leave Restore able to start a second
`applyAndSaveSettings` mid-flight — the double-save race D-10 exists to close, re-entered through
the other door.

**Nothing else disables.** No enable/disable sweep over the eight settings tabs; that reproduces the
frozen feel this phase removes.

### Rule T-1 — the busy seam must be created, because the buttons are not where you think

Measured at source: `saveButton` and `restoreButton` are **private fields of `BottomTabsPanel`**
(`BottomTabsPanel.kt:19-20`), not of `SettingsPanel`. `SettingsPanel.saveSettings()`
(`SettingsPanelActions.kt:63`) has no handle on the button that invoked it. D-10 is therefore not a
one-line `isEnabled = false`; it needs a seam.

**Required shape:** a listener installed by `BottomTabsPanel`, mirroring the seam that already exists
one line below the buttons — `settingsPanel.setDialogParent(root)` (`BottomTabsPanel.kt:93`). The
`SettingsPanel` async path raises it `true` before dispatch and `false` on **every** completion path,
success and failure alike, on the EDT.

**A completion path that forgets to lower it leaves the Settings tab permanently unsaveable.** That
is the single highest-consequence UI failure in this phase; it deserves a `finally`, not a pair of
call sites.

### Rule T-2 — the disabled Save button needs a visible affordance

`saveButton` is `isOpaque = true` with `background = UiTheme.Colors.primary` and
`foreground = UiTheme.Colors.onPrimary` (`BottomTabsPanel.kt:60-63`). A Swing button with an explicit
opaque background keeps painting that background when disabled; only the *text* falls back to the
L&F's disabled foreground. The result is Burp orange with grey text — a weak and low-contrast
"disabled" reading, in both themes.

**Required:** while in T1, recolor the button through existing tokens, in `BottomTabsPanel.kt`'s own
namespace per Rule N-1:

| Property | T0 | T1 |
|----------|----|----|
| `background` | `UiTheme.Colors.primary` | `UiTheme.Colors.outlineVariant` (canonical `borderSubtle`) |
| `foreground` | `UiTheme.Colors.onPrimary` | `UiTheme.Colors.onSurfaceVariant` |
| `isEnabled` | `true` | `false` |

Both replacement tokens already resolve from `UIManager` (`Separator.foreground`,
`Label.disabledForeground`), so the treatment inverts correctly with the theme and adds no token.
`borderSubtle` is already this project's "inactive banner" color (`SettingsPanelActions.kt:335`), so
the visual vocabulary is consistent rather than invented.

`restoreButton` needs no recolor: its background is already `surface` and only its foreground is
`primary` (`:71-72`), so the L&F's disabled text rendering reads correctly on it. Disable it plainly.

**Escape hatch, must be deliberate:** if live UAT on the target L&F shows plain `isEnabled = false`
already reading as disabled on the opaque Save button, drop the recolor and keep the two channels
that remain (the disabled button and the `"Saving settings..."` banner). Record the choice; do not
default it by omission. See FLAG-23-01.

### Rule T-3 — both modals stay on the EDT, on their existing side of the dispatch

| Modal | Source | Position relative to the worker |
|-------|--------|-------------------------------|
| Restore-defaults confirmation — `"Restore default settings? This will overwrite current values."` | `SettingsPanelActions.kt:80-88` | **Before** dispatch, on the EDT, unchanged. A confirmation that runs after the work has started is not a confirmation. |
| Save-failure alert — `"Failed to save settings: {message}"` | `SettingsPanelActions.kt:71-77` | **After** the worker, marshalled back via `invokeLater`. D-12 keeps it: a 5-second banner is genuinely missable and "my MCP server did not restart" must not be silent. |

Also preserve the existing ordering note from D-11: `currentSettings()` reads Swing components
(`SettingsPanelActions.kt:66`) and `applySettingsToUi(defaults)` (`:91`) writes them, so **both stay
on the EDT before dispatch**. Only the `applyAndSaveSettings` body moves.

`CONCERNS.md` §"UI layer has no integration tests" records that `JOptionPane` is genuinely not
headless-testable. That bounds how D-12 can be verified — assert the banner, assert the seam
lowering, and leave the modal to `23-HUMAN-UAT.md`. Do not delete the modal to make it testable.

## The Open Question, Answered

CONTEXT.md left exactly one visual question open: **does the transcript show anything between the
moment a tool is approved and `"Tool result: {tool}"` appearing?** Its Claude's-Discretion section
recommended *nothing new*. **Confirmed, with one correction and one addition.**

**Confirmed for the chain path.** Two independent markers already exist and neither is new:

1. **The card becomes a receipt in place.** `ToolApprovalCard.resolve(...)`
   (`ToolApprovalCard.kt:415-432`) mutates the pending card into a resolved outcome row reading
   `"Approved once — {h:mm a}"` or `"Approved for this chat — {h:mm a}"`
   (`ToolApprovalCard.kt:926-927`), and it stays in the transcript. The user can see which tool was
   approved and when.
2. **The panel is in S3.** Send hidden, Cancel offered, input disabled — a panel-level "something is
   running" signal that is already the vocabulary of a backend turn.

**The correction.** The receipt is past tense — it says *"Approved"*, not *"Running"*. It answers
"what did I authorise?" and not "is it still going?". S3 answers the second. The two are
complementary, and only together are they sufficient; the receipt alone would not be. A third,
per-call indicator would be redundant with S3 and would be new chrome for a state that usually lasts
under a second (D-06's own reasoning).

**The addition.** The receipt only exists on the SEC-06 chain path. The two user-originated sites
produce **no card** (Phase 22 SC5 — do not double-prompt). For those, S3 would be the *only* signal —
and for `/tool` specifically the transcript would be entirely blank until the result arrived. That is
what Rule S-4 closes, using an existing call rather than new chrome.

**Recommendation recorded, out of scope for this phase:** if live UAT shows real tool calls running
long enough that a panel-level busy state reads as a hang, a per-call progress row becomes worth
revisiting. `ChatMessagePanel` already ships a braille spinner (`ChatPanel.kt:1970-1974`,
`"Thinking..."` + `U+280B…U+280F`) that such a row could reuse. **Do not build it in Phase 23.**
CONTEXT.md §Deferred already carries this item.

## Typography

Inherited from `DesignTokens.Typography` (`DesignTokens.kt:90-112`) and its legacy shim
`UiTheme.Typography` (`UiTheme.kt:88-99`). **No new role is derived; the declared maximum of 5 roles
stands. No `Font(...)` constructor is introduced.**

| Role | Derivation | Weight | Present in the surfaces this phase touches |
|------|-----------|--------|--------------------------------------------|
| `sectionTitle` / legacy `title` | `base.deriveFont(BOLD, base * 1.2f)` | Bold | not used in these surfaces |
| `body` | `base.deriveFont(PLAIN, base)` | Regular | not used in these surfaces |
| `caption` | `base.deriveFont(PLAIN, base * 0.9f)` | Regular | not used in these surfaces |
| `label` | `base.deriveFont(BOLD, base)` | Bold | `sendBtn.font` (`ChatPanel.kt:482`) and `cancelBtn.font` (`:495`) — **unchanged across S0/S1/S3**; `saveButton.font` (`BottomTabsPanel.kt:60`), `restoreButton.font` (`:70`) — **unchanged in both T0 and T1** |
| `chatBody` (legacy, `UiTheme.kt:98`) | `TextArea.font` at its own size | Regular | Every transcript row, including the new cancel line |
| `mono` | `UIManager.getFont("TextArea.font")` | Regular | not used in these surfaces |

**Rule T-4 — the busy state changes no font.** T1 recolors the Save button; it does not embolden,
italicise or resize it. Weight is already carrying "this is the primary action"; borrowing it to also
carry "this is in flight" would collapse two meanings onto one channel.

**Line height:** Swing exposes none (`09-UI-SPEC.md` §Typography). The equivalent contract for the
one new transcript string is inherited and needs no new rule: transcript rows render through
`MarkdownRenderer.toHtml` into a `JEditorPane` whose `getPreferredSize` wraps at 75 % of the viewport
width for non-user rows (`ChatPanel.kt:1991-2005`). The ~160-character cancel line therefore wraps
rather than clips.

**This is explicitly *not* the `JLabel` overflow hazard `22-UI-SPEC.md` §Typography documents.** That
hazard applies to non-wrapping `JLabel` rows inside a `HORIZONTAL_SCROLLBAR_NEVER` scroll pane. The
strings this phase adds land in a wrapping `JEditorPane` (transcript) and in
`saveFeedbackLabel`, whose worst case is `"Save failed: {message}"` with a message the *existing*
code already interpolates at the same width. No new overflow obligation is created.

**Sizes are multipliers, never pixels**, so every surface here follows the user's OS accessibility
font setting.

## Color

Inherited from `DesignTokens.Colors` (`DesignTokens.kt:126-199`) and its legacy shim

### 60 / 30 / 10 across the surfaces this phase touches

| Share | Token | Where |
|-------|-------|-------|

### Rule C-1 — the Cancel *label* stays; the Cancel *transcript line* must not

`"Cancel"` is right for both S1 and S3: it is the same escape hatch, and a button whose text mutates
between chain steps reads as a glitch. **Do not rename it** to `Stop`, `Abort` or `Interrupt`.

What must change is the line it writes. `cancelInFlightRequest()` appends
`"Request cancelled."` (`ChatPanel.kt:966`). Under D-07 that sentence becomes **false** on the tool
path: Montoya's `sendRequest` takes no cancellation, so the worker runs to completion and the request
really does reach the target. Telling a penetration tester their request was cancelled when it was
sent is the kind of wrong that ends up in someone's report.

**New string — tool-run cancellation (chat transcript, `"System"` channel):**

```
Cancelled: {tool} was already sent to Burp and will finish. Its result was
discarded and no follow-up was sent to the AI. The call is in the audit log.
```

Three facts, in the order a tester needs them: **(1)** it happened anyway, **(2)** nothing was done
with the answer, **(3)** you can still find out what it was. Fact 3 is not decoration — it is the
user-visible half of D-07's load-bearing corollary that a cancelled call must not become an unlogged
one, and it tells the user where to look.

**One string, both paths.** `{tool}` is the raw tool name already carried at the call site; the same
sentence serves a cancelled chain step and a cancelled `/tool` or dialog invocation.

**Selection rule:** the string is chosen by *what was taken* — a backend connection yields
`"Request cancelled."` (byte-identical), a tool worker yields the new line, neither yields nothing.
Not by which button was pressed, and not by which state the panel believes it is in.

### Rule C-2 — Settings copy, per completion path

`applyAndSaveSettings` becomes async with a completion callback shared by both callers (D-13). Each
caller supplies its own pair, so no path can report a neighbour's outcome.

| Path | Start (T1) | Success | Failure |
|------|-----------|---------|---------|
| `saveSettings()` | `Saving settings...` — **unchanged**, `statusWarning` (`:64`) | `Saved and applied.` — **unchanged**, `statusSuccess`, `resetMs = 3000` (`:67`) | `Save failed: {message}` — **unchanged**, `statusError`, `resetMs = 5000` (`:69`) + modal (`:71-77`) |
| `restoreDefaultsWithConfirmation()` | `Restoring defaults...` — **NEW**, `statusWarning` | `Defaults restored and applied.` — bytes **unchanged** (`:92`), `statusSuccess`, `resetMs = 3000`, but now fires from the completion callback | `Restore failed: {message}` — **NEW**, `statusError`, `resetMs = 5000` + modal `Failed to restore defaults: {message}` |

**Why `"Restoring defaults..."` is genuinely new and not scope creep.** `restoreDefaultsWithConfirmation`
never sets a start banner today — it calls `applyAndSaveSettings` directly (`:91`) and only
`saveSettings()` writes `"Saving settings..."` (`:64`). Synchronously that is survivable because the
EDT is frozen and nothing repaints. Asynchronously it produces a live panel with two disabled
buttons and a banner still reading `"No recent save activity."` — a state that says nothing is
happening while something is. Every T1 entry must have a T1 banner.

**Why `"Defaults restored and applied."` moves.** It is printed at `:92`, on the line *after*
`applyAndSaveSettings` returns. The moment that call is async, the sentence is a lie — it claims a
completed restore before the MCP server has stopped. Same bytes, correct moment.

**House style, matched exactly, not modernised:** three ASCII dots (`...`), never `…`; sentence case;
terminal period; `{message}` falls back to `"unknown error"` exactly as `:69` and `:73` already do.
Do not "improve" the ellipsis — it would diverge from `"Saving settings..."` and `"Thinking..."`
(`ChatPanel.kt:1970`) for no reason.

### Rule C-3 — no confirmation on Cancel

Cancelling a tool run is not gated behind a dialog. A confirmation on an escape hatch defeats the
escape hatch, and the destructive consequence — a request that already left — is stated by the line
that follows, which is where a user can actually act on it.

### Copy that must NOT change

| String | Source | Why it is listed |
|--------|--------|------------------|
| `Request cancelled.` | `ChatPanel.kt:966` | Still correct for a backend-turn cancel. Keep it; add a sibling, do not overwrite. |

## Light/Dark Compliance Rules

`DesignTokens` resolves every color from `UIManager` at call time and caches nothing
(`DesignTokens.kt:8-11`), so theme tracking is inherited rather than implemented. Two rules keep it
that way:

1. **No `Color(0x…)` literal and no `Font(...)` constructor** may enter `BottomTabsPanel.kt`,
   `SettingsPanelActions.kt` or `ChatPanel.kt` in this phase. Rule T-2's recolor uses
   `UiTheme.Colors.outlineVariant` / `UiTheme.Colors.onSurfaceVariant`, both `UIManager`-resolved.
2. **Restore, do not remember.** Leaving T1 must reassign `UiTheme.Colors.primary` /
   `UiTheme.Colors.onPrimary` by reading the tokens again, never by stashing the `Color` objects
   captured on entry. A stashed value survives a theme switch that happens mid-save and repaints the
   button in the previous theme's palette.

`DesignTokens.isDarkTheme` (`:24-30`) is not consulted anywhere in this phase; every token used here
resolves through the L&F.

## Flags (Non-Blocking)

- **FLAG-23-01 — Rule T-2's disabled recolor is a judgement, not a measurement.** The reasoning
  (opaque button + explicit background keeps its fill when disabled) is sound, but the exact rendering
  depends on Burp's L&F. If live UAT shows plain `isEnabled = false` already reads as disabled, drop
  the recolor and keep the disabled button plus the `"Saving settings..."` banner. **The choice must be
  recorded, not defaulted by omission** — either way `isEnabled = false` is mandatory, because it is
  what closes the double-save race.

- **FLAG-23-02 — every non-user transcript role renders as `"AI"`.** `ChatMessagePanel`
  (`ChatPanel.kt:1963-1966`) computes `displayRole = if (isUser) "You" else "AI"`, so
  `addMessage("System", "Request cancelled.")` and `addMessage("Tool result: …", …)` are both
  attributed to the AI. The new cancel line inherits that — an extension-authored statement about
  Burp's behaviour will appear over an `"AI"` header. **Pre-existing, shipped since before Phase 22,
  and out of scope here.** Recorded so it is not mistaken for a regression introduced by this phase.
  Candidate for Phase 26 / DOC-03 alongside `22-UI-SPEC.md`'s FLAG-22-07.

- **FLAG-23-03 — Rule S-4's model-history half is the planner's call.** The transcript echo is
  required. Whether the `/tool` command is *also* appended to `session.messages` as a user
  `ChatMessage` — which the dialog path does at `ChatPanel.kt:1005` — changes what the model sees, not
  what the user sees, and is therefore outside this contract. Decide it deliberately; the current
  asymmetry between the two user-originated paths is pre-existing.

- **FLAG-23-04 — the S-3 flicker residual is confirmable only by UAT.** Listed as ⚠ unresolved in
  §UI Considerations. Add it to `23-HUMAN-UAT.md` as an observation item ("approve a tool with
  approve-for-session, watch for a Send/Cancel flash between chain steps"), not as a pass/fail gate.

- **FLAG-23-05 — WITHDRAWN 2026-08-20; inverted into a negative guard.** This flag claimed that
  per-call workers would make `"Too many concurrent MCP requests."` newly user-visible. **Verified
  false at source:** `ChatPanel.buildToolContext` constructs a fresh `McpRequestLimiter` per call
  (`ChatPanel.kt:3019`), so a `/tool` and a chain hold different semaphores and cannot contend. This
  phase therefore introduces **no new user-visible string** beyond the three this document authors.
  Inverted rather than deleted: if that string ever does appear in a chat transcript, a limiter was
  shared across call sites and it is a real defect. Tracked as AI-SPEC dimension E10.

- **FLAG-23-06 — the settings busy seam must lower in a `finally`.** Not a design choice, a hazard
  worth naming twice: any completion path that returns without lowering the seam leaves the Settings
  tab permanently unsaveable, with no error and no way back short of reloading the extension. It is the
  highest-consequence UI failure available in this phase.
