<objective>
Close the two regressions this phase introduced outside the security core, and convert SC3's HTTP/2 claim
from an accident into a contract.

Purpose: `./gradlew test -PstoreBuild=true` currently fails on a test whose declared purpose is merely to
prove the new version property did not disturb the pre-existing store-build flag. That is the exact build
invocation used to produce the BApp Store artifact, and submission #231 is live at automated code review.
Separately, this phase's own hardening runbook now promises an audit record that the code provably does
not produce for the most common browser-driven attack vector — an operator following that checklist would
conclude the audit trail is broken, or worse, read an absent record as absence of attack.

Output: a store-build test that asserts the SEAM rather than a value, and passes under both invocations; a
corrected `docs/mcp-hardening.md` Verification item; and one `response.protocol` assertion that makes
SC3's HTTP/2 half fail loudly if ALPN negotiation ever changes.
</objective>

**The store-build seam as it actually exists.** `build.gradle.kts` resolves
`val storeBuild = providers.gradleProperty("storeBuild").orNull == "true"` at configuration time, feeds it
into `generateBuildFlags`'s `storeBuildFlag` property, and already consumes the same `val` inside
`tasks.shadowJar` to choose the archive base name. The generator writes
`object BuildFlags { const val STORE_BUILD = …; const val VERSION = "…" }`. `gradle.properties` enables
`org.gradle.configuration-cache=true`, which is why the generator captures the version at configuration
time rather than reading `project.version` inside its `@TaskAction`. Referencing the already-resolved
`storeBuild` `Boolean` inside `tasks.test { }` is the same configuration-cache-safe pattern
`tasks.shadowJar` already uses — do NOT read `project.findProperty` from inside a task action.

**`tasks.test` already exists** and contains `useJUnitPlatform()`, a `jvmArgs("-ea")` line whose comment
ties it to the REL-01 SC1 gate, and the `excludeHeavyTests` filter block. Add to it; do not restructure
it, and do not move the property onto `tasks.withType<Test>` — `nightlyRegressionTest` does not run the
BuildFlags test (its filter includes only the five heavy-suffix globs), so broadening the scope buys
nothing and changes the inputs of a task this plan has no reason to touch.

**The failing test.** `McpBuildFlagsVersionTest.storeBuild_flagStillGenerated` currently calls
`assertFalse(BuildFlags.STORE_BUILD, "STORE_BUILD must default to false when -PstoreBuild is not passed")`.
The verifier independently reproduced the failure: `expected: <false> but was: <true>` under
`-PstoreBuild=true`. The sibling test `version_isARealSemverAndNotTheHardcodedPlaceholder` is NOT part of
this gap and must keep both of its assertions.

**The doc sentence to correct** is `docs/mcp-hardening.md` line 38 — Verification item 2. Its final clause
reads "the reason is recorded in Burp's Output tab and, when audit logging is enabled, in the audit log",
and item 2 lists a foreign `Origin` among the local-mode 403 cases. The reviewer confirmed against

for the code side of that vector is unchanged, and `McpAccessControlPlugin.kt` belongs to plan 20-08 in
this wave.
