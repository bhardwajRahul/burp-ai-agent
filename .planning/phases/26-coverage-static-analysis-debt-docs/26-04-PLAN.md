<objective>
SC4 (QUAL-07): resolve the disposition of `ChatPanel`'s `assert()`-based EDT enforcement.

Purpose: `ChatPanel.assertEdt()` wraps `assert(SwingUtilities.isEventDispatchThread())`. JVM `assert`
is disabled unless `-ea` is passed, and shipped Burp does not pass it — so in production the helper
compiles to nothing. Its own KDoc already admits this, but the four call sites carry `REL-01` comments
that read as enforcement, and `DECISIONS.md` ADR-15 records the residual in those terms
("`assertEdt()` is still a production no-op (QUAL-07)"). The criterion asks for one of two honest end
states: a mechanism that reports in the field, or source that says plainly it does not.

This is a genuine either/or with materially different costs and a lasting consequence inside a Burp
extension's UI thread, so it is settled by the developer at a blocking checkpoint. The planner does
not pick.

Output: the chosen mechanism, applied uniformly to all four call sites, with a proof appropriate to
the choice, and a verbatim record of the selection for ADR-17.
</objective>

## Measured facts this plan is built on

Measured by the planner at commit `4f0ebd7` on 2026-08-22:

- `assert(` appears in `src/main/kotlin` exactly **once**, in `ChatPanel.assertEdt()`.
- `assertEdt()` has **four** call sites: `cancelInFlightRequest`, `syncDraftFromInput`,
  `maybeExecuteToolCall`, `resolveToolDecision`.
- `McpToolExecutorImpl` already ships a **production** thread guard —
  `check(!SwingUtilities.isEventDispatchThread())` — with a KDoc block that explicitly rejects the JVM
  assertion facility for this exact reason. The upgrade pattern and its written justification already
  exist in this repo.
- `build.gradle.kts` `tasks.test` runs with `-ea`. A separate task,
  `edtGuardWithoutAssertionsTest`, runs with `-da` and filters to `*McpToolExecutorEdtGuardTest`. It is
  invoked by `.github/workflows/build.yml`'s pr-gate on all three OSes and by the nightly workflow.
- The `ChatPanel` test harness and every UI test that drives it marshal through
  `SwingUtilities.invokeAndWait`, so the existing suite is *expected* to respect the invariant already
  — Task 1's `<action>` requires this to be measured before the checkpoint is presented, because it is
  the whole cost argument for the upgrade options.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Background worker thread → `ChatPanel`'s `@GuardedBy("EDT")` session maps | The invariant this plan is about. A violation is a data race on the maps that hold chat sessions, drafts and tool-decision records. |

| enforcement helper → Burp Output/Errors tab (Option C only) | Anything the helper logs is written to a Burp tab and may be included in a user's bug report. |
