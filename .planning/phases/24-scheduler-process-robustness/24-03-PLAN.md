<objective>
Close SC3 and SC4 (REL-07): CLI stdout capture becomes thread-safe and bounded.

Today `CliBackend.kt:209` declares a plain unsynchronised accumulator that the daemon reader thread
`burp-ai-agent-cli-reader` appends to at :220, while three call sites read it — :252 and :264 after a
`readerThread.join(2000)` that can expire while the reader is still appending, and :275 on the success
path. There is no happens-before edge between writer and readers, and there is no ceiling on how much
a chatty or hostile subprocess can accumulate.

The trap this plan is built around: the read at :275 is **the model's answer**, not a diagnostic tail.
It feeds `stripAnsiCodes` and then the five per-backend line filters, none of which takes a last-N-lines
view. The 2000-character figure that appears twice in the file belongs to the two error paths only.
Any cap must be generous enough that no legitimate answer is ever truncated, and must retain the head
so both error messages keep their current bytes.

Purpose: a hostile or merely chatty CLI subprocess can no longer corrupt captured output through a
data race, nor exhaust the Burp JVM's heap through unbounded accumulation.
Output: a small `internal class CliOutputBuffer` with the lock inside, four converted call sites in
`CliBackend.kt`, and a headless suite that drives it without a subprocess.
</objective>

<planner_assumptions>
The phase has no SPEC; the deterministic edge probe returned 5 applicable edges, 0 resolved. This plan
resolves both REL-07 edges for the CLI buffer and restates the REL-06 ones so none is dropped.

- **A-EDGE-4 (REL-07, boundary) — RESOLVED for the CLI buffer.** *"What happens exactly at each
  min/max/threshold — and one step either side?"* The threshold is
  `Defaults.MAX_CLI_OUTPUT_CHARS = 262_144`. **Resolution, asserted at all three points:** content of
  exactly `maxChars - 1` characters is retained whole with `truncated == false`; content of exactly
  `maxChars` characters is retained whole with `truncated == false`; the first character past
  `maxChars` sets `truncated = true` and is not retained. A buffer that has never been appended to
  returns an empty snapshot with `truncated == false`.
- **A-EDGE-5 (REL-07, precision) — RESOLVED.** *"Where can precision loss, overflow, or
  rounding/tie-breaking occur — and how is it resolved?"* The cap counts **UTF-16 chars**, not bytes
  and not code points, so a cut at exactly `maxChars` can split a surrogate pair and leave an unpaired
  high surrogate at the end of the snapshot — a silent corruption of the very output this plan exists
  to protect. **Resolution:** when the character at the cut position minus one is a high surrogate,
  cut one character earlier. Asserted directly with an astral-plane string. There is no `Int` overflow
  risk: the cap is 262 144 and appends stop at it, so the accumulated length can never approach
  `Int.MAX_VALUE`.
- **A-EDGE-1 / A-EDGE-2 / A-EDGE-3 (REL-06)** were resolved in plan 24-01.

Carried from RESEARCH.md §Assumptions Log:

- **A2 — UNRESOLVED, accepted, and the KDoc must not overclaim.** The *absence* of a happens-before
  edge between the reader thread and the timeout path is documented; the specific crash shape (a
  `StringIndexOutOfBoundsException` from inside the accumulator versus merely stale or garbled data)
  is inference. The class KDoc must describe the hazard as "no happens-before edge, so a read can
  observe a partially-published state", not assert a specific exception type.
- **A3 — RESOLVED as 262 144 by this planner, with the residual named.** If a user's agentic CLI
  legitimately emits more than 256 Ki characters in one turn, its answer gains a visible truncation
  marker instead of being silently corrupted — a recoverable, visible failure. The figure is eight
  times the repo's own `LARGE_PROMPT_THRESHOLD = 32_000` and 131 times the 2000-character error head.
  Memory amplification is the reason not to go higher: `stripAnsiCodes` runs four sequential
  full-string regex replacements over the value at `CliBackend.kt:275`, each allocating a fresh
  full-size string, so peak transient heap is roughly five times the cap — about 2.5 MB at 256 Ki, and
  about 10 MB at 1 Mi. `stripAnsiCodes` also uses raw `Regex` rather than the project's `SafeRegex`
  deadline wrapper, so bounding the input is the only protection those four passes have.
</planner_assumptions>

<reversibility>
No decision in this plan is rated `one-way`, so no `checkpoint:decision` is inserted.

- Extracting `CliOutputBuffer` as an `internal class` — **reversible**: a file-level extraction behind
  four call sites in one file, no published contract.
- Head retention plus a truncation marker — **costly**: it defines what a truncated CLI answer looks
  like to a user. Switching to tail or head-plus-tail later changes user-visible output and would
  require rewriting `CliTimeoutMessageTest`, which is written against the current head bytes. Head
  retention is chosen because it preserves both error messages byte-for-byte and because the overflow
  case is pathological by construction; a head-plus-tail split remains a strictly-later refinement
  that needs no interface change to `CliOutputBuffer`. Flagged, not gated.
- The cap value — **reversible**: a one-line `Defaults` change.
</reversibility>

  <action>
Create `src/main/kotlin/com/six2dez/burp/aiagent/backends/cli/CliOutputBuffer.kt` in package
`com.six2dez.burp.aiagent.backends.cli`, declaring
`internal class CliOutputBuffer(private val maxChars: Int = Defaults.MAX_CLI_OUTPUT_CHARS)` with an
`init { require(maxChars > 0) { "maxChars must be > 0" } }` in the `CircuitBreaker` style. Hold a
`private val lock = Any()` and a private accumulator plus a private `truncatedFlag: Boolean`.

`appendLine(line: String)` takes the lock, and — if the accumulator has not already reached `maxChars`
— appends `line` followed by a newline. If that append would carry the accumulator past `maxChars`, it
appends only the portion that fits and sets `truncatedFlag = true`; if the accumulator is already at
`maxChars`, it sets `truncatedFlag = true` and appends nothing. When it cuts, and the character
immediately before the cut position is a UTF-16 high surrogate, it cuts one character earlier so the
snapshot can never end with an unpaired surrogate. That single rule is A-EDGE-5's resolution and must
carry an English comment saying so.

`snapshot(): String` takes the same lock and returns the retained content, with
`Defaults.CLI_OUTPUT_TRUNCATION_MARKER` appended **only when `truncatedFlag` is true**. That
conditional is load-bearing: it is what makes a legitimate answer round-trip byte-identically.
Expose `truncated: Boolean` and `length: Int` as lock-taking properties for assertions and callers.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI subprocess stdout -> extension heap | Untrusted, attacker-influenceable bytes of unbounded volume cross into the Burp JVM. |
| `burp-ai-agent-cli-reader` daemon thread -> timeout path | Two threads share one accumulator across a `join(2000)` that can expire mid-append. |
| captured output -> `stripAnsiCodes` -> per-backend line filters | Four sequential full-string raw-`Regex` passes with no `SafeRegex` deadline; input size is their only bound. |

| T-24-04 | Denial of Service | `CliBackend` stdout capture | high | mitigate | Hard cap `Defaults.MAX_CLI_OUTPUT_CHARS = 262_144` applied at append time. Unbounded, a chatty or hostile CLI can drive an `OutOfMemoryError` in Burp's own JVM — and `stripAnsiCodes`'s four full-string regex passes make peak transient heap roughly five times the retained size, so the unbounded case is worse than it first appears.
