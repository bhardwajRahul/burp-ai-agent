<objective>
Close SC2 (REL-06) and the scanner half of SC6 (REL-07) in `ActiveAiScanner.kt`.

SC2's first clause — "keeps processing its queue after an induced failure on one target" — is
**already true today**: the per-target `try/catch` at `ActiveAiScanner.kt:391-401` is the `AiScanCheck`
per-payload isolation idiom CONVENTIONS.md names. What is not true is the second clause: the log line
is `"[ActiveAiScanner] Error: ${e.message}"` and carries no target identifier at all. That one line is
SC2's real deliverable and it is the half that goes red before the fix.

SC6's scanner half replaces the unbounded per-request pool at `ActiveAiScanner.kt:73` with a
`ThreadPoolExecutor` carrying an explicit ceiling, a named factory and an explicit rejection policy —
and, critically, moves the `submit` at :1089 inside the `try` that begins at :1094, because with
`AbortPolicy` a saturated pool otherwise throws out of an uncaught path.

Both changes live in the same file and, more importantly, in the same failure story: a rejected submit
becomes a diagnosable per-target failure only once the log line names the target.

Purpose: a single bad target becomes a named, recoverable event instead of a silent gap, and a scan
against a black-holing host cannot spawn threads without limit.
Output: an enriched log line, a bounded named `requestExecutor`, a rejection path that returns null,
and two new headless suites.
</objective>
