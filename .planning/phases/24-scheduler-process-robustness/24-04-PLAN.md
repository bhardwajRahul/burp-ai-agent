<objective>
Close SC5 (REL-07) exactly as CONTEXT.md's four locked decisions specify.

Today `CliBackend.kt` registers each temp file with the JVM's own exit-time deletion facility at :123
(codex output file) and :138 (large-prompt file). The JDK holds those registrations in a static
`LinkedHashSet<String>` with no removal API, so every CLI invocation retains one path string for the
life of the Burp JVM. Per D-01 that per-invocation registration is replaced by **one** shutdown hook
sweeping a live-file registry bounded by concurrent CLI calls, normally zero or one.

Per D-02 the registry and the hook live in a new `internal object` in the `cli` package rather than in
a private companion inside `CliBackend`, because a companion registry can only be exercised by driving
a real subprocess — the un-assertable-seam problem Phase 23 hit repeatedly — while a separate object
gives the rewritten test a seam it can drive in pure JVM. Per D-03 the hook is registered lazily on
first temp-file creation, and `App.shutdown()` both removes it and drains the registry. Per D-04 the
hard-kill residual is accepted and named in the object's KDoc rather than papered over.

**A correction the implementation must carry, not repeat.** CONTEXT.md D-03 justifies removal by
analogy to a pinned classloader. The analogy is wrong for the *existing* leak — the JDK's set holds
plain strings, not extension-classloader objects, so today's leak is a pure unbounded-string-set leak.
The conclusion is nonetheless correct, and more strongly than stated, for the **new** hook: the
`Runnable` handed to `Runtime.addShutdownHook` by this extension *is* an extension-classloader class,
so an unremoved custom hook genuinely does pin a dead classloader across reloads. Write the KDoc
against the correct reason.

**A second correction, about the test baseline.** CONTEXT.md's original note claimed two existing
tests pin the behaviour D-01 removes and would turn the fix red. Research measured the opposite: they
are vacuous, not blocking, and SC5 therefore has **zero** real coverage today. Replace them; do not
invert them.

Purpose: repeated CLI use stops leaking JVM state, without giving up the one crash case a hook
genuinely covers.
Output: `CliTempFileRegistry.kt`, two rewritten call sites, two deregistrations, one new
`App.shutdown()` step, and a rewritten test suite that finally covers SC5.
</objective>

Planner-resolved from CONTEXT.md and RESEARCH.md:

- **D-03 drain placement — RESOLVED as after `"Backend registry"`, before `"Worker pool"`.** The CLI
  executor lives under the backend registry, so by the time `backendRegistry.shutdown()` has returned,
  every in-flight CLI call has already had its `finally` run and the drain sweeps a settled set —
  which is exactly its stated job.
- **Idempotence is a requirement, not a nicety.** Both the `finally` delete and the drain can run for
  the same file; a double delete must not surface as an error. The existing `finally` already uses the
  CONVENTIONS-blessed bare catch with an `// INTENTIONAL:` comment, which makes this free on that
  side; the registry's own drain must be equally forgiving.
- **The residual is real and must be named, not closed.** A registry living in JVM memory cannot reap
  files orphaned by SIGKILL or power loss, because neither the `finally` nor the shutdown hook runs.
  Bounded at one temp file per in-flight call, in the OS temp directory, which the OS reaps on its own
  schedule. Also: entries already accumulated in a currently-running Burp cannot be undone by this
  change — SC5 is about future invocations. Both facts belong in the KDoc so nobody tries to verify
  the fix by inspecting a long-running Burp session.

  <action>
Create `src/main/kotlin/com/six2dez/burp/aiagent/backends/cli/CliTempFileRegistry.kt` in package
`com.six2dez.burp.aiagent.backends.cli`, declaring `internal object CliTempFileRegistry`.

State: a thread-safe set of absolute path strings for files belonging to in-flight CLI calls, and a
nullable reference to the registered hook `Thread` guarded so registration happens at most once.

`register(file: File)` adds the file's absolute path to the set and, on the very first successful
registration in the object's lifetime, lazily creates and registers the shutdown hook via
`Runtime.getRuntime().addShutdownHook(...)`. Lazy is a D-03 requirement, not an optimisation: a
session that never uses a CLI backend must pay nothing.

`deregister(file: File)` removes the path. It must be safe to call for a path that is not present.

`drain()` iterates a snapshot of the set, attempts to delete each file, and clears the set. Each
delete is wrapped in the blessed bare `catch (_: Exception)` with an `// INTENTIONAL:` comment
explaining that both the `finally` block and the drain may run for the same file, so a double delete
must never surface as an error. Idempotence is a stated D-03 requirement.

`shutdown()` is what `App.shutdown()` calls. It removes the hook with `Runtime.getRuntime().removeShutdownHook(...)`
if one is registered, clears the hook reference, and then calls `drain()`. It must be idempotent —
calling it twice, or calling it when no hook was ever registered, does nothing and throws nothing.
`removeShutdownHook` throws `IllegalStateException` if the VM is already shutting down; do not
hand-roll a catch for it here beyond what idempotence needs, because the caller wraps this in
`safeShutdownStep`, which already catches `Exception`.

Add `internal fun sizeForTests(): Int` and `internal fun resetForTests()` beside the production API,
following the `…ForTests` seam pattern already house style in `ScannerTaskRegistry.kt:66-68`.
`resetForTests()` clears the set and drops the hook reference without deleting anything, so a suite can
start from a known state.
