## Why the parity test is behavioural, not reflective

`cookieHeaderRegex` and `setCookieHeaderRegex` are `private val` on the `Redaction` object. The
parity assertion therefore goes through `Redaction.apply` — for a header name `N`, build a small
request blob containing `N: <sentinel>`, run `apply` under STRICT, and read `promptStrips(N)` as
"the sentinel is gone from the output". That is the behaviour that ships, and it needs no visibility
change and no reflection.

**The corpus must be chosen so that only the two cookie rules can claim a sentinel.** This is not
optional care — it is the difference between a real invariant and a test that passes for the wrong
reason. `Authorization` and `Host` are stripped by `authHeaderRegex` and `hostHeaderRegex`
respectively, so `promptStrips("Authorization")` is true while `isCookieHeaderName("Authorization")`
is false, and the implication would fail for a reason that has nothing to do with cookies. Exclude
them. `RedactionTest`'s comment block at lines 405-433 spells out the same discipline for its own
fixture — read it, then choose sentinels the same way: no `=`, no quotes, no `Bearer`/`Basic`/`eyJ`
prefix, no dotted segments, no `=== COOKIES ===` header, and no name reachable by
`SENSITIVE_KEY_EXPR`.

## The `ordering` edge and the one thing it collides with

The resolved edge asks for: *"N `Set-Cookie` headers produce N redacted entries in their original
positions."* Read the shipped code before deciding what to do about it:

`sanitizeHeaders` builds a `LinkedHashMap<String, String>` and writes `sanitized[name] = value`,
where `name` is the header's original-cased name. Two headers named byte-identically therefore
produce ONE map entry — last value wins, at the first one's position. Two headers whose names differ
in case produce two entries. This is pre-existing behaviour of a `Map`-returning function, not
something plan 27-01 introduced, and it is **privacy-safe**: every entry that collapses was already
going to be the placeholder, so no cookie value escapes. What is lost is analysis SIGNAL — the
analyst sees one `Set-Cookie` where the response carried three.

Satisfying the edge as literally written requires changing `sanitizeHeaders`' return type and, with
it, `ParsedRequest.headers` and `ParsedResponse.headers` — the JSON shape that `request_parse` and
`response_parse` return to external MCP clients and to the model in a shipped 1.0.0 release. That is
a one-way door, and it is not this phase's door to walk through unattended. Hence CP-27-02-01.
