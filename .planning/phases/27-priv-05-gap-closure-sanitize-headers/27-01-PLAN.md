<objective>
Close the PRIV-05 gap the v0.10.0 milestone audit found: make the MCP tool-RESULT redaction path
(`McpToolHelpers.sanitizeHeaders`) recognise a cookie header by the same rule the prompt path
(`Redaction`) already uses — name-CONTAINS-`cookie`, not exact equality — and make that agreement
structural rather than a coincidence two humans have to maintain.

Purpose: PRIV-05 reads "cookie values do not reach an AI backend in STRICT or BALANCED mode **by any
path**." Phase 21 made that true on the prompt path. `sanitizeHeaders` is the second, independent
path, and it still tests exact names, so `X-Cookie`, `Cookie2`, `Set-Cookie2`, `X-Original-Cookie`
and `X-Forwarded-Cookie` reach the model VERBATIM through the `request_parse` / `response_parse` MCP
tools. Downstream cannot recover them.

Output: one shared predicate in `Redaction`, three call sites consuming it, a locale-safe compare,
and a test matrix that fails in both mutation directions.
</objective>

## The defect, measured (do not re-litigate — fix it)

Confirmed against the tree at `1.0.0` before this plan was written.

| | Prompt path (Phase 21) | MCP tool-result path (Phase 26) |
|---|---|---|
| Location | `Redaction.kt:100-106` | `McpToolHelpers.kt:321` |
| Matcher | name-**contains**-`cookie`, via `COOKIE_NAME_PART = [A-Za-z0-9-]*` | exact equality against the two canonical spellings |
| `Cookie:` | stripped | stripped |
| `X-Cookie:` | stripped | **passes through** |
| `Set-Cookie2:` | stripped | **passes through** |

`McpToolContext.redactIfNeeded` (`McpToolContext.kt:59`) cannot recover a missed header, for two
independent reasons that were both re-verified in source:

1. `sanitizeHeaders` output is serialised into **single-line JSON** by `toolJson`
   (`McpToolHelpers.kt:24`), while `cookieHeaderRegex` and `setCookieHeaderRegex` are line-anchored
   `(?im)^…$`.
2. `cookie` is absent from `SENSITIVE_WORDS` (`Redaction.kt:476-477` — `access_token|api_key|apikey|
   auth|token|secret|password|pwd|session|sid`), so `jsonSecretKeyRegex` never fires on a cookie key.

So `sanitizeHeaders` is the **last** line of defence on this path, not the first of two.

## The five design decisions this plan makes

**D-27-01 — one shared predicate, promoted (assumption-delta: `promote`, not `add-alongside`).**
The cookie-name rule becomes a single public function, `Redaction.isCookieHeaderName`, and every
consumer calls it. Both cookie regexes and the predicate are built from ONE new private literal,
`COOKIE_NAME_TOKEN`. Rejected alternative: give `sanitizeHeaders` its own matcher. That reproduces
the exact structure that failed — two independently-maintained copies of one security rule — and the
audit's own remedy note asks for the sibling relationship to be made explicit. Precedent in this
codebase: `Redaction.COOKIE_SECTION_HEADER` is owned in the redactor and imported by the emitter so a
rename is a compile error, and Phase 21 W-01 coupled `COOKIES_MAX_COUNT` to
`MAX_COOKIE_SECTION_LINES` for the same reason. Rated `costly`: undoing it means unwinding a
symbol plus three call sites plus the parity test in plan 27-02.

**D-27-02 — the over-match is ACCEPTED, deliberately, for parity.** `Cookie-Consent` and
`X-Cookie-Policy` will have their values stripped. This is the same cost the prompt path already
accepts (T-21-WA3; `.planning/codebase/CONCERNS.md` W-A: *"any `*cookie*` header is cookie-bearing by
convention, and only the VALUE is removed"*). A tighter rule was rejected because it would require
BOTH paths to change together or the divergence reopens immediately — which is precisely the failure
being repaired. The acceptance is made VISIBLE as a named test rather than left as an accident.
Rated `reversible`.

**D-27-03 — the two second-order holes in `redactIfNeeded` are NOT closed here; they are recorded as
accepted residuals.** Un-anchoring the cookie regexes so they fire mid-line would change the PROMPT
path's behaviour across every body, and adding `cookie` to `SENSITIVE_WORDS` would redact every JSON
key, form parameter and query parameter containing `cookie` as a token — against a measured Phase 21
decision that REMOVED `key` and `code` from broad matching after 27 false positives over a 32-name
corpus. Both are large-blast-radius changes to a shipped redactor, undertaken to add a backstop
behind a control this plan is making correct. Instead, the deferral is made safe by an
**outcome-level** assertion: Task 1's end-to-end test asserts the sentinel is absent from the FINAL
`redactIfNeeded` output, so if anyone ever narrows `sanitizeHeaders` again, that test goes red
without caring which layer was supposed to catch it. Residuals: **AR-27-01** (line-anchored regexes
vs single-line JSON) and **AR-27-02** (`cookie` absent from `SENSITIVE_WORDS`). Rated `reversible`.

**D-27-04 — the locale fix lands for the whole function, in the same commit.** `sanitizeHeaders`
computes one lowered name and feeds it to the cookie test, the `tokenHeaders` set lookup and the host
comparison. There is no way to fix the cookie branch's locale hazard without fixing all three, and
splitting the change would be worse than useless. Under a `tr-TR` default locale, `"COOKIE"` lowered
without a locale argument yields `cookıe` (dotless i) and the control silently stops working.
`java.util.Locale.ROOT` is the established convention in this codebase (`CliBackend.kt:817/842/964`,
`AgentSupervisor.kt:1143/1199`, `Entropy.kt:154`). The same one-line hazard exists at
`PassiveAiScannerFilters.kt:169` and is fixed in Task 3. Rated `reversible`.

**D-27-05 — the record reconciliation is real work with its own plan (27-03), not a footnote.** See
plan 27-03. It is out of scope here; this plan only produces the source evidence 27-03 must cite.
