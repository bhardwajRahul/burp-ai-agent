<objective>
Close PRIV-05 on the THIRD carrier of the same cookie bytes: COOKIE-typed HTTP parameters.

Burp parses the `Cookie:` header into `HttpParameterType.COOKIE` parameters. `HttpRequest.parameters()`
returns them, and four live MCP producers emit their VALUES with no cookie control in front and no
redaction rule behind. In `request_parse` the leak sits three lines below the fix this phase was
created for: `headers = sanitizeHeaders(...)` writes `"Cookie":"[STRIPPED]"` and `parameters` returns
the identical value in the same JSON object. The control is defeated on its own output.

Purpose: make PRIV-05's "by any path" wording true on the parameter carrier, using a control whose
key is the parameter TYPE rather than the rendered SHAPE — because shape-keyed controls are exactly
what has failed three times here.

Output: one owned predicate, one shared sanitizer, four rewired producers, one rewired prompt-path
producer, and a behavioural test file whose red probes fail if any of them is unwired.

**Severity, stated at the width the evidence supports and no wider.** `request_parse` and
`params_extract` both call `HttpRequest.httpRequest(input.content)` on CALLER-SUPPLIED content, so
they ECHO a cookie the caller already holds rather than exfiltrating Burp-held traffic. That is the
same mitigating property the original PRIV-05 finding had, and it was treated as a blocker then. The
maintainer has decided to FIX rather than to accept; this plan does not reopen that disposition and
does not inflate the risk. The echoed value is additionally written to the transcript and audit
surfaces, for which `redactIfNeeded` is the sole control — that is why the echo still matters.
`BountyPromptTagResolver` (task 3) is the one site in this class that would carry BURP-HELD data.
</objective>

**D-27-17 — The control goes at the PRODUCER, in one shared TYPE-KEYED sanitizer.**
`McpToolHelpers.sanitizeParameters` mirrors `sanitizeHeaders`: same file, same `RedactionPolicy.fromMode`
source, same marker, same call position. It consumes one owned predicate, `Redaction.isCookieParameterType`.
- *Rejected — per-site inline strips at the four producers.* That is the shape waves 1-3 paid for: two
  independent implementations of one rule drifted apart and the narrower one shipped.
- *Rejected — widening `cookieTypedParamRegex` to reach the two MCP shapes.* It would be a THIRD and
  FOURTH shape-bound rule for one data class. Waves 4-6 learned that a rule at the choke point reaches
  every site — but the reason it worked there is that all fourteen sites emit ONE shape (a raw HTTP
  message inside a JSON string). The parameter carrier emits TWO shapes today and its shapes are ours
  to change, so a shape-bound rule is defeated by any future formatting edit and would be silently
  defeated, exactly as `cookieTypedParamRegex` is silently defeated today.
- *The property that makes this different from all three prior rounds:* the key is
  `HttpParameterType`, a value Burp gives us, never a rendered string. Reformat either tool's output
  and the control still fires.
- Reversibility: **reversible**. An `internal` function in a single-module build, no public API, no
  persisted state, revert is a straight `git revert`.

**D-27-18 — The marker is the same one the sibling field already uses, and the JSON shape does not change.**
A stripped cookie parameter value becomes the same literal `sanitizeHeaders` writes for a stripped
cookie header, so a reader of one `request_parse` result sees one vocabulary in both fields.
`ParsedParam.value` stays a non-null `String`; no field is added, removed, reordered or made nullable,
so `toolJson.encodeToString` emits a byte-identical structure and no MCP client's schema breaks.
- Reversibility: **costly**, not one-way. It IS a user-visible behaviour change on a shipped 1.0.0
  tool contract — a caller who today gets cookie values back from `request_parse` under STRICT will
  get the marker instead. Nothing is destroyed and a revert restores prior behaviour exactly, so it
  does not meet the one-way bar; it is flagged here so the change is read as intentional.
  It is also the behaviour the requirement demands, and `sanitizeHeaders` already makes exactly this
  trade on the sibling field of the same object.

**D-27-19 — `cookieTypedParamRegex` is neither widened nor removed in this plan.**
It stays the control for the passive scanner's `name=value (COOKIE)` prompt shape, which the
verifier re-measured as WORKING (probe Q3: `wibble=[REDACTED] (COOKIE)` in both redacting modes).
`WINDOWS.md` records what a rule change costs when a fixture does not exist for the old correct
behaviour — a quote-terminated tail that leaked on RFC 6265 DQUOTE-wrapped values and would have
shipped green. Plan 27-08 narrows its KDoc (which today claims coverage of `request.parameters()`
that the rule does not have) and adds the preservation fixtures. Reversibility: **reversible**.

**D-27-20 — Non-cookie parameter types are explicitly OUT of this plan's scope.**
PRIV-05's wording is about cookie values. A URL- or BODY-typed parameter named `access_token` may
well survive `request_parse`'s JSON shape — `jsonSecretKeyRegex` keys on the JSON KEY, which here is
the literal `value`, so it cannot fire (this is AR-27-02's mechanism, one field over). That is a
DIFFERENT requirement class and widening the shared key vocabulary was already measured expensive
(WR-01, 32 false positives). It is not assumed either way here: plan 27-08 task 3 MEASURES it and
records the result verbatim. `sanitizeParameters` is written as a `when` over the type so the
extension point is visible, and its KDoc names the untouched types and points at the measurement.
Reversibility: **reversible**.

**D-27-21 — `BountyPromptTagResolver.buildRequestParameters` is FIXED now, not recorded as latent.**
It is the only site in this carrier class that would carry BURP-HELD request data rather than
caller-echoed content, which makes its severity strictly higher the moment it is wired up. The fix is
the same predicate. Its dead-code status is RE-MEASURED at execution time (task 3) rather than
inherited from this plan — a live instantiation would change the finding's severity, so the plan may
not assert the measurement it was written from. Reversibility: **reversible**.
