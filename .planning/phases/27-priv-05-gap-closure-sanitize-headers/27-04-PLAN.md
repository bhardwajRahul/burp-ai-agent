| Fixture | shipped `^…:\s*.+$` | single tail + `(?<!\\)"` | single tail + escape-pair | TWO-BRANCH (the spec) |

| serialized, cookie mid-string | miss (leak) | strip, JSON OK | strip, JSON OK | strip, JSON OK |

Both backslash-tail cases break, contrary to a framing that names only the odd-length run: after JSON
encoding the character immediately before the closing quote is a literal backslash whether the value
ended in one backslash or two, so a one-character negative lookbehind fails in both. Parity is the
real predicate and a lookbehind cannot count it.

The two rejected candidates additionally regress REAL multi-line behaviour, which no shipped
`RedactionTest` fixture covers. That is the finding that forced the two-branch shape, and it was
found by measurement while re-checking the blocker, not by reasoning.

Header-stage cost, best of three, three header rules over one single-line payload:

```
size    shipped   two-branch, variable-width lookbehind   two-branch, FIXED-width lookbehind
1 MB      4 ms                129 ms                                 54 ms
2 MB      8 ms                259 ms                                109 ms
4 MB     17 ms                519 ms                                220 ms
```

Linear in input size, and flat across escape density (4 MB of `\n`-escape-separated runs of length 1,
40 and 4000 all cost ~145 ms) — so the cost is a constant factor, not a backtracking surface. The
fixed-width form is output-identical to the variable-width form on all nine fixtures and 2.4x cheaper,
because `\\r\\n` ends with `\\n` and is therefore already covered by a two-character lookbehind.

`newlineFreeOversizeBodyIsScannedNotDestroyed` CANNOT gate any of this: it calls
`Redaction.testWindowedBodyStage(body, budgetMs = …)`, and that seam bypasses the header stage
entirely (stated in the comment above `NEWLINE_FREE_INJECTED_BUDGET_MS`). The header stage also runs
outside `MAX_REDACTION_BUDGET_MS` — `windowedScan` starts its own budget clock — so the added cost
cannot push the body stage over budget either. It is real, bounded and unmeasured by anything that
exists today, which is why task 2 adds a direct measurement.

<decisions>
Each decision below is stated with its rationale, what the rejected alternative would have cost, and
a reversibility rating. Ratings drive checkpoints: no decision here is `one-way`, so this plan
carries no `checkpoint:decision`.

**D-27-06 — Where the control goes: a JSON-escaped-newline-aware boundary in `Redaction`, NOT a
sanitizer in front of serialization.** `reversibility: reversible` — a regex composition change in
one file, revertible by a code revert, no persisted artifact, no schema change, no data migration.

Chosen because it is STRUCTURAL rather than disciplinary. `redactIfNeeded` is the single choke point
every MCP tool result passes through, so one rule change covers all 14 measured emission sites AND
any site added tomorrow. It also keeps 27-01's shared-rule discipline: this is the THIRD consumer of
the cookie rule, and a header-aware sanitizer in `Serialization.kt` would be a FOURTH hand-written
answer to "what is a cookie header" — the exact drift that created this phase.

What the alternative would have cost: `Serialization.kt` is a context-free schema module. Sanitizing
before serialization means threading `McpToolContext` or `RedactionPolicy` through four extension
functions and 14 call sites; implementing raw-HTTP header parsing there; and accepting that a 15th
call site added later silently skips the control unless the parameter is made required (a source-
compatibility break on the shipped 1.0.0 API surface). It would also leave `redactIfNeeded`'s blind
spot intact for the other single-line-JSON payloads that reach it — scanner metadata and the tool
ARGUMENTS redaction at `McpToolExecutorImpl.kt:1143`.

**D-27-07 — The rule becomes a TWO-BRANCH alternation; the shipped branch is kept verbatim.**
`reversibility: reversible`. `AR-27-01` and `AR-27-02` were deferred because un-anchoring regresses
measured Phase-21 decisions. The chosen shape keeps the MULTILINE `^` branch WITH ITS SHIPPED TAIL
unchanged, and adds a second branch that is reachable only from a position preceded by a
two-character escaped-newline and that carries its own JSON-aware tail.

Two branches rather than one shared start boundary with one shared tail, on measurement. A shared
tail must carry the double-quote terminator the JSON shape needs; on REAL multi-line input that
terminator stops at a legitimate quoted cookie value (`Cookie: a="q"; session=<sentinel>` — RFC 6265
permits DQUOTE-wrapped values) and leaks the tail. Coupling the terminator set to the start boundary
makes the byte-identity claim structural: a real-line match cannot reach the quote terminator,
because it is not in that branch. The claim is still TESTED — `RedactionTest` green on a zero-line
diff, plus explicit fixtures for the two real-multi-line shapes `RedactionTest` does not cover — but
it is now true by construction first and by test second.

**D-27-08 — The escaped branch's tail consumes JSON escape PAIRS atomically.** `reversibility:
reversible`. Not cosmetic and not optional. Two measured failures drive it:

1. `.+$` on a single-line JSON payload runs to end-of-input, swallows the closing quote and the
   closing brace, and emits INVALID JSON — a tool-contract break worse than the leak.
2. Fixing (1) with a reluctant tail terminated by "a quote not preceded by a backslash" ALSO emits
   invalid JSON, whenever the cookie value ends in a backslash and the header is the last content in
   the string. JSON encoding doubles backslashes, so the character before the closing quote is a
   backslash for a value ending in one backslash AND for a value ending in two; the lookbehind
   suppresses the terminator in both cases and the match again runs to end-of-input. A
   one-character lookbehind cannot express the real predicate, which is a parity check over the
   backslash run.

The shape that satisfies both is a reluctant repetition of `(?:\\.|[^"\\])` — an escape pair, or any
character that is neither a quote nor a backslash — terminated by a lookahead over the escaped
newline, end-of-input, or a double quote. Because an escape pair is consumed as ONE unit, the tail
can never come to rest between a backslash and the character it escapes, so the quote that follows an
encoded backslash IS seen as the string terminator, and an escaped quote INSIDE the value is stepped
over rather than treated as a boundary. Parity is enforced by tokenization instead of by look-back.

Its alternatives are disjoint on their first character (backslash versus not), so the repetition is
deterministic: no ambiguity, no nested quantifier, no backtracking surface. Measured flat at ~145 ms
per 4 MB across escape densities spanning three orders of magnitude.

**D-27-15 — The escaped-newline boundary is a FIXED-WIDTH two-character lookbehind, and its
over-match is stated rather than engineered away.** `reversibility: reversible`. (Numbered after
plan 27-05's D-27-12…D-27-14 because it was added in revision; the ID is unique, which is what it is
for.) `\r\n` encodes to four characters ending in `\n`, so a two-character lookbehind over
"backslash followed by r or n" already covers the CR, LF and CRLF cases. Measured: output-identical
to the variable-width alternation on all nine fixtures, and 2.4x cheaper (220 ms versus 519 ms per
4 MB), because Java need not try two look-back widths at every position.

The bound, which belongs in the KDoc rather than in a SUMMARY: this boundary cannot distinguish a
JSON-encoded newline from a raw message that literally contained a backslash followed by `r` or `n`
(a Windows path, a regex in a body). Measured consequence: a `cookie:` appearing immediately after
such a sequence is treated as a logical line start and its value is stripped. That is OVER-redaction
of a header-shaped run inside a value — fail-safe in direction, and cheaper to state than to fix,
since fixing it needs the same backslash-parity check that D-27-08 deliberately declines to express
as a look-back.

**D-27-16 — The header-stage cost is measured and accepted at a stated number, and the existing 4 MB
fixture is NOT claimed as its gate.** `reversibility: reversible`. Measured: 17 ms → 220 ms for the
three header rules over a 4 MB single-line payload, linear in size and flat across escape density.
Accepted because the header stage runs on a background thread outside `MAX_REDACTION_BUDGET_MS`
(`windowedScan` starts its own clock at `Redaction.kt:1217`), so it cannot starve the body stage, and
because the same input already spends ~1.9 s in the body stage.

What is NOT true, and was claimed before this revision: that
`newlineFreeOversizeBodyIsScannedNotDestroyed` gates it. That test drives
`Redaction.testWindowedBodyStage`, a seam that bypasses the header stage entirely. Citing it would be
this phase's own failure mode — a claim wider than its gate can measure — so task 2 takes a direct
`Redaction.apply` measurement instead, and records the number rather than asserting a threshold that
would flake on a loaded machine.

**D-27-09 — The tool contract question is answered by a parse gate, not by inspection.** The redacted
output must still parse as JSON with the same key set and field count as the input, asserted for all
three carriers. Because that gate is automated and green, this is NOT a one-way door and earns no
`checkpoint:decision`. The shipped release is 1.0.0; the gate is what makes that safe to say.

**D-27-10 — `AR-27-02` (`cookie` absent from `SENSITIVE_WORDS`) is re-decided on evidence and stays
NOT adopted, now as superseded rather than deferred.** `reversibility: reversible`. It was
load-bearing only because the primary cookie rule could not fire on this shape; after D-27-06 it can.
Adding `cookie` to `SENSITIVE_WORDS` would be a second, far broader widening — every JSON key, query
parameter and form field whose name contains `cookie` would redact wherever `redactTokens` is on,
including benign `cookie_consent` / `cookiePolicy` — and it would have to be re-measured against the
WR-01 monotonicity corpora (31 must-redact / 21 must-not-redact / 8 camelCase). The honest bound,
which plan 27-06 records: the cookie rules are now a SINGLE point of control on this path, with no
independent backstop behind them.

**D-27-11 — `Host:` (and the un-anonymised `url` field) under STRICT on this shape is OUT of scope
for the code change and IN scope for the record.** `reversibility: reversible` (a scoping choice,
not an implementation). Three reasons, none of them "it looks hard": PRIV-05's wording is about
cookie VALUES, so this is a different requirement class; `hostHeaderRegex` rewrites through
`anonymizeHost`, which RECORDS a de-anonymisation mapping into a map that `RedactionHostMapBoundTest`
exists to bound — firing it on every raw message in every `site_map` result is a measured interaction
that deserves its own evidence; and entangling it here would couple this plan's cookie gate to a
STRICT behaviour change in shipped tool output. Plan 27-05 MEASURES it and plan 27-06 records it as
open finding AR-27-04. It is not silently ignored, and no test is added that pins it green.
</decisions>
