<decisions>
Each decision below is stated with its rationale, what the rejected alternative would have cost, and
a reversibility rating. Ratings drive checkpoints: no decision here is `one-way`, so this plan
carries no `checkpoint:decision`.

**D-27-06 — Where the control goes: a JSON-escaped-newline-aware boundary in `Redaction`, NOT a
sanitizer in front of serialization.** `reversibility: reversible` — a regex composition change in
one file, revertible by a code revert, no persisted artifact, no schema change, no data migration.

Chosen because it is STRUCTURAL rather than disciplinary. `redactIfNeeded` is the single choke point
every MCP tool result passes through, so one rule change covers all 14 measured emission sites AND
any site added tomorrow. It also keeps 27-01's shared-rule discipline: this is the THIRD consumer of
the cookie rule, and a header-aware sanitizer in `Serialization.kt` would be a FOURTH hand-written
answer to "what is a cookie header" — the exact drift that created this phase.

What the alternative would have cost: `Serialization.kt` is a context-free schema module. Sanitizing
before serialization means threading `McpToolContext` or `RedactionPolicy` through four extension
functions and 14 call sites; implementing raw-HTTP header parsing there; and accepting that a 15th
call site added later silently skips the control unless the parameter is made required (a source-
compatibility break on the shipped 1.0.0 API surface). It would also leave `redactIfNeeded`'s blind
spot intact for the other single-line-JSON payloads that reach it — scanner metadata and the tool
ARGUMENTS redaction at `McpToolExecutorImpl.kt:1143`.

**D-27-07 — The anchor is WIDENED, not removed.** `reversibility: reversible`. `AR-27-01` and
`AR-27-02` were deferred because un-anchoring regresses measured Phase-21 decisions. The chosen shape
keeps the MULTILINE `^` alternative and adds a bounded-width lookbehind over the escaped-newline
sequence beside it. Real multi-line behaviour is therefore byte-identical, and that is a TESTABLE
claim rather than an argument: `RedactionTest` must stay green with a zero-line diff.

**D-27-08 — The value tail becomes reluctant with a terminator lookahead.** `reversibility:
reversible`. Not cosmetic and not optional: with only the start boundary widened, `.+$` on a
single-line JSON payload matches to end-of-input, swallows the closing quote and the closing brace,
and emits INVALID JSON — a real tool-contract break, worse than the leak. The terminator set must
include the escaped-newline sequence, a real end-of-line, end-of-input, and a double quote that is
NOT preceded by a backslash. The last qualifier is the difference between stopping at the JSON string
terminator (correct) and stopping at an escaped quote inside the cookie value (an under-redaction
that leaks the tail).

**D-27-09 — The tool contract question is answered by a parse gate, not by inspection.** The redacted
output must still parse as JSON with the same key set and field count as the input, asserted for all
three carriers. Because that gate is automated and green, this is NOT a one-way door and earns no
`checkpoint:decision`. The shipped release is 1.0.0; the gate is what makes that safe to say.

**D-27-10 — `AR-27-02` (`cookie` absent from `SENSITIVE_WORDS`) is re-decided on evidence and stays
NOT adopted, now as superseded rather than deferred.** `reversibility: reversible`. It was
load-bearing only because the primary cookie rule could not fire on this shape; after D-27-06 it can.
Adding `cookie` to `SENSITIVE_WORDS` would be a second, far broader widening — every JSON key, query
parameter and form field whose name contains `cookie` would redact wherever `redactTokens` is on,
including benign `cookie_consent` / `cookiePolicy` — and it would have to be re-measured against the
WR-01 monotonicity corpora (31 must-redact / 21 must-not-redact / 8 camelCase). The honest bound,
which plan 27-06 records: the cookie rules are now a SINGLE point of control on this path, with no
independent backstop behind them.

**D-27-11 — `Host:` (and the un-anonymised `url` field) under STRICT on this shape is OUT of scope
for the code change and IN scope for the record.** `reversibility: reversible` (a scoping choice,
not an implementation). Three reasons, none of them "it looks hard": PRIV-05's wording is about
cookie VALUES, so this is a different requirement class; `hostHeaderRegex` rewrites through
`anonymizeHost`, which RECORDS a de-anonymisation mapping into a map that `RedactionHostMapBoundTest`
exists to bound — firing it on every raw message in every `site_map` result is a measured interaction
that deserves its own evidence; and entangling it here would couple this plan's cookie gate to a
STRICT behaviour change in shipped tool output. Plan 27-05 MEASURES it and plan 27-06 records it as
open finding AR-27-04. It is not silently ignored, and no test is added that pins it green.
</decisions>
