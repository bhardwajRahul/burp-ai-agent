<the_structural_question_answered>
**Decision: ACCEPTED. Build the carrier mechanism.** Recorded here as D-27-22, with its bound and its
blind axis stated in the same breath, because a mechanism claimed wider than it measures is the exact
defect this phase exists to repair.

**Why the three prior mechanisms each went blind, stated precisely.** Each keyed on a RENDERING of the
data. `CookieHeaderRuleOwnershipTest` keys on how a matcher is SPELLED. `SerializedEmissionSiteInventoryTest`
keys on how an emission is SHAPED. `cookieTypedParamRegex` keys on how a parameter is FORMATTED. A
rendering-keyed mechanism can only see renderings it already knows, so each round's mechanism was
complete for its own axis and structurally incapable of seeing the next.

**What plan 27-07 did differently, and why it is not a fourth gate of the same kind.** Its control is
TYPE-KEYED, not SHAPE-KEYED: it reads `HttpParameterType` and never a rendered string, so a change to
either MCP output format cannot defeat it. That is a real answer to why three axis-specific mechanisms
each went blind, rather than another mechanism of the same kind.

**What this plan adds.** The control is type-keyed at four producers; the QUESTION "which sites can
carry cookie bytes at all?" is still unanswered. So: enumerate the ACCESSORS. A cookie byte can only
enter this extension through a Montoya call that returns it. Enumerate those calls, and every site
that makes one must be routed through a named control or classified with a reason. That is one axis up
from the three that failed — it keys on the SOURCE of the data rather than on any rendering of it.

**THE BOUND, stated first and not as a footnote.** This mechanism keys on a MEASURED ACCESSOR SET. It
is a tripwire over that set, not a proof of coverage. What it cannot see, named explicitly so nobody
has to discover it as round five:

1. **A cookie byte that never passes a Montoya accessor.** Operator-pasted text in the chat box; a
   model echoing a cookie back into the transcript; a cookie the extension itself persisted to
   settings or a cache and later emitted. No accessor-keyed mechanism can reach any of these.
2. **`bodyToString()`, deliberately EXCLUDED — with the reason that actually holds.** Measured at
   **32** call sites across 8 files, comment-stripped, re-measured 2026-08-25.
   The exclusion is NOT because an entity body cannot contain cookie bytes. It can: a body can carry
   a pasted raw HTTP message, a forwarded webhook envelope, or a proxied upstream request, and any of
   those carries a `Cookie:` header inside the body text. Stating the exclusion as "an entity body
   does not contain the `Cookie` header" would be an absolute that a single pasted request falsifies —
   a premise written to be refuted in round five, which is the failure mode this whole section exists
   to stop.
   **The reason that does hold:** a body of that shape reaching a backend passes `Redaction.apply` at
   the `redactIfNeeded` choke point, and there the logical-line cookie rules DO fire — because such a
   body carries a REAL newline before the `Cookie:` token, which is exactly the boundary waves 4-6
   taught those rules to see. The carrier is covered by an EXISTING control on a DIFFERENT axis, so
   enumerating its 32 call sites here would add churn without adding coverage.
   Two consequences belong in the record with it, because the reason is contingent where the old one
   pretended to be absolute: (a) the exclusion FAILS for any body that reaches a backend on a path
   bypassing `Redaction.apply`, and an accessor-keyed inventory cannot see such a path — that is this
   same list's axis 1, one step out; and (b) a session token duplicated into a body FIELD (a JSON
   value, a form parameter) carries no header line and no newline discriminator, so it is the TOKEN
   class (PRIV-02) reachable by different rules — a separate question, named so it is not read as
   covered here either. Excluded on that reasoning, not on cost.
3. **Transitive carriers**, where a cookie byte is copied into a field whose accessor is not on the
   list — `AuditIssue.detail()` is the worked example and task 3 measures it. The inventory can point
   at the FIRST hop; it cannot follow the value through arbitrary copies.
4. **A new Montoya accessor** added by a future API version that returns cookie data under a name not
   in the set. The set is additive-only and a reader adding one must extend it.

Anyone who quotes this test as evidence that no cookie value can reach a backend reproduces, one
iteration smaller, the defect this phase exists to repair. The test's own KDoc must say so.
</the_structural_question_answered>
