<objective>
Close the three things plan 22-07 deliberately left out: the pending-decision lifecycle, the SC3 audit
record, and discoverability of a pending decision from outside the active session.

**The lifecycle is where this phase can still break.** D-08 names three implicit-denial signals; research
measured **five** paths that destroy the card or the session state, and two of them —
`clearCurrentChat()` and `clearInMemorySessionState()` (reached from `MainTab.onProjectChanged()`) —
are not in D-08's list. `clearCurrentChat` calls `panel.clearMessages()`, which removes the card from the
transcript while the pending record survives with no UI able to resolve it: the decision becomes
permanently unresolvable and `onCompleted` never fires, hanging whichever caller supplied it. One
`resolvePending` / `resolveAllPending` pair called from all five sites is the fix; three ad-hoc hooks is
the bug.

**The contradiction between D-08 and D-12 is resolved here, explicitly.** D-08 says every implicit-denial
signal "returns the standard denial result so the model is never left hanging"; D-12 makes the denial
result flow into a followup turn. For paths 2–5 there is no session left to run a turn in, and for path 1
the user has already supplied the next turn. The resolution: **an implicit denial resolves the card,
writes the audit event, invokes the parked `onCompleted`, and terminates — it does not send a followup.**
Only an explicit `Deny` / `Deny for session` click sends the D-12 followup. That satisfies D-08's actual
goal (no continuation dangles) without dispatching a backend request while Burp is tearing down the
extension classloader, or concurrently with the user's own turn.

Purpose: SEC-06 / SC3 (every decision written to the audit log with the tool name, the decision and the
chain step); D-08, D-10 lifecycle.
Output: the five-path lifecycle, the dual-destination decision record, the session-list marker and
`scrollToComponent`.
</objective>

**1. Add the pair.**

- `private fun resolvePending(sessionId: String, reason: ImplicitDenyReason, sendFollowup: Boolean = false)`
- `private fun resolveAllPending(reason: ImplicitDenyReason)`

Both are EDT-confined and touch `pendingDecisions` under the same `@GuardedBy("EDT")` discipline as the
other session maps. `resolvePending` removes the record, calls `ToolApprovalGate.resolve(call.tool,
memory, ToolDecision.IMPLICIT_DENY)`, calls `card.resolve(ToolDecision.IMPLICIT_DENY, reason)` when the
card still exists, emits the SC3 event (Task 2 wires the reporter; leave a single call site here so
Task 2 has one place to fill), invokes the parked `onCompleted`, and returns.

`sendFollowup` defaults to `false` and **stays false at every one of the five call sites**. It exists
only so the parameter documents the decision rather than the absence of a call: an implicit denial
terminates the chain; only an explicit `Deny` click sends the D-12 followup. Put that sentence in the
KDoc together with the two concrete hazards — on `shutdown()` a followup would dispatch a backend request
while Burp is tearing down the extension classloader, and on `sendFromInput()` it would run concurrently
with the user's own turn and clobber `inFlightConnection`.

`onCompleted?.invoke(ToolApprovalGate.DENIAL_RESULT, null)`. Denial is a policy outcome, not an error
