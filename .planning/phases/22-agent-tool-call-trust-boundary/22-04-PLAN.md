<objective>
Complete the AWT-free decision core: per-session approval memory (D-10), the `evaluate` / `resolve` state
machine over D-02's three tiers and D-11's four actions, the D-12 denial constant, and the monotone
iteration-budget helpers that make D-13's "one-line proof" literally a unit test.

Everything here is pure and Swing-free, which is the point: `.planning/codebase/CONCERNS.md` §"UI layer
has no integration tests" is the gap that let SEC-04 ship green, and the answer is not to test a Swing
gate by hand — it is to put the policy where it can be asserted with no harness at all. This mirrors
`mcp/McpAccessControlDecision.kt`, whose access-control matrix is provable with no server and no clock.

Two consequences worth stating up front because they shape later plans:

- `CONFIRM_EACH` consults **neither** session set and writes to **neither**. Combined with plan 22-03's
  fail-closed unknown fallback, this means an unrecognised tool name can never enter
  `approvedForSession` or `deniedForSession` — so `22-UI-SPEC.md`'s compact-row unknown-tool string
  (`Not a known tool — no catalog entry matches this name.`) is **unreachable in this phase**. Plan
  22-06 implements it only for `when` exhaustiveness and ADR-15 records it under "claim only what ships".
- The iteration-budget helpers live here rather than being inlined in `ChatPanel`, so the denial branch
  and the success branch provably share one decrement.

Purpose: SEC-06 / SC2 (approve once, approve-for-session, deny), SC4 (the chain still terminates and a
denied call does not loop); D-02, D-09, D-10, D-11, D-12, D-13.

Extend `mcp/ToolApprovalGate.kt`. Everything stays AWT-free and `internal`.

**1. `internal class ToolApprovalMemory`** — the per-chat-session holder D-10 describes. Three fields,
all private with narrow accessors so the UI cannot mutate them ad hoc:
`approvedForSession: MutableSet<String>`, `deniedForSession: MutableSet<String>`, and
`requestCounts: MutableMap<String, Int>` (the FLAG-22-01 repeat counter, which the planner has
**accepted** — it is the anti-habituation signal `22-UI-SPEC.md` mechanism B needs, and without it the
caption would always read "1st"). All three are keyed on the **canonical** tool ID, never the raw model
string. Constructible with no arguments so `ChatPanel.ToolSessionState` can hold one as a default-valued
field.

KDoc must state D-10's decisive case: an approval granted while reviewing target A must not silently
apply when the user opens a new chat about target B; the memory dies with the chat session because the
holder does. Add the measured fact that `ChatPanel.restoreSessions()` builds a fresh `ToolSessionState`
(`ChatPanel.kt:1475`), so approvals do not survive a Burp restart — that is stricter than D-10 requires
and is deliberate; do not "fix" it by persisting.

Expose `fun recordRequest(canonicalId: String): Int` returning the 1-based count of times this tool has
been requested in this chat, incrementing as a side effect. It is the only mutating method the UI calls
directly.

**2. `internal sealed interface ToolApprovalOutcome`** with three variants, in the shape of
`McpAccessControlDecision.GateDecision`:

- `Run(val origin: ToolCallOrigin, val tier: SecTier, val decision: ToolDecision)` — proceed; `origin`
  is the minted model-approved token from plan 22-03.
- `Ask(val tier: SecTier, val canonicalId: String, val offersSessionActions: Boolean)` — a decision is
  required. `offersSessionActions` is `true` for `CONFIRM` and `false` for `CONFIRM_EACH`, which is
  exactly D-11's four-buttons-versus-two rule computed **here** rather than in the card. The card reads
  the flag; it must not re-derive it from the tier.
- `Denied(val tier: SecTier, val decision: ToolDecision, val result: String)` — refuse; `result` is the
  D-12 constant.

**3. `internal const val DENIAL_RESULT`** — the single fixed, neutral, deterministic denial string
(D-12). Use exactly:

`This tool call was not authorised by the user. Do not retry it; continue with the information you already have.`

English only (CLAUDE.md, AGENTS.md — non-negotiable). KDoc must record **why it is not `Error:`-prefixed**:
`ChatPanel.kt:2157` derives telemetry `status = "error"` from that prefix, and denial is a policy
outcome, not a malfunction — conflating them tells the model something broke, which invites a retry with
different args, and it corrupts the audit record. Also record that determinism matters because stable
templates are a shipped feature, and that the user is deliberately not offered a free-text reason
(user-authored text on a security path breaks determinism and turns a two-second decision into a writing
task).

**4. `internal fun evaluate(rawToolName: String, memory: ToolApprovalMemory): ToolApprovalOutcome`** —
the pre-card branch. Order, exactly:

1. `val canonical = McpToolExecutor.canonicalToolId(rawToolName)`; `val tier = tierFor(rawToolName)`.
2. If `tier == SecTier.AUTO` → `Run(approvedOrigin(tier, ToolDecision.AUTO), tier, ToolDecision.AUTO)`.
3. If `tier == SecTier.CONFIRM_EACH` → **skip both session sets entirely** and return
   `Ask(tier, canonical, offersSessionActions = false)`. Comment this branch: per D-02 this tier has no
   session memory in either direction, which is the whole reason the third tier exists — one click must
   not hand the model unlimited `http1_request` / `http2_request` / `intruder` / `scan_audit_start`.
4. `CONFIRM`: if `canonical` is in `deniedForSession` → `Denied(tier, ToolDecision.SESSION_DENIED, DENIAL_RESULT)`;
   else if in `approvedForSession` → `Run(approvedOrigin(tier, ToolDecision.SESSION_APPROVED), tier, ToolDecision.SESSION_APPROVED)`;
   else `Ask(tier, canonical, offersSessionActions = true)`.
   Check **denied before approved** so a tool that somehow ended up in both fails closed.

`evaluate` takes exactly these two parameters. It takes **no** settings object, **no** enable flag and
**no** bypass parameter — D-09 ships no opt-out and no tier downgrade, and the absence of the parameter
is what keeps ADR-15 a rule rather than a default. Put that sentence in the KDoc.

**5. `internal fun resolve(rawToolName: String, memory: ToolApprovalMemory, action: ToolDecision): ToolApprovalOutcome`** —
applies a user click. Accept only the four D-11 actions plus `IMPLICIT_DENY`; reject `AUTO`,
`SESSION_APPROVED` and `SESSION_DENIED` with `require(...)` since those are gate-derived, not clickable.
Behaviour:

- `APPROVE_ONCE` → `Run(...)`, no memory write.
- `APPROVE_SESSION` → add `canonical` to `approvedForSession`, then `Run(...)`.
- `DENY` → `Denied(..., DENIAL_RESULT)`, no memory write.
- `DENY_SESSION` → add `canonical` to `deniedForSession`, then `Denied(..., DENIAL_RESULT)`.
- `IMPLICIT_DENY` → `Denied(..., DENIAL_RESULT)`, no memory write.

If the resolved tier is `CONFIRM_EACH`, `require` that `action` is not `APPROVE_SESSION` or
`DENY_SESSION` — the card never offers them, and a caller that passes one has a bug the gate should
surface rather than absorb.

**6. Iteration-budget helpers (D-13).** Two one-line functions that reproduce
`ChatPanel.kt:2186-2195`'s existing arithmetic so the denial branch and the success branch provably
share one decrement:

- `internal fun nextIterationBudget(remaining: Int): Int = (remaining - 1).coerceAtLeast(0)`
- `internal fun allowsFurtherToolCalls(remaining: Int): Boolean = remaining > 1`

KDoc must state D-13's property in one sentence: the counter is monotone regardless of what the user
clicks, so `MAX_AUTO_TOOL_ITERATIONS = 8` is respected with no case analysis; and state the reason free
denials were rejected — injected traffic could otherwise walk the model through 59 *different* tools and
produce 59 cards, a user-facing denial of service delivered through the safety control itself. Also
record the residual research measured: a session-denied tool still costs up to seven further backend
round-trips, so deny-for-session bounds the *prompting*, not the *token cost*.

Do not add logging, audit emission or any I/O to this file — the reporter is plan 22-05 and the caller
invokes it from the resolved branch, exactly as `McpAccessControlDecision` and `McpBlockedRequestReporter`
are split.
