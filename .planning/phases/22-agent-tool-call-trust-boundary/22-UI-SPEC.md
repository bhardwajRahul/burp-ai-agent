# Phase 22 — UI Design Contract: Agent Tool-Call Trust Boundary

> Visual and interaction contract for the SEC-06 decision surface. Generated by gsd-ui-researcher.
> Pending verification by gsd-ui-checker.
>
> **Stack: Kotlin + Java Swing inside Burp Suite (ADR-2).** There is no browser, no DOM, no CSS, no
> Tailwind, no shadcn, no design-token JSON and no responsive viewport. The component specified here
> lives inside a `JScrollPane` in a Burp tab whose width the user drags. Web-specific template
> sections are explicitly replaced with their Swing equivalents — see §"Web Sections → Swing
> Equivalents".
>
> **The design system already exists and is authoritative.** Spacing, typography and color are
> inherited verbatim from `09-UI-SPEC.md` / `ui/design/DesignTokens.kt`. This phase declares **zero
> new spacing values, zero new typography roles and zero new color tokens.** Every visual claim below
> cites a token, a builder, or a `file:line` in this repository.

## The Hard Problem: Trust Typography

**This is the single most important section in the document.** Two classes of text share one card:

| Class | Content | Trust |
|-------|---------|-------|
| **Extension-derived** | Card heading, catalog title, tier badge, button labels, tooltips, outcome lines, captions, footers | Trustworthy. Written by this codebase. |
| **Model-supplied** | The parsed tool ID (`ParsedToolCall.tool` — "whatever string the model wrote", `22-CONTEXT.md` §Integration Points), the args JSON | **Attacker-influenceable.** An injected prompt can write "safe routine read" into either. |

A user must tell them apart **without reading carefully.** The mechanism is **containment**, not
decoration — model text is always inside a box, extension text is never inside a box — reinforced by
two further independent channels so that no single failure (a theme with low panel/field contrast, a
colorblind user) collapses the distinction.

### Rule T-1 — Containment (primary channel)

Every model-supplied string is rendered into a **bordered input-styled region** and **nothing
extension-derived ever appears inside one**.

| Region | Widget | Styling | Cites |
|--------|--------|---------|-------|
| Tool ID | `JTextField`, `isEditable = false`, `caretPosition = 0` | `applyFieldStyle(field)` | `Components.kt:484-489` |
| Args JSON | `JTextArea`, `isEditable = false`, `lineWrap = true`, `wrapStyleWord = true` | `applyAreaStyle(area)` | `Components.kt:498-505` |

Both builders set `Typography.mono` + `LineBorder(Colors.border, 1, true)` + `Colors.inputBackground`
+ `Colors.inputForeground`. That single call supplies all three channels at once — this is why the
design-system builder is used rather than hand-set properties.

**Implementation note (real Swing trap):** set `isEditable = false` **before** calling the builder, or
re-assign `background` after it. Several L&Fs paint a non-editable text component with the disabled
background and will overwrite the token value if the order is reversed.

### Rule T-2 — Widget class is a hard boundary (anti-spoofing)

Model text is rendered **only** into `JTextField` / `JTextArea`. It is **forbidden** in:

| Forbidden widget | Why |
|------------------|-----|
| `JLabel` | Swing's `JLabel` interprets a leading `<html>` tag. `"<html><b>Approved</b>"` in a tool ID would render as extension-looking chrome. |
| `JEditorPane` / `JTextPane` with `contentType = "text/html"` | Same, worse. This is exactly what the transcript's message body does (`ChatPanel.kt:1864`) and exactly what `SubtleNotice` does (`SubtleNotice.kt:59`). **Neither may be used for model text on this card.** |
| `setToolTipText(...)` with model content | Swing tooltips render HTML (`SafetyIndicator.kt:43` passes `tooltipHtml` deliberately). A model-authored tooltip is styled, floating, extension-looking text. |
| Any widget that also carries extension text | One widget = one trust class. No `"Tool: " + modelString` concatenations anywhere. |

D-07 says "never markdown, never as extension chrome". In Swing that sentence resolves to exactly this
table.

### Rule T-3 — Font family (secondary channel, theme-independent)

Extension text is **proportional** (`Typography.sectionTitle` / `body` / `caption`); model text is
**monospace** (`Typography.mono`). This channel works in both themes, in grayscale, and at any OS font
size, because it does not depend on any color. It is the channel that still works when the other two
are weak.

### Rule T-4 — Background (third channel — honestly weak in light theme)

Card background is `Colors.cardSurface`; model regions are `Colors.inputBackground`.

- **Dark theme:** `Table.background` ≈ `#333333` vs `TextField.background` ≈ `#3C3C3C` — visible.
- **Light theme:** both resolve close to white (`#F5F5F5` vs `#FFFFFF`) — **nearly invisible.**

This is stated rather than glossed: in light theme the **1 px border (T-1) and the monospace font
(T-3) are the load-bearing signals**, and the design must not be reviewed as if the background did the
work.

### Rule T-5 — An explicit label, in extension chrome

Immediately above the first model region, a `helpLabel` (`Components.kt:331` — `Typography.caption`
+ `Colors.onSurfaceVariant`):

> `AI-supplied — this extension did not write the text below:`

It is outside every box, so by T-1 it cannot be spoofed: model text physically cannot escape into it.

### Rule T-6 — Sanitize before display, with **two** different sanitizers

Reuse the `McpBlockedRequestReporter.sanitize` idiom (`McpBlockedRequestReporter.kt:220-233`,
Phase 20 D-07). It needs two variants, and conflating them is a real defect:

| Sanitizer | Applied to | Regex | Whitespace | Cap |
|-----------|-----------|-------|------------|-----|
| **inline** | Tool ID | `Regex("[\\p{Cntrl}\\u0080-\\u009F]")` → remove | collapse `\s+` → `" "` | 120 chars, `…` suffix |
| **block** | Args JSON | `Regex("[\\p{Cntrl}&&[^\\n\\t]]\|[\\u0080-\\u009F]")` → remove | **preserve `\n` and `\t`** | see §"Args Preview" |

Rationale for the split: `\p{Cntrl}` includes `\n` and `\t`. Applying the inline sanitizer to args
would flatten JSON into one unreadable line — the opposite of D-07's "full args are shown because the
args are where exfiltration hides". Applying the block sanitizer to the tool ID would let a name like
`"scope_check\n\n✔ Approved"` occupy several lines and imitate an outcome row.

Control characters are **removed, never replaced** (CWE-117). The regex lives at
`McpBlockedRequestReporter.kt:25` and the reasoning at `:222-223` — *"REMOVED rather than replaced, so
`"a\r\nInjected: line"` collapses to `"aInjected: line"` and a forged second log line is impossible"*. Stripping `ESC` (0x1B) also neuters ANSI sequences — Swing does not interpret them, but a
bare 0x1B renders as a missing-glyph box and shifts apparent text.

### Rule T-7 — Unknown tool names are labelled, never shown bare

D-07. When tier resolution cannot map the canonicalised ID to a catalog descriptor, the
extension-derived title line reads:

> `Not a known tool — this call will fail if you approve it.`

The model's string still appears, sanitized, inside its box (the user must see *what* was asked for),
but no catalog title is fabricated for it.

## The Hard Problem: Tier Legibility

`AUTO` / `CONFIRM` / `CONFIRM_EACH` must be distinguishable **without relying on color alone** — Burp
ships both themes and some users are colorblind.

### Decision: add a sibling, do not reuse

| Candidate | Verdict | Why |
|-----------|---------|-----|
| `SafetyIndicator` (`ui/components/SafetyIndicator.kt`) | **Reuse the pattern, not the class** | It is `JLabel("Safety: OK")` with an `OK/WARN/RISK` enum and a `setSummary(level, tooltipHtml)` API bound to the main-tab header. Mapping a SEC-06 tier onto a safety level would make one word mean two things. Its **structure** — self-describing text, opaque pill, `EmptyBorder(4,8,4,8)`, `updateUI()` re-apply with an `initialized` guard (`:23-27`, `:50-57`) — is the model. |
| `PrivacyPill` (`ui/components/PrivacyPill.kt`) | **Do not reuse** | It is bound to `PrivacyMode` and it **hardcodes `Color(0x1B9E5A)` / `Color(0xF9A825)` / `Color(0xB3261E)`** (`:11-13`), which violates the token contract. Copying it would propagate that defect. |
| `toolBadge(label, BadgeStyle)` (`Components.kt:426-472`) | **Reuse the rendering idiom** | Correct design-system pill: rounded rect via `fillRoundRect(…, 6, 6)`, `Typography.caption`, `EmptyBorder(2,6,2,6)`, and it **re-reads tokens at paint time** (`:447-451`) plus re-applies foreground in `updateUI()` (`:458-465`). But `BadgeStyle.NATIVE/FULL` means *build provenance*; adding tier variants to that enum makes it mean two things. |

**Specification:** a `private fun tierBadge(tier: SecTier): JLabel` inside `ToolApprovalCard.kt`,
structured exactly like `toolBadge` (`Components.kt:426`) with a border added. Not a public builder in
`Components.kt` — Phase 13's stance ("avoid premature generalisation") applies until a second caller
exists.

### Four redundant channels

| # | Channel | `CONFIRM` | `CONFIRM_EACH` | `AUTO` |
|---|---------|-----------|----------------|--------|
| 1 | **Text** (load-bearing) | `Tier: CONFIRM` | `Tier: CONFIRM EACH` | `Tier: AUTO` |
| 2 | **Border color** (redundant) | 1 px `LineBorder(Colors.statusWarning, 1, true)` | 1 px `LineBorder(Colors.statusError, 1, true)` | 1 px `LineBorder(Colors.statusSuccess, 1, true)` |
| 3 | **Card accent strip** (redundant) | 3 px `statusWarning` | 3 px `statusError` | — |
| 4 | **Button count** (structural) | 4 buttons | 2 buttons | no card |

Channel 1 mirrors `SafetyIndicator`'s own stated rationale verbatim: *"the text spells out the state so
the indicator self-describes without relying on color alone"* (`SafetyIndicator.kt:12-14`). Channel 4
is not decoration — it **is** the semantic difference D-02 encodes, and it survives grayscale, low
vision and a screenshot.

### Badge fill: outlined, not filled — and why

- Background: `Colors.cardSurface` (the design system's declared badge-background role,
  `DesignTokens.kt:138-140`).
- Foreground: `Colors.onSurface`.
- Border: 1 px `LineBorder(tierColor, 1, true)`.

**A filled tier pill was rejected on contrast grounds, measured.** `SafetyIndicator` fills with
`statusTerminal` (`#F57C00`) and sets `foreground = onPrimary` (white) — that is ≈2.9:1, below WCAG AA
for normal text. `PrivacyPill` avoids it for BALANCED by using `onSurface` (`PrivacyPill.kt:35`), but
`onSurface` resolves to `Label.foreground`, which is **light** in dark theme — so the same fix breaks
in the other theme. An outlined badge on `cardSurface` with `onSurface` text has the same contrast
relationship as ordinary body text on a table row, which the design system already guarantees in both
themes. **Color therefore never carries text on this card**; it is moved to the 3 px accent strip
(channel 3), where contrast is irrelevant because the strip carries no glyph.

`AUTO` is specified for completeness so the `when (tier)` is exhaustive and a future value cannot
render blank, but **`AUTO` is unreachable in this phase** — it produces no card (D-02). Claim only what
ships.

## The Hard Problem: The Full State Machine as Visual States

The card is a **record**, not just a prompt (`22-CONTEXT.md` §Specific Ideas). It must read
unambiguously months later.

### Invariant: at most one pending card per chat session

By construction. A pending card parks the continuation, so no second turn runs in that session; and if
the user types a new message, path 1 of the implicit-denial list resolves the pending card **before**
`sendMessage` (22-RESEARCH.md §"Pending-Decision Lifecycle"). Across sessions, N pending cards (one per
session) are possible. **The gate must enforce this invariant; the card must not be designed for a
second one.**

### All states

| # | State | Trigger | Card in transcript | Accent strip | Buttons | Args region |
|---|-------|---------|--------------------|--------------|---------|-------------|
| 1 | **Suppressed — auto** | tier = `AUTO` | **none** | — | — | — |
| 2 | **Suppressed — session-approved** | tool in `approvedForSession` | compact resolved row (**recommended**, see FLAG-22-03) | `borderSubtle` | none | collapsed, expandable |
| 3 | **Suppressed — session-denied** | tool in `deniedForSession` | compact resolved row (**required**) | `borderSubtle` | none | collapsed, expandable |
| 4 | **Pending** | tier = `CONFIRM` | full card | `statusWarning` | 4 | collapsed, expandable |
| 5 | **Pending** | tier = `CONFIRM_EACH` | full card | `statusError` | 2 | **expanded by default** |
| 6 | **Approved once** | click `Approve once` | same card, mutated | `borderSubtle` | replaced by outcome row | state preserved |
| 7 | **Approved for session** | click `Approve for session` | same card, mutated | `borderSubtle` | replaced by outcome row | state preserved |
| 8 | **Denied** | click `Deny` | same card, mutated | `borderSubtle` | replaced by outcome row | state preserved |
| 9 | **Denied for session** | click `Deny for session` | same card, mutated | `borderSubtle` | replaced by outcome row | state preserved |
| 10 | **Implicitly denied** | user sent a new message in this session | same card, mutated | `borderSubtle` | replaced by outcome row | state preserved |
| 11 | **Implicitly denied — container destroyed** | chat cleared / session deleted / project changed / unload | **card no longer exists** | — | — | — |

**State 11 is honest scope.** Four of the five implicit-denial paths (`clearCurrentChat` at
`ChatPanel.kt:971` calls `clearMessages()` at `:1699`; `deleteSession` at `:775`;
`clearInMemorySessionState` at `:1348`; `shutdown` at `:1322`) destroy the transcript or the whole
panel. There is no surviving surface to render an outcome onto. **The durable record for those four is
the SC3 audit event, not the UI.** State 10 — a new message in the same session — is the only implicit
denial with an observable visual state. Do not write a spec sentence claiming otherwise.

### Resolution: buttons are **removed**, not disabled

| Option | Verdict |
|--------|---------|
| Disable the four buttons | **Rejected.** A disabled `JButton` renders as grey text on the same chrome — months later it is indistinguishable from "unavailable", and four dead buttons occupy ~32 px of permanent noise per card in a scrolling record. |
| Remove and replace with an outcome row | **Chosen.** |

The record of *what was offered* is preserved without the widgets, by two things that stay on the card
forever: the **tier badge** (which is what determines whether 4 or 2 buttons existed) and the outcome
line, which **names the clicked action verbatim**.

**Mechanism:** `remove(buttonRow)`, `add(outcomeRow, sameGridBagConstraints)`, `revalidate()`,
`repaint()`. Replacing in the same grid cell keeps every other row from reflowing. The wrapper installed
by `SessionPanel.addComponent` recomputes from `preferredSize` on every layout pass
(`ChatPanel.kt:1681`), so the card shrinking is handled with no extra work.

### Outcome row

`BoxLayout.X_AXIS`: glyph label, `Box.createRigidArea(Dimension(Spacing.xs, 0))`, verb label,
`rigidArea(Spacing.sm)`, timestamp label, `Box.createHorizontalGlue()`.

| Element | Font | Color |
|---------|------|-------|
| Glyph (U+2714 approved / U+2716 denied) | `Typography.body` | `Colors.statusSuccess` / `Colors.statusError` |
| Verb | `Typography.label` | `Colors.onSurface` |
| Timestamp | `Typography.caption` | `Colors.onSurfaceVariant` |

Color appears on the glyph **only**. No filled background on a resolved card: a resolved card must
recede, and a denied card that shouts red forever is itself a habituation trainer.

Timestamp format: reuse whatever `ChatMessagePanel` renders at `ChatPanel.kt:1827` — do not invent a
second format in the same transcript.

### The args region stays expandable after resolution

Non-negotiable. The args are the record; collapsing them on resolution would destroy the reason the
card persists, and auto-collapsing on approve would hide the thing the user just authorised. Whatever
expand state the user left it in is preserved through resolution.

## The Hard Problem: Anti-Habituation

Chains run up to `MAX_AUTO_TOOL_ITERATIONS = 8` (`ChatPanel.kt:1191`), so a user may see several cards
in a row. **Position, stated plainly:**

### Do not add friction to the approve path

Rejected: type-to-confirm, hold-to-confirm, a timed delay before `Approve` becomes enabled, a second
confirmation dialog.

1. **Constant cost trains the routine it is meant to break.** A fixed extra motion becomes part of the
   motor pattern (click, wait, click) and runs without reading. The CONTEXT's own rejection of
   "prompt-for-everything" (D-01) and its acceptance of a deliberately small `AUTO` set (D-05) rest on
   exactly this reasoning: *fewer, more meaningful prompts beat many cheap ones.* Adding cost per prompt
   reverses that.
2. **A time-dependent button contradicts D-11.** D-11 rejected the "remember" checkbox because a widget
   that silently changes what a security button means is a mis-click generator. A button whose
   availability changes over time has the same defect on a different axis: the user cannot answer "what
   does this button do right now" from looking at it.
3. **The escape hatch already exists and is better.** D-09 points at `ToolSessionState.toolsMode`
   (`ChatPanel.kt:1601`). A user who is clicking through is better served by turning tools off than by
   being slowed down.

**Answering the question directly:** friction is *cost without information* and it is automatable.
Anti-habituation is *information that varies with context*, which a motor routine cannot absorb. The
three mechanisms below are all of the second kind.

### The three anti-habituation mechanisms

| # | Mechanism | Applies to | Why it is information, not cost |
|---|-----------|-----------|----------------------------------|
| **A** | Args **expanded by default** on `CONFIRM_EACH`; collapsed on `CONFIRM` | tier | D-02/D-04's entire argument for `CONFIRM_EACH` is *"constant tool name and hostile args"* — the args **are** the decision for that tier. Showing them is not friction, it is showing the thing that must be read. Side effect: the two tiers become physically different sizes, so a `CONFIRM_EACH` card visually interrupts a run of `CONFIRM` cards. Mechanism already exists: `ActionCard(initiallyExpanded: Boolean = false)` (`ActionCard.kt:22`). |
| **B** | **Repeat counter** caption: `2nd request for this tool in this chat` | any tier, when count > 1 | The one signal that actually breaks autopilot: it says *the model is insisting*. Extension-derived (a per-canonical-ID `Map<String,Int>` on `ToolSessionState`), costs nothing, and it changes on every card so it cannot be tuned out. `Typography.caption` + `Colors.statusWarning` foreground. **Required for `CONFIRM_EACH`, recommended for `CONFIRM`.** |
| **C** | **Payload size in the collapsed toggle label**: `▶ Show arguments (4021 characters)` | any tier | A large args blob announces itself before it is opened. Varies per call. |

### Buttons carry no color, and there is no primary action

All four are plain `JButton` with `Typography.body` and default L&F chrome.

- **No `primaryButton(...)`** (`Components.kt:347`). It fills with `Colors.primary` — the 10% accent —
  whose reserved list in `09-UI-SPEC.md` §Color is *"Primary action buttons (e.g. Save Settings),
  ToggleSwitch track when ON, keyboard focus ring, store badge, link-style secondary buttons"*. A
  security affirmative is not on that list, and making `Approve once` the visually dominant control is
  the exact opposite of the goal.
- **No `statusError` on `Deny`.** `09-UI-SPEC.md` reserves the destructive color for *"Delete / Reset /
  irreversible confirmation buttons"*. Deny is neither destructive nor irreversible — it is the safe
  outcome. Colouring it red would miscolour the safe action as dangerous.
- **There is deliberately no default / recommended action.** The card must not nominate a winner. This
  also states the answer to "should approve be more deliberate than deny": approve must not be made
  *easier*, which is a different and stronger claim than making it harder.

## The Hard Problem: Args Preview Sizing and Overflow

### No nested `JScrollPane`

`ActionCard` puts its preview in a `JScrollPane` (`ActionCard.kt:30`). **Do not copy that here.** Three
reasons:

1. **It hides args below a fold**, which is precisely what D-07 argues against ("full args are shown
   because the args are where exfiltration hides").
2. **Nested-scroll wheel trap.** A `JScrollPane` inside the transcript's `JScrollPane`
   (`ChatPanel.kt:1652`) swallows the wheel while the pointer is over it. `ActionCard` rarely hits this
   because it appears once at the top of a session; an approval card appears repeatedly mid-transcript.
3. It removes an entire class of `preferredSize`-vs-`lineWrap`-vs-`maximumSize` interactions.

The args render into a plain `JTextArea` added directly to the card's grid. Height is whatever the
wrapped, capped content needs; the **transcript** scroll pane does the scrolling, which it already does
correctly.

### Three-stage disclosure

| Stage | Toggle label | Content shown | Footer |
|-------|--------------|---------------|--------|
| **Collapsed** (default for `CONFIRM`) | `▶ Show arguments (N characters)` | args area `isVisible = false` | none |
| **Preview** (default for `CONFIRM_EACH`) | `▼ Hide arguments` | first **40 source lines** or **3200 characters**, whichever bites first | if truncated: footer + `Show all N characters` button |
| **Full** | `▼ Hide arguments` | entire sanitized args | `Showing all N characters.`; the button is removed |

Glyphs U+25B6 / U+25BC match `AccordionPanel.kt:103`, so the affordance reads the same as everywhere
else in the extension. `ActionCard`'s label text ("Show payload preview") is not reused because
"arguments" is the accurate noun here.

**Collapsed means `isVisible = false`, not zero height** — `ActionCard.updateExpandedState()`
(`ActionCard.kt:112`) is the correct idiom. A hidden component contributes nothing to `preferredSize`,
which keeps the `getMaximumSize` wrapper at `ChatPanel.kt:1681` correct.

### The caps and where they come from

| Cap | Value | Anchor |
|-----|-------|--------|
| Preview source lines | **40** | Tightens `ActionCard.limitLines(raw, 50)` (`ActionCard.kt:106,118`). 40 is chosen so worst-case preview height ≈ 40 rows ≈ 680 px at base 13 pt — large, but finite, and only reached by a genuinely huge payload, which D-07 wants conspicuous. |
| Preview characters | **3200** | ≈ 40 rows × 80 columns, so the two caps bite at roughly the same visual height instead of one always winning. Covers a typical POST body (500–2000 chars) without truncating. |
| Tool ID inline cap | **120** | Same class of cap as `MAX_HEADER_VALUE_LENGTH = 200` (`McpBlockedRequestReporter.kt:17`), tightened because the field is single-line and narrow. Long enough for any legitimate `ext:<server>:<tool>` triple; short enough that a model cannot use the ID as a canvas. |
| Absolute ceiling (Full stage) | **`Defaults.MAX_CONTEXT_TOTAL_CHARS` = 40 000** (`Defaults.kt:47`) | Defensive only. The args come from model output, which is requested at `Defaults.CHAT_MAX_OUTPUT_TOKENS = 4096` ≈ 16 000 chars (`Defaults.kt:48`), so in practice this can never bite. It exists because a **local** backend may ignore the output cap. |

### Truncation must be honest

When the preview stage truncates, an extension-derived `helpLabel` (`Components.kt:331`) sits directly
under the args box, **outside** it:

> `Showing the first 3200 of 41003 characters. The full arguments are sent to the tool if you approve.`

A bare `…` is **forbidden** here. On a card whose whole purpose is authorisation, an ellipsis reads as
"nothing important follows". The second sentence is the load-bearing one: **the display cap is a
display limit, not an execution limit** — `McpToolExecutor.executeTool` receives the full args string
regardless of what the card renders.

### Wrap behaviour is mandatory, not cosmetic

`lineWrap = true` + `wrapStyleWord = true` (supplied by `applyAreaStyle`, `Components.kt:503-504`).
The transcript scroll pane sets `horizontalScrollBarPolicy = HORIZONTAL_SCROLLBAR_NEVER`
(`ChatPanel.kt:1662`), so a non-wrapping args area would be **clipped with no way to read the rest.**

## The Hard Problem: Keyboard and Focus

### Focus does not move when the card appears

**Required.** Do not call `requestFocusInWindow()` on the card or any of its buttons when it is added.

1. The card is appended from an `invokeLater` (`ChatPanel.kt:667`) after `setSendingState(false)` has
   already re-enabled `inputArea` (`ChatPanel.kt:590`, `:866`). The user may be mid-word. Async focus
   theft loses keystrokes.
2. `inputArea` binds bare `VK_ENTER` to `sendMessage` (`ChatPanel.kt:381`) with `WHEN_FOCUSED`. Moving
   focus away and back makes the destination of an in-flight Enter nondeterministic.
3. An auto-focused approve button plus a stray Enter is exactly the mis-click class D-11 rejected the
   checkbox to avoid.

### Traversal order — safe action first

Visual order **equals** focus order. Do not use a custom `FocusTraversalPolicy` to diverge them.

```
[tool ID field] → [args toggle] → [args area, when visible] →
  [Deny] → [Deny for session] → ⟵16px gap⟶ → [Approve once] → [Approve for session]
```

- Tab from `inputArea` reaches **`Deny`** first. A stray Space on the first-reached button denies —
  the fail-closed outcome, matching this codebase's stated discipline that blocked paths fail closed
  (`22-CONTEXT.md` §Established Patterns).
- **`Deny`, not `Deny for session`, is the reflex target.** Deny-for-session has no in-session undo
  (D-09 ships no settings surface); `Deny` is fully recoverable because the model may ask again.
- Scope escalates left-to-right within each group, so the two **narrowest** actions (`Deny`,
  `Approve once`) flank the gap and the two session-wide actions sit at the outer edges.
- The **16 px gap** (`Spacing.lg`) between the poles is the cheapest mis-click mitigation available: a
  mis-aimed click near the boundary lands in dead space rather than on the wrong pole.
- The non-editable tool-ID `JTextField` is focusable and is a deliberate Tab stop, so a keyboard user
  can select and copy the tool ID.

### Forbidden bindings

| Forbidden | Why |
|-----------|-----|
| `rootPane.defaultButton = <any card button>` | A default button fires on Enter from anywhere in the window. `inputArea`'s Enter binding is `WHEN_FOCUSED` (`ChatPanel.kt:375`), so the moment focus is anywhere without a local Enter binding, the default button wins. |
| `JButton.setMnemonic(...)` | Mnemonics register at `WHEN_IN_FOCUSED_WINDOW`. Alt+A firing an approve from across the panel is the same defect. |
| Escape → Deny | Escape-to-dismiss is a **modal** idiom. On an inline record it would silently resolve a security decision from a keystroke aimed at something else — and it would add a sixth implicit-denial path outside the gate's `resolvePending` set, which is Pitfall 3's exact shape. `inputArea` already owns Escape for `cancelInFlight` (`ChatPanel.kt:384`). |
| Any accelerator or global key binding on the card | Same reasoning. |

**Only a mouse click, or Space on an explicitly-focused card button, resolves the decision.** Space is
Swing's standard `BasicButtonUI` press key and is acceptable *because* the focused button is `Deny`.

### Focus ring must be painted

`isFocusPainted = true` on all four decision buttons. This is a **deliberate deviation from the
neighbouring code** — `ActionCard.kt:58` and `ChatPanel.kt:433` both set `isFocusPainted = false` — and
the executor will copy the wrong line if it is not called out. A keyboard user must see which pole is
focused before pressing Space. Precedent for `true`: `primaryButton` (`Components.kt:353`).

The args toggle keeps `isFocusPainted = false`, matching `ActionCard.kt:58` — it is not a decision
control.

### Focus after resolution

Removing the button row while it owns focus lets Swing move focus somewhere arbitrary (often another
card, or the sessions list). **Before removing the row:** if the focus owner is a descendant of the
card, call `inputArea.requestFocusInWindow()`. That is the only deterministic target and it is where
the user's next action is. Precedent: `ChatPanel.kt:960` already does exactly this after the tools
menu. Guard it on ownership so a mouse click does not yank focus from wherever the user put it.

**Do not scroll on resolution.** The user is where they are.

### Accessibility

Set `AccessibleContext.accessibleDescription` on the card root to an extension-derived sentence naming
the tool, the tier, and the fact that the quoted text is model-supplied. It must embed only the
**inline-sanitized** tool ID (Rule T-6) — this is the one place where a sanitized model string is
concatenated into extension text, and it is acceptable because the accessible description is not a
rendered surface. It is the only channel through which a screen-reader user receives the trust
distinction that sighted users get from the box.

## The Hard Problem: Multiple Pending Cards

### Within the active session

Only pending cards carry a **colored accent strip** (states 4/5); every resolved card drops to
`borderSubtle`. Scanning the transcript therefore answers "is anything waiting for me" with one glance
and no reading. `SessionPanel.refreshScroll()` (`ChatPanel.kt:1711-1716`) already auto-scrolls to the
bottom on `addComponent`, so a newly created card is always in view in the active session.

### Returning to a session that has a pending card

`switchToSession` only swaps the `CardLayout` card, so the transcript is exactly as the user left it —
which means the pending card may be scrolled out of view (22-RESEARCH.md §"Pending-Decision Lifecycle",
verified). **Required:** on switching to a session with a pending decision, scroll the transcript to
the pending card.

New method on `SessionPanel`, mirroring the existing `refreshScroll` idiom (revalidate, then
`invokeLater` so it runs after layout):

```
fun scrollToComponent(c: JComponent)   // c.scrollRectToVisible(Rectangle(0, 0, c.width, c.height))
```

**Do not move focus on switch** — same reasoning as above.

### From outside the session

Without a signal, a pending decision in a background session is invisible and the chain is parked; the
user concludes the model gave up. **Required, minimal:** a third `JLabel` in `ChatSessionRenderer`'s
`textPanel` (already `BoxLayout.Y_AXIS`, `ChatPanel.kt:1625-1627`), visible only when that session has
a pending decision.

| Property | Value |
|----------|-------|
| Text | `Awaiting approval` |
| Font | `Typography.caption` |
| Foreground | `Colors.statusWarning`, **except when selected**, where it follows `list.selectionForeground` exactly as the two existing labels do (`ChatPanel.kt:1631`, `:1639`) |
| Refresh | the existing `refreshSessionList()` (`ChatPanel.kt:1248-1257`) — it re-sets every model element, which re-runs the renderer. Call it when a decision is created and when it resolves. |

Text-first, color redundant. Cheap fallback if adding a label to the renderer is judged too invasive:
append `"  ·  Awaiting approval"` to the existing info string at `ChatPanel.kt:1636` (the `·` separator
is already in use there).

## Color

Inherited from `DesignTokens.Colors` (`DesignTokens.kt:126-199`). **No new token, no `Color(0x…)`
literal, no `Font(...)` constructor.**

### 60 / 30 / 10 on this card

| Share | Token | Where |
|-------|-------|-------|
| **60 % dominant** | `surface` | The transcript this card sits in (`ChatPanel.kt:1658`) — the card does not repaint it |
| **30 % secondary** | `cardSurface` | The card body; the tier badge background |
| | `inputBackground` | Model-supplied regions (rows 5, 7) |
| | `border` / `borderSubtle` | Card outline; model-region outlines; resolved accent strip |
| **10 % accent** | **`primary` is NOT used on this card** | See below |

**`primary` (Burp orange) is deliberately absent.** `09-UI-SPEC.md` reserves it for primary action
buttons, the toggle-on track, the focus ring, the store badge and link-style secondaries. Spending it
on a security affirmative would both violate that list and nominate `Approve` as the recommended
action — the opposite of §"Anti-Habituation".

### Status color budget — three uses, all redundant, none carrying text

| Token | Use | Redundant with |
|-------|-----|----------------|
| `statusWarning` | 3 px accent strip on a pending `CONFIRM` card; tier badge border; repeat-counter caption; session-list pending marker | The badge **text** ("Tier: CONFIRM"), the button count, the caption text |
| `statusError` | 3 px accent strip on a pending `CONFIRM_EACH` card; tier badge border; denied outcome glyph | The badge text ("Tier: CONFIRM EACH"), the button count, the outcome verb |
| `statusSuccess` | Approved outcome glyph; `AUTO` tier badge border (unreachable this phase) | The outcome verb |
| `borderSubtle` | Accent strip on every **resolved** card | The presence of an outcome row instead of buttons |

**Every colored element has a text or structural equivalent carrying the same meaning.** Remove all
color and the card still reads correctly — which is the requirement for two themes plus color
blindness.

### Contrast

The one contrast hazard is the tier badge; it is resolved by outlining rather than filling. See
§"Tier Legibility" for the measured reasoning (`SafetyIndicator`'s white-on-`#F57C00` ≈ 2.9:1;
`PrivacyPill`'s `onSurface` fix inverts in dark theme).

### Destructive color

`statusError` is **not** used on the `Deny` buttons. `09-UI-SPEC.md` reserves it for irreversible
actions; deny is the safe, recoverable outcome. Colouring it red would teach the wrong thing.

## Light/Dark Compliance Rules

1. **No `Color(0x…)` literal, no `Font(...)` constructor, no hardcoded pixel font size** in
   `ToolApprovalCard.kt`. Every value comes from `DesignTokens`. (`PrivacyPill.kt:11-13` is the
   in-repo counterexample — do not follow it.)
2. **All tokens are read at call time**, never cached in a `val` at construction. `DesignTokens`
   properties are computed `get`s for exactly this reason (`DesignTokens.kt:11-14`).
3. **`ToolApprovalCard` MUST override `updateUI()`** and re-apply every token-derived color, font and
   border, using the `initialized`-flag guard idiom. `SafetyIndicator.kt:23-27` documents the hazard
   precisely: the super-constructor calls `updateUI()` **before** Kotlin field initialisers run, so an
   unguarded re-apply NPEs. Same pattern in `SubtleNotice.kt:44-46,91-98` and `AccordionPanel.kt:72-80`.
   `ActionCard` has no such override — that is an existing gap, not a precedent.
4. **The tier badge re-reads its background at paint time** in `paintComponent`, and re-applies its
   foreground in `updateUI()` — exactly `toolBadge`'s two-part handling (`Components.kt:447-451`,
   `:458-465`, flagged there as FLAG-10-01).
5. **Do not migrate neighbouring legacy code.** `ChatPanel` and `ActionCard` keep their `UiTheme`
   imports. This phase adds a component; it does not restructure `ChatPanel.kt` (2248 lines, split
   explicitly out of scope for v0.10.0).

## Flags (Non-Blocking)

- **FLAG-22-01 — Repeat counter needs one new field.** Mechanism B (§Anti-Habituation) requires a
  per-canonical-ID call count on `ToolSessionState` (`ChatPanel.kt:1601`), beside D-10's approve/deny
  sets. It is AWT-free and trivial, but it is the only net-new state the card needs beyond the gate's
  own. If the planner declines it, the counter caption is dropped and mechanisms A and C still stand;
  say so explicitly rather than shipping a caption that always reads "1st".

- **FLAG-22-02 — Session-list pending marker rendering.** Preferred: a third `JLabel` in
  `ChatSessionRenderer.textPanel`. Permitted equivalent: append `"  ·  Awaiting approval"` to the
  existing info string at `ChatPanel.kt:1636`. Both satisfy the requirement (a pending decision in a
  background session must be discoverable). Do not ship neither.

- **FLAG-22-03 — Compact row for session-approved suppression.** Required for **session-denied**
  (otherwise the denial is completely invisible and the chain appears to stall). **Recommended but
  optional** for session-approved, where the existing "Tool result: …" message already shows that
  something ran. Symmetry argues for it; transcript noise argues against. Executor's call — but the
  choice must be deliberate and recorded, not defaulted by omission.

- **FLAG-22-04 — Preview caps (40 lines / 3200 chars) are a judgement, not a measurement.** They are
  anchored to `ActionCard`'s existing 50-line cap and to a ~80-column wrap, and they bound the worst-case
  preview at ≈40 rows. If live UAT shows real `http1_request` args routinely exceeding 3200 characters,
  raise the character cap and keep the line cap — the truncation footer and the `Show all` stage mean
  the security property does not depend on the exact number.

- **FLAG-22-05 — Tier badge stays private to `ToolApprovalCard.kt`.** Not promoted to a public builder
  in `Components.kt` while there is one caller (Phase 13's "avoid premature generalisation" stance). If
  a second surface ever renders a tier — e.g. a column in the MCP Tools tab — promote it then, and take
  the `tier → label` mapping with it so the strings cannot diverge.

- **FLAG-22-06 — U+2716 is an addition to Phase 09's declared glyph set.** Justified in §Glyphs. If the
  checker treats the glyph set as closed, drop both outcome glyphs and keep the text — the text is
  load-bearing and the design degrades cleanly.

- **FLAG-22-07 — Existing transcript renders model text as markdown.** `MarkdownRenderer.toHtml` into a
  `JEditorPane` with `contentType = "text/html"` (`ChatPanel.kt:1864`, `:2070`) escapes `<`
  (`MarkdownRenderer.kt:21`) but still applies markdown styling to model output, including tool results.
  **Out of scope for Phase 22** — recorded here so the observation is not lost. Candidate for Phase 26 /
  DOC-03.
