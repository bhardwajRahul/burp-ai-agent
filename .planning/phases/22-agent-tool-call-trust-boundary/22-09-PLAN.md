  <action>
Append `## ADR-15: A model-emitted tool call requires a user decision before it reaches Burp (SEC-06)` to
`DECISIONS.md`, using ADR-13's three-bold-labelled-section structure and its one-screen length.

**`**Context.**`** must state, with `file:line` anchors in the style ADR-13 uses:

- The threat model in D-14's own terms: model context contains attacker-controlled data — proxy traffic
  sent via "Send to AI", passive-scan findings, and external MCP tool results; the model chooses which
  tool to call; **therefore tool selection is attacker-influenceable**.
- The defect as it stood: `ChatPanel.maybeExecuteToolCall` took `ToolCallParser.extractFirst` output and
  called `McpToolExecutor.executeTool` directly, chaining up to `MAX_AUTO_TOOL_ITERATIONS = 8`, with only
  the per-tool toggles and the `unsafeOnly` flag in the path.
- The demonstrated instance, not the argued one: a model-emitted `scope_check` was observed reaching
  `api.scope().isInScope("http://evil.example/")` with no user decision, driven through the real Send
  button of a real `ChatPanel`. That assertion was red before the gate landed and is green after.
- **Why the `[EXTERNAL-TOOL-RESULT:...]` marker and its advisory note (ADR-11) are mitigation, not a
  control.** Give the concrete, checkable reason: the note at `McpToolExecutorImpl.kt:127-133` is
  appended **only when external tools are present**, so a session that uses no external MCP server
  receives no trust-boundary instruction at all — even though "Send to AI" proxy traffic is already in
  its context. A prompt-level instruction is in any case advisory to a model the attacker is also
  instructing. The marker stays; it stops being counted as a control.

**`**Decision.**`** must state:

- Every model-originated tool call is classified by a required, non-defaulted `secTier` on
  `McpToolDescriptor`. Three tiers: `AUTO` runs silently; `CONFIRM` prompts and offers a per-tool,
  per-chat-session approval; `CONFIRM_EACH` prompts on every call and has no session memory in either
  direction. External `ext:<server>:<tool>` names derive `CONFIRM_EACH` from the namespace. An
  unrecognised name resolves to `CONFIRM_EACH` — fail closed, never `AUTO`.
- **D-05's definition, verbatim and quoted, on its own line** — this sentence is what future tool authors
  inherit and the guard test in Task 2 asserts it byte-for-byte:

  > `AUTO` means read-only AND bounded output. A tool qualifies only if it neither mutates Burp state nor
  > pulls bulk attacker-controlled traffic into model context.

  Immediately after it, the worked examples that close the local-secrets gap **without altering the
  sentence** (research Pitfall 1): `project_options_get` and `user_options_get` are `CONFIRM` despite
  being read-only, because the data is not attacker-controlled but it is the user's own credential
  material — upstream-proxy configuration, session-handling rules, platform-auth material — and the
  destination is the same third-party model. Also state that `proxy_http_history`, site-map listing and
  issue listing are `CONFIRM`, not `AUTO`, which is the load-bearing consequence of the definition.
- **`AUTO` is enumerated, not derived.** The tier is a declared descriptor field; the definition guides
  an author, it does not compute anything at runtime, and `McpToolCatalogTierParityTest` pins the exact
  19-tool `AUTO` set so a promotion is a deliberate, reviewed diff.
- **The classification is deliberately independent of `unsafeOnly` (D-01).** State the sentence a future
  contributor needs when they ask why there are two classifications: *`unsafeOnly` is a capability switch
  — may this tool ever run — not a trust model.* Give the evidence:
  `McpToolContext.isUnsafeToolAllowed` returns `true` for everything the moment `unsafeEnabled` is on, so
  binding the trust boundary to it means one unrelated toggle silently disables the gate. Give the
  concrete demonstration: `ai_analyze` and `ai_passive_scan` are `CONFIRM_EACH` while not being
  `unsafeOnly` at all.
- The decision surface: an inline card in the chat transcript, not a modal, with four explicit actions
  (`Approve once` / `Approve for session` / `Deny` / `Deny for session`) on `CONFIRM` and two on
  `CONFIRM_EACH`. Denial returns one fixed neutral constant that is deliberately not `Error:`-prefixed,
  so a policy outcome is never reported to the model — or to the audit log — as a malfunction.
- **No opt-out and no tier downgrade ship (D-09).** Name the rejected alternatives and why: a persisted
  per-tool `CONFIRM`→`AUTO` downgrade would make a malicious settings import a gate bypass, and a warned
  global off-switch is the control's own bypass shipped in the box — and Unsafe Mode being on is
  precisely the state in which the gate matters most. The escape hatch that does exist is
  `ToolSessionState.toolsMode`, which stops the model calling tools at all rather than un-gating them.
- Origin is structural: `McpToolExecutor.executeTool` takes a required, non-defaulted `ToolCallOrigin`,
  and the model-approved variant is file-private to `ToolApprovalGate.kt`, so a future parse-and-execute
  call site cannot obtain one without going through the decision.
- **Phrasing correction research measured (Pitfall 6):** describe the `CONFIRM_EACH` tier as tools that
  *put attacker-chosen traffic on the wire, **or stage it for one click***. `intruder` and
  `intruder_prepare` populate an Intruder tab rather than launching an attack, so the unqualified
  wire-traffic claim would be false the day it shipped.

**`**Consequences.**`** — bullets, ending with explicit `Residual:` bullets per D-14's "claim only what
ships":

- `AUTO` is deliberately a small set (19 of 59), so the gate is felt. Fewer, more meaningful prompts beat
  many cheap ones; every rejected alternative that produced more dialogs was rejected partly because a
  safety control that trains the user to dismiss it is not a safety control.
- A denied call decrements the iteration budget, so the counter is monotone regardless of what the user
  clicks and `MAX_AUTO_TOOL_ITERATIONS = 8` is respected with no case analysis. Free denials were
  rejected because injected traffic could otherwise walk the model through 59 different tools and produce
  59 cards — a denial of service delivered through the safety control itself.
- Clear Chat clears the per-session approval memory as well as `toolsMode` and `toolCatalogSent`, because
  Clear Chat is the user declaring a new task, which is D-10's own justification for re-consent.
- **Deliberate omission:** the tier is **not** advertised in the tool preamble alongside the existing
  `[unsafe]` / `[pro]` / `[external]` markers, because that would hand an injected prompt a map of which
  tools run silently.
- **Residual:** deny-for-session bounds the *prompting*, not the *token cost* — a session-denied tool
  still costs up to seven further backend round-trips within one chain.
- **Residual:** approvals do not survive a Burp restart. `restoreSessions()` builds a fresh
  `ToolSessionState`, so a chat session restored from `.burp` project data comes back with no approvals.
  That is stricter than required and is intentional; do not "fix" it by persisting the set.
- **Residual:** the resolved card is a **live-session record only**. Decisions are deliberately not
  appended to `session.messages`, because that would also feed them back to the model as history — a new
  prompt-injection surface for no stated requirement — and because tool results are already transient.
  The durable record is the `mcp_tool_decision` audit event plus the enriched `MCP_TOOL_CALL` entry.
- **Residual:** four of the five implicit-denial paths destroy the transcript or the whole panel, so
  they leave no observable card. For those four the audit event is the only record.
- **Residual:** an unrecognised tool name resolves to `CONFIRM_EACH`, which has no session memory, so an
  unknown tool can never occupy a session-suppressed compact row. The compact unknown-tool string is
  implemented for exhaustiveness and is unreachable in this release.
- **Residual:** `assertEdt()` is still a production no-op (QUAL-07), and tool execution is still on the
  EDT — Phase 23 / REL-05 owns moving it. This ADR makes no claim about EDT behaviour.

English only (CLAUDE.md, AGENTS.md — non-negotiable). Do not renumber or edit any existing ADR.
