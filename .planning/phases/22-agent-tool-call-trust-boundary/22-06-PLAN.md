<objective>
Build `ui/components/ToolApprovalCard.kt` — the SEC-06 decision surface — to the approved contract in
`22-UI-SPEC.md`, which is **binding** for every visual and interaction claim in this plan.

The hard problem this component solves is not layout. It is that **two classes of text share one card**:
extension-derived text the user can trust, and model-supplied text an injected prompt can write
"safe routine read" into. The card must let a user tell them apart without reading carefully, which the
UI-SPEC solves by containment (model text is always inside a bordered input-styled box, extension text
never is) reinforced by font family and background, plus an explicit label above the first model region.
Getting this wrong is a live UI-spoofing vector, which is why the spec forbids `JLabel`,
`AbstractButton`, `JEditorPane` and tooltips for model text — all four route text through
`BasicHTML.updateRenderer`, so `"<html><b>Approved</b>"` in a tool ID would render as chrome.

Five `22-UI-SPEC.md` flags are **decided by this plan, not left to the executor**:

- **FLAG-22-01 — repeat counter: ACCEPTED.** Plan 22-04's `ToolApprovalMemory.recordRequest` supplies
  the count; the card renders row 3 when it is greater than 1.
- **FLAG-22-03 — compact resolved row: SHIP BOTH VARIANTS.** Session-denied is required (otherwise the
  denial is invisible and the chain appears to stall); session-approved costs one `when` branch and the
  card is a record, so ship it. Recorded here so the choice is deliberate, not defaulted by omission.
- **FLAG-22-04 — preview caps: keep 40 lines / 3200 characters**, with the 40 000 absolute ceiling read
  from `config/Defaults.MAX_CONTEXT_TOTAL_CHARS` rather than typed literally.
- **FLAG-22-05 — the tier badge stays private** to this file; it is not promoted to `Components.kt`.
- **FLAG-22-06 — U+2716 is kept** as the denied glyph, paired with the already-declared U+2714.

One reachability question the UI-SPEC left open is also resolved here: an unrecognised non-`ext:` name
resolves to `CONFIRM_EACH` (plan 22-03's fail-closed fallback), and `CONFIRM_EACH` has no session memory
in either direction (plan 22-04), so **an unknown tool can never occupy a compact resolved row**. The
compact unknown-tool string is therefore implemented for `when` exhaustiveness and is unreachable in this
phase; ADR-15 records that under "claim only what ships".

Purpose: SEC-06 / SC2 (the decision surfaces to the user before execution); D-06, D-07, D-11.
Output: `ToolApprovalCard.kt` and `ToolApprovalCardTest.kt`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Model-supplied tool ID and args → rendered Swing widget | An injected prompt controls both strings. If either can install Swing's HTML renderer or escape into extension-derived chrome, the card lies to the user at the exact moment it is asking for authorisation. |
| Extension-derived chrome → the user's trust judgement | The catalog title, the tier badge and the button labels are the only trustworthy text on the card; they must be visually and structurally separable from the model's. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-07 | Spoofing | Model text rendered as extension chrome — `"<html><b>Approved</b>"` in a tool ID, or `"scope_check\n\n✔ Approved"` imitating an outcome row | mitigate | Rule T-1/T-2: model text goes only into `JTextField` / `JTextArea`, which never install the HTML renderer; `JLabel`, `AbstractButton`, `JEditorPane` and tooltips are forbidden for it.
