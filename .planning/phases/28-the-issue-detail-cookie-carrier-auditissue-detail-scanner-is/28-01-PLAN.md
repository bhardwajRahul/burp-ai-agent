<objective>
Close the write half of `AR-27-08`: stop a COOKIE-typed injection point's `originalValue` from
reaching `AuditIssue.detail()`, and therefore the `scanner_issues` MCP tool result, under STRICT and
BALANCED — while leaving it verbatim under OFF.

Purpose: this is the one finding in the phase-27 series carrying BURP-HELD proxied traffic (a real
session cookie the operator's browser sent) with no privacy mode protecting it. Phase 27 measured it
and applied no control; disposition stayed TRANSFER, not mitigate.

Output: a policy-keyed control at the write site, and a committed end-to-end test that carries its
own attribution control, its own positive control and its own non-vacuity guard.
</objective>

<design_decision id="D-28-01" title="WHERE the control goes: the write site">
**Chosen:** `ActiveAiScanner.createConfirmedIssue`, via a new named producer
`ScannerIssueSupport.buildActiveIssueDetailLines(...)` that takes a `RedactionPolicy` and applies a
type-keyed gate on `InjectionType.COOKIE`.

**Why:** the write site is the LAST point in the route that still holds the `InjectionType`. Every
site downstream of it holds only a rendered string, so a control placed there must key on the
rendering — and keying on renderings is precisely the mechanism `26-SECURITY.md` records as
structurally blind, and precisely why `cookieTypedParamRegex` could not see this route in the first
place. `McpToolHelpers.kt:359` already states this rule for the sibling parameter carrier:
type-keyed, never shape-keyed. This plan applies the same rule to the same data one hop later.

**Rejected — `IssueUtils.formatIssueDetailHtml`:** it receives `List<String>` and has neither a
privacy mode nor any knowledge of which line came from which injection-point type. An unconditional
rewrite there fails SC2 on its own (OFF would be rewritten too). Plumbing a policy in would make a
pure HTML-escaping utility privacy-aware AND force it to re-parse its own `Original Value: ` prefix
to locate the value — shape-keyed, the rejected mechanism.

**Rejected — `Serialization.kt:14` (`detail = detail()`):** too late and too wide. By then the value
sits inside an HTML-escaped, `<br>`-joined blob with the type information discarded; recovering it
needs the same prefix match, shape-keyed again. It would also control only the MCP emission and
leave the value in Burp's site-map issue for any differently-shaped future consumer.

**Rejected — a new `Redaction` rule:** this is the mechanism phase 27 MEASURED as unable to fire —
no newline for the logical-line rules, wrong shape for `cookieTypedParamRegex`, and `detail` absent
from `SENSITIVE_WORDS`. Fixing it there means either widening `SENSITIVE_WORDS` (measured at 32
false positives, WR-01, and explicitly refused in AR-27-07's maintainer disposition) or teaching the
logical-line rules a `<br>` boundary, which widens the redactor's blast radius across every JSON blob
in the product and adds branches to the one package carrying a jacoco branch floor. Highest cost,
lowest precision.

**Accepted trade, recorded rather than hidden (reversibility: costly, not one-way).** Under
STRICT/BALANCED the operator's own Burp UI issue detail now shows the stripped marker instead of the
value, because `AuditIssue.detail` is stored in Burp's site map as well as emitted over MCP. This is
a user-visible product change in the DEFAULT privacy mode. It is accepted because the operator
retains the raw value byte-for-byte in the SAME issue's request pane — Burp's UI renders
`requestResponses` directly and does not pass through `Redaction.apply`. Task 1 converts that from a
claim into a checked invariant.
</design_decision>
