<design_decision id="D-28-03" title="SC6's scope: examine and file, not fix">
**Chosen:** file as a named residual, `AR-28-01`, with a severity DERIVED from a measurement this
phase takes. Do not fix in this phase.

**Why:** the evidence tail is a different carrier CLASS from the one phase 28 closes. `AR-27-08` is
a TYPED value — an `InjectionPoint` of type `COOKIE` — and a type-keyed gate can see it. The
evidence tail is a matched substring of a per-vuln-class error or success signature; it carries no
type, no name and no shape a gate could key on. Controlling it means one of two things, both bad:
(a) redacting `VulnConfirmation.evidence` wholesale, which destroys the field that is the entire
reason a finding is a finding, and which is the content-destruction regression class round 4 shipped;
or (b) a shape-keyed rule over signature matches, which is exactly the blind mechanism D-28-01
rejects and which `26-SECURITY.md` records failing three times.

**Why filing is nonetheless defensible here and not a repeat of the deferral pattern:** the objection
to phase 27's deferral was never that it deferred — it was that `T-27-08-06`'s disposition stayed
TRANSFER while the record read like mitigation, and that the deferral for a while had no named
owner. This filing carries a measurement taken in-phase, a severity derived from it, an id, an owner
and a decision venue.

**Rejected — fix it here:** would require deciding the redaction shape for a free-text evidence field
under time pressure, in the same phase as an unrelated control, with no measurement of how often a
cookie value can actually match a vuln signature. That is how the previous rounds produced controls
wider than their records.

**Rejected — say nothing:** SC6 explicitly requires the tail to be examined in the same pass. An
unstated choice is the failure the roadmap names.

**A SCOPE FACT THAT MUST TRAVEL WITH BOTH RECORDS, IN A FORM A GREP CAN FIND.** Plan 28-01 controls
ONE LINE of the issue-detail blob — the `Original Value` line at `ActiveAiScanner.kt:1239`. The
`Evidence` line sits in the SAME blob, built at `ActiveAiScanner.kt:1242`, and is NOT controlled;
it is carried forward as `AR-28-01`. Anyone reading "the issue-detail cookie carrier is closed"
without this sentence concludes something false, and that is not hypothetical: a record that reads
WIDER THAN ITS CONTROL is the precise defect behind four wrong PRIV-05 closures.

Because "it must be stated" is exactly the kind of requirement that gets asserted and then not
shipped, the clause is given a FIXED, GREPPABLE FORM. Both the amended `AR-27-08` cell and the new
`AR-28-01` row must carry, verbatim, the sentinel string:

    SCOPE: ONE LINE, NOT THE BLOB

and, in the same cell, both citations that give the sentinel meaning: `Original Value` — the line
plan 28-01 DOES control, at `ActiveAiScanner.kt:1239` — and `ActiveAiScanner.kt:1242`, the `Evidence`
line in the same blob that it does NOT control and which is carried as `AR-28-01`.

**Vacuity, measured rather than assumed, because two of these three greps are not equal.** MEASURED
2026-08-27 against the CURRENT `AR-27-08` cell (3545 characters): `Original Value` ALREADY APPEARS —
the row's mechanism paragraph says the rendered shape is `Original Value: <value>` — so a grep for it
on that row passes TODAY and proves NOTHING about the amendment. `ActiveAiScanner.kt:1242` and the
sentinel are both ABSENT (count 0 each), so those two are the load-bearing gates. On the NEW
`AR-28-01` row all three are non-vacuous because the row does not yet exist. Task 3 derives these
pre-amendment counts and records them, so a reader can tell which gate measured a change.

A clause that lives only in the SUMMARY does not satisfy this: the SUMMARY is read once, by this
phase; the register is read by every round after it.

**Owner and venue:** the maintainer, at phase 28 human UAT — the same venue that dispositioned
`AR-27-04`, `AR-27-07`, `AR-27-10` and `AR-27-11`. Named in the register's OWNER field per standing
rule (viii)(a).

Reversibility: **one-way.** The register is append-never-rewrite; once `AR-28-01` and the `AR-27-08`
supersession are written they can be superseded but never deleted. Task 2 is the gate.
</design_decision>

<design_decision id="D-28-04" title="PRIV-05 stays OPEN">
**Chosen:** leave `REQUIREMENTS.md` byte-unchanged. PRIV-05 stays `- [ ]`.

**The enumeration, because the requirement's own wording demands one.** PRIV-05 reads: "Cookie
values do not reach an AI backend in STRICT or BALANCED mode **by any path**"
(`REQUIREMENTS.md:23`). "By any path" is an enumeration obligation. Carriers with recorded human
dispositions that are still OPEN:

- **AR-27-04** — MEDIUM, MAINTAINER-SIGNED ACCEPTANCE. `Host:` and `SiteMapEntry.url` reach an AI
  backend un-anonymised under STRICT on the serialized emission shape. Behaviour SHIPS.
- **AR-27-07** — LOW, KEPT AT LOW. A sensitive-NAMED non-COOKIE parameter survives `request_parse`'s
  serialized JSON in STRICT. `SENSITIVE_WORDS` deliberately not widened (WR-01's measured 32 false
  positives).
- **AR-27-10** — LOW, ACCEPTED. 13 RFC 9110 tchars still uncovered; both halves remain inferred.
- **AR-27-11** — MEDIUM, ACCEPTED over FOUR measured families. `JSON_STRING_OPEN` is literally
  colon-then-quote, so any interposed character — a space in pretty-printed JSON, a backslash in an
  escaped nested body — or no colon at all is not a recognised logical-line start. This is the one
  reachable in the DEFAULT posture.
- **AR-28-01** — this phase's new residual, severity derived by task 1.

And the `CookieCarrierInventoryTest` mechanism states its own bound in its class KDoc: it is a
tripwire over a measured accessor set, NOT a proof of coverage, blind to four named axes —
operator-pasted text, `bodyToString()` bodies reaching a backend on a path bypassing
`Redaction.apply`, transitive carriers beyond the first hop, and future Montoya accessors.

Closing `AR-27-08` closes ONE carrier. Five are open and the enumeration mechanism disclaims
completeness. PRIV-05 cannot close.

**Enforcement, not just intent — AND NOT ONLY IN THE WRONG PLACE:** on 2026-08-27
`gsd-tools query phase.complete 27` flipped PRIV-05 to `[x]` as a side effect while its own warnings
said it was skipping that write (WINDOWS entry 54). Refraining from editing the file is therefore not
sufficient. But note WHERE that happened: at PHASE-COMPLETION time, after the last plan's last task.
A gate that runs only inside task 3 runs strictly BEFORE `phase.complete` and is structurally
incapable of observing the very failure this decision cites. So the gate runs TWICE.
RUN 1 is in task 3: re-derive the sha256, assert the unchecked box, record under
`## PRIV-05 gate — RUN 1, in-task (plan 28-03 task 3)`.
RUN 2 is mandated in this plan's `<verification>` block: the same two commands re-run AFTER
`gsd-tools query phase.complete 28` and immediately BEFORE the phase commit, with revert-and-record
on any movement, under `## PRIV-05 gate — RUN 2, post-completion, pre-commit`. RUN 2 is the run that
gates the recorded incident; RUN 1 alone does not satisfy this decision.

Reversibility: reversible — a future phase can close PRIV-05 when the enumeration comes out clean.
</design_decision>
