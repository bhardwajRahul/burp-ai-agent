<objective>
Close Finding 15 (SEC-07, ROADMAP SC3 + SC4): `SsrfGuard` **parses** IPv4 literals written in decimal,
octal and hexadecimal notation instead of rejecting them at a dotted-quad regex, then classifies them
identically to their dotted-quad equivalent — while performing strictly less name resolution than it
does today, not more.

Purpose: `SsrfGuard.kt:43-45` gates classification behind `IPV4_REGEX = ^\d{1,3}(\.\d{1,3}){3}$`.
Anything that is not a dotted quad and not IPv6-shaped returns `false` before
`InetAddress.getByName` at `:49` is ever reached. So `http://2852039166/` — the decimal spelling of
`169.254.169.254`, the cloud-metadata address the guard exists to flag — is silently classified as
"not private". The advisory warning is sidestepped by notation alone.

Output: a pure, network-free `Ipv4Literal.parse` implementing inet_aton notation rules; `SsrfGuard`
rewired to classify from its bytes via `InetAddress.getByAddress`; and a behavioural proof, not an
assumption, that the classifier resolves nothing.
</objective>

<named_assumptions>
Unresolved edges surfaced as explicit assumptions. Each carries a paired assertion that resolves it.

- **A-25-07 (boundary).** The accepted notation set is the classic `inet_aton` grammar, with the
  arity-dependent ranges in the table below. Everything outside it is rejected — and rejection means
  `parse` returns null and `SsrfGuard` returns false WITHOUT resolving, which is a strictly safer
  outcome than today's silent DNS lookup.

  | parts | form | per-part maxima | assembled 32-bit value |
  |---|---|---|---|
  | 4 | `a.b.c.d` | a,b,c,d <= 255 | `a<<24 \| b<<16 \| c<<8 \| d` |
  | 3 | `a.b.c` | a,b <= 255; c <= 65 535 | `a<<24 \| b<<16 \| c` |
  | 2 | `a.b` | a <= 255; b <= 16 777 215 | `a<<24 \| b` |
  | 1 | `a` | a <= 4 294 967 295 | `a` |

  *Paired assertion:* `Ipv4LiteralTest` pins both sides of every boundary named in the probe —
  `255` accepted / `256` rejected in 4-part form; `0xFFFFFFFF` accepted / `0x100000000` rejected in
  1-part form; octal `0377` accepted / `0400` rejected in 4-part form; the 3-, 2- and 1-part forms
  each producing the address in the table; and empty, over-long, zero-part and five-part inputs all
  rejected.

- **A-25-08 (precision).** Every intermediate value is a Kotlin **`Long`**. `2852039166` already
  exceeds `Int.MAX_VALUE` (2 147 483 647) and would overflow to a negative `Int`; the largest legal
  1-part value, `4 294 967 295`, needs 33 signed bits. The contract is: each part is accumulated with
  `String.toLongOrNull(radix)` (which returns null on overflow rather than wrapping), range-checked
  as a `Long` against the table above, assembled into a single `Long`, and only then truncated one
  byte at a time into the output `ByteArray`. **No `Int` appears anywhere in the arithmetic path.**
  *Paired assertion:* `Ipv4LiteralTest` asserts `parse("2852039166")` yields the bytes
  169/254/169/254 (the exact value that would have overflowed), `parse("4294967295")` yields
  255/255/255/255, and `parse("4294967296")` returns null.

- **A-25-09 (JDK divergence).** `InetAddress.getByName` on JDK 21 does not implement inet_aton octal —
  measured above, `0177.0.0.1` becomes `177.0.0.1`. The JDK therefore cannot be used as the parser,
  and the divergence is permanent enough to hard-code an expectation against.
  *Paired assertion:* `Ipv4LiteralTest` asserts `parse("0177.0.0.1")` yields the bytes 127/0/0/1, and
  a KDoc line in `Ipv4Literal.kt` records the measured JDK result so the next reader does not
  "simplify" the parser away.
</named_assumptions>
