<objective>
Close ROADMAP SC5 (SEC-07): the `openConnection` loopback trust-all path stops accepting any
certificate from any listener and is scoped to exactly the certificate the extension generated.
Record the whole phase's security reasoning in ADR-16 and in the operator runbook.

Purpose: `McpSupervisor.openConnection` builds an `X509TrustManager` whose `checkServerTrusted` body
is `= Unit` and sets `conn.hostnameVerifier = HostnameVerifier { _, _ -> true }` whenever TLS is on
and the host is loopback. Under that configuration the takeover client cannot distinguish the
extension's own MCP server from any local process holding the port with any self-signed certificate.
Plan 25-01 removes the bearer token from that exchange, so the blanket trust no longer leaks a
credential — but it still leaves the client structurally unable to tell who it is talking to, and
25-01's own threat register (T-25-02, T-25-03) defers "real listener identity for TLS configurations"
to this plan. Leaving it deferred would make that mitigation text false.

Output: `McpTls.pinnedLeafSha256`, an `openConnection` that trusts exactly one certificate and fails
closed when it cannot name one, a test that proves the pin discriminates against a real second
certificate, ADR-16, and an operator-facing section in `docs/mcp-hardening.md`.
</objective>

<sc5_option_selection>
ROADMAP SC5 offers two answers: **scope the trust-all path to exactly the certificate the extension
generated**, or **document its residual risk**. This plan takes the first, and the reason is stated
here rather than left implicit because SC5 permits either.

Documenting the residual is the weaker answer in this specific phase, for three checkable reasons.
First, the ROADMAP itself says a blanket trust-all on loopback "is what makes finding 7 exploitable" —
so a phase whose entire purpose is finding 7 would be closing the credential half and writing down
the other half. Second, 25-01's threat register already promises this: T-25-02 and T-25-03 both carry
the sentence "Real listener identity is additionally restored for TLS configurations by plan 25-03's
certificate pin", and shipping documentation instead would leave two mitigations in a committed
threat model describing something that does not exist. Third, the work is small and the material is
already in hand — the extension generates the certificate itself, in a path its own settings name, so
"exactly the certificate we generated" is one keystore read away rather than a new trust
infrastructure.

The residual that genuinely cannot be engineered away is recorded in ADR-16 instead: a local attacker
who can READ `settings.tlsKeystorePath` can present that certificate and satisfy the pin. That
attacker also holds the MCP token, because `SecretCipher`'s master key sits beside its ciphertext in
Burp Preferences (QUAL-07), so pinning was never the control standing between them and the server.
The boundary pinning does defend is the one finding 7 is about: another local process that can bind
the port but cannot read the user's files.
</sc5_option_selection>

<named_assumptions>
Unresolved edges surfaced as explicit assumptions. Each carries a paired assertion or a named
fallback that resolves it.

- **A-25-10 (pin availability implies our server).** `KtorMcpServerManager.start` throws
  `IllegalStateException("TLS enabled but keystore not available.")` when `McpTls.resolve` returns
  null, so the extension's own MCP server cannot be running under TLS unless a readable keystore
  exists at `settings.tlsKeystorePath`. Therefore a client that cannot compute a pin from that same
  path is not talking to our server, and weakening TLS to reach it would be exactly backwards.
  Fail-closed is not a compromise here; it is the correct classification.
  *Paired assertion:* `McpTakeoverCertificatePinTest.noPinAvailableInstallsNoOverrideAndFailsClosed`
  asserts the takeover returns false, the server survives, and the non-existent keystore path is
  STILL non-existent afterwards.

- **A-25-11 (JDK client against a Netty TLS connector).** `openConnection` returns an
  `HttpURLConnection`, so the takeover client speaks HTTP/1.1 over the JDK's TLS stack. Every existing
  TLS test in this repo (`McpLocalTlsAuthorityPipelineTest`) drives the server with OkHttp instead, so
  a JDK client against the Netty `sslConnector` has no in-repo precedent, and the connector advertises
  `h2` ahead of `http/1.1` over ALPN. The assumption is that a JDK client which offers no ALPN
  protocols negotiates `http/1.1` normally.
  *Named fallback, to be used only if the handshake fails for a reason unrelated to pinning and to be
  recorded in the SUMMARY:* prove the pin at the `SSLContext` layer instead — take the
  `SSLSocketFactory` that `openConnection` installs, open a raw `SSLSocket` to the running server and
  assert the handshake completes with the right pin and throws `SSLHandshakeException` with the wrong
  one. That is still behavioural and still against the real server; it simply stops one layer short
  of the HTTP exchange. Do NOT downgrade to a mock-connection assertion — `McpSupervisorConnectionTest`
  already covers the wiring, and wiring is not a handshake.
</named_assumptions>

  <action>
Add `fun pinnedLeafSha256(settings: McpSettings): ByteArray?` to the `McpTls` object. It trims
`settings.tlsKeystorePath`, returns null when blank, returns null when the file does not exist, and
otherwise loads a `PKCS12` `KeyStore` with `settings.tlsKeystorePassword`, takes the first alias
exactly as `resolve` does, and returns the SHA-256 digest of that certificate's `encoded` form. Wrap
the load in `runCatching { }.getOrNull()` so a corrupt or wrong-password keystore yields null rather
than a throw — `runCatching` has no catch clause, so it introduces no `TooGenericExceptionCaught` or
`SwallowedException` finding, and the baseline is frozen at 1096 by QUAL-07.

**Do not implement this by calling `resolve`, and leave a KDoc line saying why.** `resolve`
auto-generates a keystore when `tlsAutoGenerate` is on and none exists. A client-side probe that
generated one would create a file the user never asked for AND mint a fresh certificate that by
construction cannot match the certificate the already-running server is presenting — a pin that is
guaranteed wrong. This function reads or returns null. That asymmetry is the reason the duplication
is deliberate rather than sloppy, and the next reviewer will ask.

Then change `openConnection` in `McpSupervisor.kt` from `(url: URL, tlsEnabled: Boolean)` to
`(url: URL, settings: McpSettings)` and update both call sites, which currently pass
`settings.tlsEnabled`. Inside, keep the existing `tlsEnabled && conn is HttpsURLConnection` and
loopback-host conditions exactly as they are. What changes is what happens inside them:

- Compute `McpTls.pinnedLeafSha256(settings)`.
- **Pin available:** install an `SSLContext` whose single `X509TrustManager` implements
  `checkServerTrusted` as: SHA-256 the FIRST certificate of the presented chain, compare against the
  pin with `MessageDigest.isEqual`, and throw `java.security.cert.CertificateException` when it
  differs. `checkClientTrusted` throws as well — this is a client-side manager and is never called,
  and leaving it as `= Unit` is a footgun the day someone reuses the object. `getAcceptedIssuers`
  returns an empty array. Then set a `HostnameVerifier` that returns true only when the session's
  first peer certificate digests to the same pin. That verifier is a REPLACEMENT for hostname
  identity, not a disabling of it: the generated certificate is `CN=burp-mcp` and can never match
  `localhost` or `127.0.0.1`, so the identity assertion moves from the name to the key. Read the
  peer chain through `runCatching { session.peerCertificates }.getOrNull()` so an unverified session
  yields false instead of propagating `SSLPeerUnverifiedException`.
- **Pin unavailable (null):** install NOTHING. Leave `conn.sslSocketFactory` and
  `conn.hostnameVerifier` at their JDK defaults, which reject the self-signed certificate and make
  the takeover fail closed. Log one line through `api.logging().logToOutput` naming the keystore path
  and saying the takeover was not attempted under TLS because no pinned certificate could be read.
  See A-25-10 for why this is the correct classification and not a degradation.

Keep the whole thing within detekt's limits: `ReturnCount` is active at a maximum of 2, so extract
the trust-manager construction into a private helper such as `pinnedSslContext(pin: ByteArray)` and a
private `leafDigestMatches(chain, pin)` rather than growing `openConnection` into a return cascade.
`MessageDigest.getInstance("SHA-256")` needs no named constant (it is a string), and `chain[0]` uses
index 0, which detekt's `MagicNumber` ignores by default.
