<objective>
Surface **WR-01** as a maintainer decision and record the answer.

Plan 21-04's `SENSITIVE_KEY_EXPR` widening satisfied SC3 exactly as designed — 31/31 must-redact, 21/21
must-not-redact, strictly monotone, zero new vocabulary words. But the code review drove the same
expression over a wider corpus and found the redacted class is far bigger than the ten accepted
over-redactions the tests record, and includes names a security-analysis prompt cannot function without:
`status_code`, `error_code`, `response_code`, `http_code`, `statusCode`, `errorCode`, `token_type`,
`tokenType`, `zip_code`, `country_code`, `postal_code`, `primary_key`, `foreign_key`, `sort_key`,
`partition_key`, `cache_key`, `public_key`, and more. `{"statusCode": 401, "errorCode": "AUTH_FAILED"}`
becomes `{"statusCode": "[REDACTED]", "errorCode": "[REDACTED]"}` before the analysis prompt is built —
the model is then asked to find an authentication flaw with the status and error code removed.

This is a **judgement call with real utility impact in both directions**, which is why it is a decision
gate and not an implementation task. Narrowing the expression would *loosen* a security pattern, which
`.planning/codebase/CONCERNS.md`'s tightening protocol permits only with the reason documented, and it
risks the 31/31 must-redact result plan 21-04 measured. Leaving it costs the scanner its status and error
codes on every JSON body. The reviewer's framing is the operative one: silently accepting `status_code`
is not the same as deciding it.

This plan therefore does exactly two things: it asks, and it pins the answer in the test corpus so the
decision is asserted rather than remembered. It is the last wave because it touches `RedactionTest.kt`
and `Redaction.kt`, both of which are serialization points for the earlier gap-closure plans.

Purpose: PRIV-05 / SC3, WR-01.
Output: a recorded decision, a corpus that asserts it, and the phase-wide deferral record.
</objective>

Combined with D-11's whole-token boundary rule, the two broadest words — `code` and `key` — drive an
over-redaction class much larger than the ten cases plan 21-04 recorded and asserted. Measured by the
reviewer against the live `formBodyParamRegex` and `jsonSecretKeyRegex`:

`primary_key`, `foreign_key`, `sort_key`, `partition_key`, `cache_key`, `idempotency_key`, `row_key`,
`public_key`, `sortKey`, `cacheKey`, `zipCode` — all redacted.

What is at stake in each direction:

- **Keeping it** costs the passive scanner its status and error codes on every JSON response body it
  analyses. `token_type: "Bearer"` — benign OAuth metadata — goes the same way. The reviewer classifies
  this as a functional regression in a passive-vulnerability scanner rather than a cosmetic
  over-redaction, and the product's core job is reasoning about exactly those values.
- **Narrowing it** is a *loosening* of a security pattern. `.planning/codebase/CONCERNS.md`'s protocol —
  "add the pattern, add the test, never loosen an existing pattern without documenting why" — is binding
  and was explicitly honoured in Phase 21, where the widening was verified strictly monotone across the
  60-key corpus. Any narrowing must re-measure that corpus rather than reason about it, and `public_key`
  in particular sits on the boundary: it is benign in a JWKS response and is not benign next to a
  private key.

Nothing else in this gap-closure round depends on the answer. All four blockers CR-01..CR-04 are closed
by plans 21-08 through 21-11 regardless of which option is chosen.
  </context>

## Deferred

Warnings from `21-REVIEW.md` deliberately **not** folded into this gap-closure round, with the reason each
was left. None is a blocker; all remain open and are recorded here so a later reader can tell a deliberate
deferral from an oversight.

- **WR-02** — the OFF-mode privacy banner infers "custom patterns are applied" from the unsaved
  `JTextArea` text rather than from `settings.customRedactionPatterns`. Not adjacent to any blocker; it is
  a `ui/` fix in a file no gap-closure plan touches, and the two sibling call sites already read the
  persisted list, so the corrected form is already established in the codebase. One-line fix, better
  batched with the next `ui/` pass.
- **WR-03** — `SafeRegex.replaceAllSafe` is dead in production and retained as a fail-open footgun.
  Deleting or `DeprecationLevel.ERROR`-marking it touches `SafeRegex.kt` and `SafeRegexTest.kt`, neither of
  which any blocker fix needs, and D-14 deliberately preserved the function's contract so
  `SafeRegexTest:44` would stay green unchanged. Reversing that decision belongs with the maintainer, not
  inside a blocker fix.
- **WR-04** — `Redaction.truncationLogger` is never cleared in `App.shutdown`, so a redaction in flight
  during teardown can call a torn-down `api.logging()`. Real, and a two-line fix, but it is in `App.kt`
  which no gap-closure plan touches, and it is a teardown-race robustness issue rather than a correctness
  or disclosure defect. Fold into the next `App.kt` change.
- **WR-07** — `isPatternSafe`'s single fixed probe (`"a".repeat(2_000) + "!"`) accepts patterns that are
  catastrophic on a different character class, and D-05 widened the blast radius of a bad accept in both
  directions. Genuinely important, but widening the probe corpus and re-validating at seed time changes
  `SafeRegex.kt` and `App.kt` and needs its own measurement of the added startup cost. Too large to fold
  into a blocker fix; flag for the next privacy phase.

**Folded in rather than deferred:** WR-05 (plan 21-11) and WR-06 (plan 21-09), both because they are the
test gaps the blockers fell through — WR-06 is the missing D-01 invariant assertion CR-02 slipped past,
and WR-05's `assertFalse(output.contains(body))` is satisfied by any single-character change and therefore
guarded nothing in the very machinery CR-04 rewrites.
