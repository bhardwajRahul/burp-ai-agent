<objective>
SC3. Replace the exact-word `SENSITIVE_KEYS` alternation with a key **expression**, so that
`auth_token`, `api-key`, `X-Session-Id`, `remember_me`, `JSESSIONID`, `PHPSESSID`, `connect.sid` and
`csrftoken` are recognised as sensitive, without over-redacting `keyboard_layout` or `codename`.

Today `SENSITIVE_KEYS` demands the key be *exactly* one of twelve words, which is why `auth_token`
misses (`auth` is followed by `_`, not `=`) and why only a cookie literally named `session` is caught.
The replacement mechanism was measured against the project's live regexes on JDK 21: **31/31**
must-redact, **21/21** must-not-redact, and strictly monotone across a 60-key corpus.

`SENSITIVE_KEYS` is a single `private const val` shared by `urlTokenParamRegex`, `formBodyParamRegex`
and `jsonSecretKeyRegex` — one point of change and one point of blast radius. Widening it widens
query-string, form-body and JSON redaction simultaneously. That is desirable and must be
regression-tested in all three.

Purpose: PRIV-05 / SC3.
Output: `SENSITIVE_KEY_EXPR` plus a vendor-name list in `Redaction.kt`, and a both-directions corpus in
`RedactionTest.kt`.

**This plan does not touch cookies (plan 21-05), the body stage (plan 21-06), the HKDF block
(`Redaction.kt:167-227`, SC6 forbids it) or `Redaction.apply`'s control flow.**
</objective>

  <action>
Five new `private const val`s in `object Redaction`, replacing `SENSITIVE_KEYS` at `:86-89`. Write them
in this order, immediately where `SENSITIVE_KEYS` is today, each with a `//` comment tagged
`PRIV-05 / SC3 / D-11` (or `D-13` for the camelCase pair):

1. `SENSITIVE_WORDS` — the **unchanged** twelve-word vocabulary, byte-identical to today's
   `SENSITIVE_KEYS` value: `access_token|api_key|apikey|auth|token|key|secret|password|pwd|session|sid|code`.
   Comment that the vocabulary is deliberately not widened: the SC3 corpus is satisfied without adding
   a single word, and adding words multiplies the false-positive surface across three regexes
   (Pitfall 10).

2. `KNOWN_SESSION_KEYS` — vendor and framework session-cookie names that no morphological rule can
   catch, because the sensitive word is concatenated without a separator or absent entirely. Whole-key,
   case-insensitive, dots escaped. Value (Kotlin string, so each regex backslash is doubled in source):
   `jsessionid|phpsessid|asp\.net_sessionid|\.aspxauth|aspxauth|csrftoken|remember_me|remember_token|laravel_session|ci_session|_session_id|sessionid|sessid|cfid|cftoken|xsrf-token|_csrf`

3. `KEY_CHARS` — the character class a key name may be built from: `[A-Za-z0-9_.\-\[\]]`. Comment that
   the square brackets cover PHP array parameters of the `a[b]` form.

4. `WORD_BEFORE` and `WORD_AFTER` — the boundary constructs (D-13). `WORD_BEFORE` is
   `(?:(?<![A-Za-z0-9])|(?-i:(?<=[a-z0-9])(?=[A-Z])))` and `WORD_AFTER` is
   `(?:(?![A-Za-z0-9])|(?-i:(?<=[a-z0-9])(?=[A-Z])))`. Comment the non-obvious blocker: the camelCase
   half **cannot** be written inline under `(?i)`, because case-insensitivity makes `[A-Z]` match
   lowercase — Java's inline flag-off group `(?-i:...)` is what makes it work, and it is verified on
   JDK 21. Name the one-line revert point explicitly: dropping the `(?-i:...)` alternative from both
   constants reverts D-13 and loses nothing SC3 requires.

5. `SENSITIVE_KEY_EXPR` — `(?:(?:$KNOWN_SESSION_KEYS)|$KEY_CHARS{0,64}$WORD_BEFORE(?:$SENSITIVE_WORDS)$WORD_AFTER$KEY_CHARS{0,64})`.
   Its comment must state three things: (a) a key is sensitive when it **is** a known vendor name or
   when it **contains** one of the words as a separator-delimited whole token, treating `_`, `-`, `.`,
   `[`, `]`, the string boundaries and lower-to-upper case transitions as delimiters; (b) prefix and
   suffix are **bounded at 64 characters** because an unbounded `*` measured 2.3x slower on adversarial
   input (21 ms vs 9 ms on 1 MB) and reintroduces exactly the unbounded-quantifier adjacency this file
   already warns about at `:100`; (c) every internal group is **non-capturing**, so the group numbering
   of every consumer is unchanged (Pitfall 7).

Then rewrite the three consumers, keeping every existing comment block above them intact and adding a
`PRIV-05 / SC3` line to each:

- `urlTokenParamRegex` becomes `(?i)([?&](?:$SENSITIVE_KEY_EXPR)=)[^&\s"'<>]+` — group 1 is still the
  `[?&]key=` prefix, so the existing `"$1[REDACTED]"` replacement at `:251` is unchanged.
- `formBodyParamRegex` becomes `(?im)(^|[?&])($SENSITIVE_KEY_EXPR)=[^&\s"'<>]+` — group 1 is still the
  `^`/`?`/`&` prefix and group 2 is now the **whole** key, so the existing lambda at `:261-263` still
  reproduces compound keys such as `auth_token` exactly.
- `jsonSecretKeyRegex` becomes `(?i)("$SENSITIVE_KEY_EXPR"\s*:\s*)("[^"]*"|true|false|null|-?\d+(?:\.\d+)?)`
  — group 1 is still `"key":` including whitespace and group 2 is still the value, so the existing
  lambda at `:266-268` is unchanged. Note that the old value had an explicit `(?:...)` wrapper around
  `SENSITIVE_KEYS`; `SENSITIVE_KEY_EXPR` is already `(?:...)`-wrapped, so do not double-wrap it here.

**Explicitly do NOT add a benign-key guard (D-12).** The recommendation proposed one; measurement found
zero false positives to guard against — all 21 must-not-redact keys pass on the boundary rule alone.
Say so in the `SENSITIVE_KEY_EXPR` comment so a future reader does not add a denylist: every entry in
such a list is a place where a real credential could be accidentally allowlisted.

Record two residuals in the same comment block, both deliberate: **plural forms** (`codes`, `tokens`,
`keys`) are not handled — adding `s?` to the vocabulary would catch them at the cost of a second
widening axis, and SC3 does not require it; and the **accepted over-redactions** produced by
whole-token matching — `token_bucket_size`, `session_timeout_seconds`, `auth_provider`, `key_size`,
`code_version`, `secret_santa`, `password_hint_enabled` under the separator rule, and `codeName`,
`keyName`, `tokenCount` under the camelCase rule. All are over-redaction (the fail-safe direction) of
analytically low-value data; `auth_provider` is the only one with real analytic value and is still the
correct default.

Change nothing else in this file: not `apply`'s control flow, not the header-stage regexes, not the
size-cap branch at `:257` (plan 21-06 owns it), and above all not `Redaction.kt:167-227` — SC6 names
`hkdfMatchesRfc5869Vector` as the vector that must stay green.
