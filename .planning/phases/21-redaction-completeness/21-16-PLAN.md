<objective>
Close the CI flake and the three test-integrity findings that let it hide.

**W-04 — the flake, and the maintainer's chosen remedy.**
`newlineFreeOversizeBodyIsScannedNotDestroyed` measured **1.931 / 1.973 / 2.022 s** against
`MAX_REDACTION_BUDGET_MS = 2_000` on Apple Silicon / JDK 21 with the JaCoCo agent attached — 97-101 %
of the budget it races. The reviewer bisected the failure threshold by re-running the same fixture
under reduced budgets: at ~1000 ms effective budget the capability assertion
`output.contains("\"api_key\":\"[REDACTED]\"")` breaks, which is the normal speed of a GitHub-hosted
`ubuntu-latest` runner for single-threaded regex work, before instrumentation. Plan 21-12 already saw
it fail once under full-suite load. Predicting a flake in a comment does not stop it going red and
does not stop the next contributor from `@Disabled`-ing it.

**The maintainer's decision, 2026-08-12: make the test deterministic via an injected budget. Do NOT
change the shipped `MAX_REDACTION_BUDGET_MS` — 2 s is a deliberate product decision made on
2026-08-11, and the fixture-multiplier reduction was NOT the option chosen.** Use the injected-budget
seam pattern plans 21-08 (`testRedactCookieSections`) and 21-11 (`testSplitPoint`) already
established, so the assertion proves scanning behaviour without racing wall-clock. Audit the rest of
the suite for other timing-exposed assertions while you are there.

**IN-03** — reaching `MAX_JSON_BOUNDARY_LOOKAHEAD_LINES` has no test. The reviewer confirmed the cap
behaves as documented, but nothing asserts either half: not that the loop stops at eight, and not that
the window stays line-aligned at the cap. A change to the cap or to the continuation predicate would
move the boundary silently — and this round has just widened that predicate, which makes the gap live
rather than theoretical.

**IN-02** — `splitPoint`'s three-point safety argument opens with "A window with **no interior
newline** has no interior line anchors to corrupt." The branch it justifies is reached whenever
`backward <= 0 && (forward < 0 || forward + 1 >= window.length)`, which includes windows that *do*
have a newline at index 0 or at the final position: `splitPoint("\n" + "x".repeat(10))` returns 5,
cutting mid-line in a window with two lines. Points 2 and 3 still carry the argument, so this is
comment accuracy, not behaviour — but the argument is the only thing licensing an artificial `(?m)^`
anchor, so a false premise inside it is not cosmetic.

**W-07 (test half)** — `RedactionTest.kt:1133` says the end-to-end guard is
`PassiveAiScannerPromptRedactionTest.emittedSectionShapedCookieCannotTerminateSpan`. No such test
exists; it is `poisonedCookieHeaderCannotTerminateTheCookieSection`. A reader following the reference
concludes the guard was deleted. This codebase uses "the named guard is X" comments as a load-bearing
safety mechanism, so a wrong one devalues every other.

Locked decisions in force: **D-01 AMENDED**, **D-02**, **D-04** (`MAX_REDACTION_BODY_CHARS` keeps its
name and value), **D-08 REFINED**.
