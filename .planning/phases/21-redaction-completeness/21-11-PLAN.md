<objective>
Close **CR-04** — a newline-free body above the window width is destroyed in its entirety.

`windowEnd` deliberately makes an over-width line its own window. `splitPoint` then returns `0` for any
window with no interior newline, so `dropOrRetry` skips straight to the drop and the whole payload is
replaced by `[REDACTION INCOMPLETE - N CHARS DROPPED AND NOT SENT]`. The `WINDOW_RETRY_MAX_DEPTH`
machinery — justified in source as existing so a 2-3x slower machine would not "drop content that ships
today" — is structurally inapplicable to the single most common oversized payload shape.

This is not theoretical. `McpToolContext.redactIfNeeded` receives serialized tool output capped at
`maxBodyBytes` (default 2 MiB) and `toolJson.encodeToString(...)` emits **minified, newline-free JSON**.
Measured on the maintainers' own reference hardware, a 2 MiB newline-free body is one window and the JSON
rule alone takes 62-66 ms against a 50 ms per-pattern deadline, so the model receives the marker and
nothing else. The 27 ms/MB sizing note in `Defaults.kt:72-74` was evidently taken on newline-bearing
content; dense newline-free JSON costs ~31 ms/MB, putting the cliff around 1.6 MB on fast hardware and
~800 KB on a 2x slower machine.

It fails **closed**, so this is a utility failure rather than a leak — but it is a capability regression
this phase introduced, and silently emitting an empty analysis for a default-configuration input is
incorrect behaviour.

## The design tension, resolved explicitly

Line-boundary cutting exists **because** naive `substring()` windowing corrupts `(?m)^` anchors — proven
in both directions in `21-RESEARCH.md` section "Decision 3": a mid-line cut can create a match at an
artificial line start and can truncate a match that spans the cut. Reintroducing a character cut appears
to reopen that trap. It does not, for three reasons that must be written into the source:

1. **A newline-free window has no interior line anchors to corrupt.** The only artificial line start a cut
   can create is at the cut itself, one position in the whole window.
2. **That artificial anchor can only over-redact, never leak.** `(^|[?&])` matching at the head of the
   second half produces a false positive. False positives here are fail-safe.
3. **The character cut is reachable only where the alternative is discarding the window outright.**
   `dropOrRetry` is entered when a rule has already timed out; without a cut the entire window is replaced
   by a marker. A straddling match that is truncated by the cut is a false negative — but the content it
   sits in is currently not scanned *and not emitted at all*, so there is strictly nothing to lose.

**Chosen mechanism: a hard cut with a bounded safe-boundary search, not overlap.** From the midpoint,
scan forward a bounded distance for the first character that terminates every built-in body rule's match,
and cut just after it; fall back to the exact midpoint when none is found. This is **not** overlap: the
two halves remain disjoint and no region is processed twice. D-01 AMENDED dropped the overlap clause on
measured grounds — single matches of the built-in rules reach 200 006 characters, so no finite overlap
constant is sound — and that stays dropped. The residual is named and recorded rather than solved.

**WR-05 is folded in** rather than deferred, because both fail-closed tests guard exactly the machinery
this plan changes, and both currently assert `assertFalse(output.contains(body))`, which any
single-character modification satisfies. A mutation that emitted three windows unscanned and marked only
the fourth would keep both tests green while the fail-open this phase exists to kill was back in place.
Strengthening them here is the difference between a real gate and a decorative one.

Output: a `splitPoint` that can engage on newline-free content, a deeper retry ladder, two deterministic
