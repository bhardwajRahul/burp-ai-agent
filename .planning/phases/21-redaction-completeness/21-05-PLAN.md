<objective>
SC1 and SC2 — close both entry points of the PRIV-05 cookie leak.

The passive scanner extracts cookies into a dedicated `=== COOKIES ===` section as bare `name=value`,
splitting the `Cookie:` header on `;` and dropping the prefix that `cookieHeaderRegex` keys on. The call
site is correct — `Redaction.apply` runs over the whole blob — so this is a **pattern-reach** problem,
not a call-site problem. The same mechanism leaks a second time through `request.parameters()`, which
surfaces `COOKIE`-type params into `=== PARAMETERS ===` as `name=value (COOKIE)`.

Two rules close it, and the asymmetry between them is deliberate: the cookie-section rule is
**section-scoped** (there is no other discriminator in that section), while the parameter rule is
**context-free** and keys on the trailing ` (COOKIE)` — a Montoya *semantic* type label, far more stable
than a prompt-layout choice, so it survives a section rename and works wherever the shape appears.

Purpose: PRIV-05 / SC1 / SC2, decisions D-09 and D-10.
Output: `COOKIE_SECTION_HEADER`, `redactCookieSections`, `cookieTypedParamRegex`, an emitter that
imports the constant, and the tests including D-10's named regression test.
</objective>

**2. `redactCookieSections(text: String): String`**, a `private fun` on `Redaction`, plus two supporting
private regexes: `cookieSectionPairRegex` as `(?m)^([^=\r\n]+)=(.*)$` and `nextSectionRegex` as
`(?m)^=== `.

Algorithm, exactly as verified: loop with `var from = 0`; find `out.indexOf(COOKIE_SECTION_HEADER, from)`;
if not found, return. Otherwise set `bodyStart` to the index just past the header; compute `end` as the
minimum of the text length, the index of the next `"\n\n"` at or after `bodyStart`, and the start of the
next `nextSectionRegex` match at or after `bodyStart`; take that span as `section`; rebuild the string as
the prefix, plus `section` with `cookieSectionPairRegex` replaced by group 1 followed by `=[REDACTED]`,
plus the suffix; then set `from = bodyStart` and continue.

**The loop is the security requirement (D-10), not a robustness nicety.** Use
`while ((h = indexOf(HEADER, from)) >= 0)`, never `if (indexOf(HEADER) >= 0)`. The executed exploit:
`ScanKnowledgeBase.recordTechStack` populates the tech list from the response's `Server`,
`X-Powered-By`, `X-AspNet-Version` and `X-Generator` headers — fully attacker-controlled — and
`buildContextSummary` emits it into `=== PRIOR KNOWLEDGE ===`, which the emitter appends **first**. A
`Server: === COOKIES ===` header therefore plants a decoy section ahead of the real one, and a
first-occurrence scan redacts the decoy while `JSESSIONID` and `abtest_bucket` leak intact. Put that
transcript's conclusion in the KDoc.

The KDoc must also state the value policy (D-09 / Correction 2): **every** value is redacted, not only
sensitive-named ones, because cookies are near-universally session-bearing and name-based selectivity is
precisely what produced PRIV-05. Names are preserved deliberately — `COOKIES_MAX_COUNT = 6` bounds the
section to six lines, so this costs the model at most six opaque values while keeping all six names,
which is the analytically useful part (`ScanKnowledgeBase.recordAuthInfo` already records
`authCookieNames` separately for exactly this reason). Full-line stripping in the
`Cookie: [STRIPPED]` style would destroy the names and is therefore wrong here.

Record the accepted residual in the same KDoc: an attacker who injects `=== COOKIES ===` into a header
causes **extra** redaction of their own response content. That is an over-redaction nuisance, never a
leak, and it is strictly better than the alternative.

**3. `cookieTypedParamRegex`**, a private regex `(?im)^([^=\r\n]+)=(.*?)(\s\(COOKIE\))\s*$`, applied
with a replacement of group 1, then `=[REDACTED]`, then group 3 — so `remember_me=abc (COOKIE)` becomes
`remember_me=[REDACTED] (COOKIE)`. Its KDoc explains Pattern 2: parameters are emitted as
`name=value (TYPE)` where TYPE is the Montoya `HttpParameterType` name, so keying on the semantic type
label rather than the section header makes this rule context-free and survives a section rename. State
the asymmetry with the section rule explicitly, and state why the context-free `^name=value$`
alternative was rejected: it **cannot satisfy SC2 at all** (the trailing ` (COOKIE)` defeats the end
anchor), while simultaneously mangling `x=1`, `DEBUG=true` and `AAAA==`.

**4. Wire both into `apply`** inside the existing `if (policy.stripCookies)` block, after the two header
regexes: first `redactCookieSections(out)`, then the `cookieTypedParamRegex` replacement. `stripCookies`
is true in STRICT and BALANCED and false in OFF, which is what keeps every OFF test green. Both rules
are idempotent with respect to the token rules — re-matching `JSESSIONID=[REDACTED]` yields
`JSESSIONID=[REDACTED]` — so no ordering hazard exists with the header stage that follows.

Do NOT change the emitter's cookie extraction at `PassiveAiScannerAnalysis.kt:247-252`: verified
unnecessary, and leaving it alone keeps the diff in `redact/` where the tests live. Do NOT touch
`Redaction.kt:167-227` (SC6). Do NOT touch the size-cap branch (plan 21-06 owns it).

|----------|-------------|
| response headers → prompt text | `Server`, `X-Powered-By`, `X-AspNet-Version` and `X-Generator` are attacker-controlled and reach the prompt through `ScanKnowledgeBase.recordTechStack` into a section emitted BEFORE the cookie section |

| prompt text → AI backend | Everything surviving `Redaction.apply` is transmitted to a possibly third-party provider |
