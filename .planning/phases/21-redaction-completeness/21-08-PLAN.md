<objective>
Close **CR-01** (the live PRIV-05 cookie leak) and **CR-03** (the quadratic, unbounded cookie rule).
Both are defects in the same function, `Redaction.redactCookieSections`, so they are fixed in one pass.

CR-01: `COOKIE_SECTION_HEADER` carries no trailing newline but the emitter uses `appendLine`, so
`bodyStart` lands on the header line's own `\n`. A blank first cookie entry makes `out.indexOf("\n\n",
bodyStart)` match **at `bodyStart`**, the span collapses to the empty string and **every cookie in the
section reaches the AI backend unredacted**. A blank entry anywhere later truncates the span at that
point. The scanner produces blank entries: `.split(";").map { it.trim() }` has no blank filter, so
`Cookie: ; JSESSIONID=...` or any `a=b;;c=d` yields one.

CR-03: the loop rebuilds the entire string per occurrence — 65 ms at 64 KB rising cleanly 4x per
doubling to 2631 ms at 512 KB, ~42 s at the MCP default `maxBodyBytes` of 2 MiB, on an uninterruptible
worker thread with no budget and no marker.

**Decision on fix placement (design tension 4), stated explicitly.** The redactor is the fix. The
emitter filter is defence in depth and ships separately in plan 21-10. Rationale: the maintainer's
standing framing since Phase 20 is that a fix must be structural rather than something a future edit can
silently undo, and an emitter-only filter re-opens the leak the moment anyone adds a new prompt section
or a second producer. There is exactly one exception, and it is stated rather than papered over: a
cookie element shaped like `=== FOO ===` terminates the span, and that is **in-band signalling** — the
span terminator is derived from content inside the region it protects, so no redactor-side rule can tell
a planted section header from a real one. That class is closed at the emitter and only at the emitter,
which is why this plan **exports** the sanitizer from `redact/` (so it is owned beside the rule that
depends on it) and plan 21-10 wires it.

Purpose: PRIV-05, CR-01, CR-03. Preserves D-09, D-10, SC1, SC2, SC6.
Output: a single-pass, line-bounded, deadline-bounded `redactCookieSections`; a `cookieSectionEnd` span
bound that cannot collapse; `sanitizeCookieSectionEntries` for plan 21-10; four regression tests.
</objective>

**1. Two new private constants**, each with a KDoc explaining the number so detekt's `MagicNumber` rule
is satisfied by a named binding rather than by a suppression.

`MAX_COOKIE_SECTION_LINES = 16`: the scanner emits at most `COOKIES_MAX_COUNT` = 6 entry lines
(`PassiveAiScannerAnalysis.kt:26`), so 16 is roughly 2.5x slack. It is a **bound, not a contract** —
`redactCookieSections` also runs over arbitrary MCP tool output via `McpToolContext.redactIfNeeded`,
where any occurrence of the header is attacker-planted, and this constant is what bounds the

`COOKIE_SECTION_BUDGET_MS = 250L`: the wall-clock ceiling for the whole rule across all occurrences.

**2. `private fun cookieSectionEnd(text: String, bodyStart: Int): Int`** — the span bound, and the whole
of CR-01. Contract, in this order:

- Compute `scanFrom`: the index just past the first `'\n'` at or after `bodyStart`, or `bodyStart` when
  there is none. **This single step is the core of CR-01**: `COOKIE_SECTION_HEADER` has no trailing
  newline while the emitter uses `appendLine`, so `bodyStart` is the header line's own newline, and any
  terminator search that starts there can match before the section's first content line. State that in
  the KDoc in exactly those terms.
- Walk forward line by line from `scanFrom`, at most `MAX_COOKIE_SECTION_LINES` lines. For each line
  start `p`, find the line end as the next `'\n'` at or after `p`, or the text length.
  - If the line begins with `"=== "`, return `p` — this is the next prompt section.
  - If the line is empty (`p` equals its line end), **continue**: a blank line is skipped, never a
    terminator. This is what closes the mid-list blank case the reviewer's own snippet leaves open, and
    it is safe precisely because a blank line contains no `name=value` pair, so extending the span
    across it redacts nothing extra.
  - Otherwise advance `p` past the line end.
- On running out of lines or off the end of the text, return the text length or the line start reached,
  whichever the loop arrived at.
- Finally clamp with `maxOf(result, bodyStart)` so the span can never be negative-length.

Note the deliberate departure from the current implementation: `"\n\n"` and `nextSectionRegex` are
**both** dropped as terminator searches. Two independent searches were the second half of CR-03 — each
can scan to the end of the text even when the other finds a near terminator, which is what makes the
loop O(k*n) even after the rebuild is fixed. A single forward line walk is strictly monotone: it never
examines a character before the cursor, so the total work across all occurrences is O(n). Put that
reasoning in the KDoc; it is the correctness argument for the complexity claim and a future reader will
otherwise reintroduce the two searches. `nextSectionRegex` becomes unused — delete it and its comment.

detekt: `cookieSectionEnd` will have more than two `return` statements. Add `@Suppress("ReturnCount")` on
the declaration, matching the existing precedent on `bodyStage` (`:441`) and `windowEnd` (`:625`).
QUAL-07 forbids growing `detekt-baseline.xml`, so a suppression on the declaration is the required
route.

**3. Rewrite `redactCookieSections`** as
`private fun redactCookieSections(text: String, budgetMs: Long = COOKIE_SECTION_BUDGET_MS): String`.

Single pass: one `StringBuilder` sized `text.length`; a `cursor` starting at 0; a deadline computed once
as `System.nanoTime() + budgetMs * NANOS_PER_MS`. Loop: check the deadline first — if it has passed,
append `windowDroppedMarker(text.length - cursor)`, call
`maybeLogTruncation(System.currentTimeMillis(), (text.length - cursor).toLong())`, and break **without**
appending the remainder. Otherwise `indexOf(COOKIE_SECTION_HEADER, cursor)`; if absent, break. Append
`text` from `cursor` up to `bodyStart` (the index just past the header) verbatim; compute `end` via
`cookieSectionEnd`; append the `bodyStart..end` span with `cookieSectionPairRegex` replaced by group 1
followed by `=[REDACTED]`; set `cursor = end`. After the loop, append the tail from `cursor` — but only
on the normal exit, never after a deadline break.

Termination and complexity, to be stated in the KDoc as the replacement for the current
`from = bodyStart` comment: `bodyStart` is strictly greater than the header index and `end` is clamped to
be at least `bodyStart`, so `cursor` advances by at least `COOKIE_SECTION_HEADER.length` every
iteration; the spans appended are disjoint; and `cookieSectionEnd` only ever reads forward from the
cursor. Therefore the pass is O(n), which is the whole of CR-03.

**Fail closed, not open, and say why.** Dropping the tail is the D-02 discipline the body stage already
follows and it is deliberately not the alternative of capping the section count and letting the
remainder through — that remainder can contain unredacted cookie sections, which is fail-open and is the
exact failure class this phase exists to remove. Reuse `windowDroppedMarker` rather than adding a third
marker shape: its four wording properties (content was removed not passed through; distinguishable from
`[REDACTED]`; constant shape plus one integer so it carries zero attacker-controlled substring; not
phrased as an instruction to the model) apply here unchanged.
