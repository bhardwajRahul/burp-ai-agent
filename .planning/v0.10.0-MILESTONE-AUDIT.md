## The gap: PRIV-05

**The requirement says:** "Cookie values do not reach an AI backend in STRICT or BALANCED mode **by
any path**."

**What ships:** two redaction paths that disagree about what a cookie header is called.

| | Prompt path (Phase 21) | MCP tool-result path (Phase 26) |
|---|---|---|
| Location | `Redaction.kt:100-106` | `McpToolHelpers.kt:321` |
| Matcher | name-**contains**-`cookie`, via `COOKIE_NAME_PART = [A-Za-z0-9-]*` | `lowered == "cookie" \|\| lowered == "set-cookie"` |
| `Cookie:` | stripped | stripped |
| `X-Cookie:` | stripped | **passes through** |
| `Set-Cookie2:` | stripped | **passes through** |

The narrowing is not recoverable downstream. `McpToolContext.redactIfNeeded` runs the same two
regexes over `sanitizeHeaders`' output, but that output is a single-line JSON object while both
regexes are line-anchored `(?im)^…$` — applying them to the real output shape matches neither. And
`cookie` is absent from `SENSITIVE_WORDS` (`access_token|api_key|apikey|auth|token|secret|password|
pwd|session|sid`), so `jsonSecretKeyRegex` does not fire either. Reachable through the
`request_parse` and `response_parse` MCP tools.

**This is not an accepted residual — it is the opposite.** `.planning/codebase/CONCERNS.md` records
this exact class as **"W-A CLOSED — the cookie header NAME class is fixed, not accepted.
Maintainer-decided 2026-08-13"**, with the reasoning that name-contains-`cookie` is a *bounded and
complete* predicate over a class whose members are all cookie-bearing by convention — explicitly
contrasted against the vendor auth-header class, which stays deferred because an open-ended vendor
list is never complete. That reasoning applies unchanged to the sibling path. The fix was simply
never mirrored into a path that did not exist when the decision was taken.

**The record was stronger than the code.** `26-SECURITY.md` T-26-02-01 read *"the PRIV-05 failure
mode — a real-world header spelling that the matcher misses — cannot recur unnoticed in this second
redaction path"* and was marked `closed`. It has been reopened by this audit; that phase's
`threats_open` is now `1`. The ASVS L1 pass that closed it verified the control was *present* and
case-insensitive, which is true; it did not compare the control's *width* against its sibling, which
is the entire reason the threat was written.

**Remedy:** one line — make `McpToolHelpers.kt:321` a name-contains test mirroring
`Redaction.COOKIE_NAME_PART`, keeping `set-cookie` mutually exclusive the way the prompt path does
with its negative lookahead. It needs a red probe in both directions (the prompt-path fix has one;
this path should match it), which is closure-phase work, not an audit commit.

### Closure note — 2026-08-24 (appended after the audit; the verdict above is untouched)

**Closed by Phase 27** (`27-priv-05-gap-closure-sanitize-headers`), plans 27-01 (the fix and the
ownership tripwire), 27-02 (the parity test and the tool-result header-shape decision) and 27-03
(this record repair).

**The shipped symbol.** `Redaction.isCookieHeaderName(name)` = `name.lowercase(Locale.ROOT)
.contains(COOKIE_NAME_TOKEN)` at `Redaction.kt:158`. `McpToolHelpers.sanitizeHeaders` now calls it
(`:336`) instead of comparing against the two canonical spellings, and both prompt-path regexes are
composed from that same `COOKIE_NAME_TOKEN` (`:91`), so the predicate and the regexes cannot drift
apart by construction.

**Scope of the singularity claim, stated at the width the evidence supports.**
`isCookieHeaderName` is the single cookie-header-name rule across **the two redaction paths and the
passive-scan admitter** — `Redaction.apply`'s two regexes, `McpToolHelpers.sanitizeHeaders` and
`PassiveAiScannerFilters.sanitizeHeadersForPrompt` (`:186`) — and no wider. Four cookie-header-name
matchers survive elsewhere in `src/main/kotlin` and were each classified against their consumer
chain rather than assumed: the passive-scan cookie-section extractor
(`PassiveAiScannerAnalysis.kt:267`, redacted downstream by `Redaction.apply`), the local-only
scanner heuristics (`PassiveAiScannerHeuristics.kt:102,117`, `ActiveAiScanner.kt:936`, each
collapsing a cookie value to a boolean), the bounty-prompt extractor
(`BountyPromptTagResolver.kt:144,150`, running on already-redacted text) and the active-scanner
request mutator (`ActiveAiScanner.kt:1411`, which writes to the target, not to an AI backend). None
is a redaction path.

**Guarded by three tests.** `McpToolHelpersTest.cookieHeaderNameVariantsAreStrippedOnTheToolResult
Path` (the tool-result outcome); `CookieHeaderNameParityTest.everyNameThePromptPathStripsIsMatchedBy
TheSharedPredicate` (guards a narrowing of the predicate — a narrowing of the prompt-path regexes is
guarded by `RedactionTest.cookieHeaderNameVariantsAreStripped` instead); and
`CookieHeaderRuleOwnershipTest`, a tripwire that fails on an unclassified fourth hand-written
matcher, bounded to five measured spelling classes and therefore not a proof of exhaustive coverage.

**Three residuals remain accepted.** **AR-27-01** — `McpToolContext.redactIfNeeded` still cannot
recover a header `sanitizeHeaders` misses, because its output is single-line JSON while both cookie
regexes are line-anchored. **AR-27-02** — `cookie` remains absent from `SENSITIVE_WORDS`, so
`jsonSecretKeyRegex` is not a backstop either. **AR-27-03** — byte-identically-named headers collapse
to one entry in the tool-result header map (CP-27-02-01, human-decided): privacy-safe and asserted to
leak no original value, but it costs analysis signal.

**Locale scope.** The explicit `Locale.ROOT` argument was added only at the two header-name functions
this phase changed, and per plan 27-01's MEASURED backlog observation it is defensive documentation
rather than a defect fix — Kotlin's no-argument `lowercase()` is already locale-agnostic, so
`src/main/kotlin` holds zero locale-sensitive lowering call sites today. Nothing here closes a
locale hazard beyond those two functions.

`status`, `scores` and `gaps` blocks, and `.planning/REQUIREMENTS.md`, are untouched by the phase
that closed this gap. A phase that grades its own homework produces exactly the record this closure
was repairing. The next `/gsd-audit-milestone` run re-derives its own verdict from the phase
artifacts rather than inheriting an edited one.

### Correction to the closure note above — 2026-08-24 (appended; nothing above is edited)

**The closure note's BODY was carefully scoped. Its HEADING was not, and the difference matters.**
"Closure note" sits directly under the PRIV-05 gap narrative and reads as closing the **PRIV-05
requirement gap**. What the body actually closes, and all it claims to close, is the cookie-header
NAME class on `McpToolHelpers.sanitizeHeaders`. Read that heading at the width it invites and it is
an overclaim — which is the same failure mode, one document out, that the note itself is recording.

**PRIV-05 remained refuted for the whole interval between that note and plan 27-04.** The closure
note was appended on **2026-08-24**. Later that same day, phase 27's own verification
(`27-VERIFICATION.md`, verified `2026-08-24T14:12:50Z`, 7/9 truths) measured cookie values still
reaching an AI backend verbatim in STRICT **and** BALANCED. Closed by plan **27-04** on **2026-08-24**
and, for the auth-header class, by plan **27-05** the same day.

**The leak was strictly broader than the variant-spelling defect the note describes.** Not `Cookie2`
/ `X-Cookie` / `Set-Cookie2` / `X-Original-Cookie` / `X-Forwarded-Cookie`, but the **canonical
`Cookie:` and `Set-Cookie:` names themselves** — the two the note's own source entry says "render
exactly as before" — through `proxy_http_history`, `proxy_http_history_regex`, `site_map`,
`site_map_regex` and `scanner_issues`, in both the current and the legacy executor. **Root cause:** a
raw HTTP message embedded in a JSON string carries no real newline (`toolJson.encodeToString` writes
every CRLF as the two characters `\r` / `\n`), and both cookie rules were line-anchored `(?im)^…$`,
so `^` never landed on a header name — and unlike `request_parse` / `response_parse`, nothing runs
`sanitizeHeaders` in front of that path.

**What closed it, cited by symbol, test and pinned count.** `Redaction.kt` composes its logical-line
header rules from `JSON_ESCAPED_NEWLINE` (`:206`), `REAL_LINE_HEADER_VALUE` (`:210`) and
`JSON_ESCAPED_HEADER_VALUE` (`:218-219`) through one private composer,
`logicalLineHeaderRule(namePattern)` (`:236-240`), whose real-line branch is the tail that shipped
character for character — so multi-line behaviour is unchanged by construction, and `RedactionTest`
held a zero-line diff at 46/46 green throughout. `cookieHeaderRegex` (`:242-246`) and
`setCookieHeaderRegex` (`:247-248`) are built from it (plan 27-04); `authHeaderRegex` (`:97-105`) too
(plan 27-05), with its 16-name alternation byte-identical — measured, a plain-token `X-API-Key` value
moved `STRICT APIKEY SURVIVES` → `STRICT APIKEY STRIPPED`. **The claim is bounded to the serialized
emission path — the pinned inventory of `14` emission sites (`SerializedEmissionSiteInventoryTest`),
of which 10 carry raw HTTP across 5 tool names — and to the cookie-header class and the exact-name
auth-header class on that path, at no wider scope.** `LogicalLineBoundaryScopeTest` pins the rule set
carrying the boundary at `3`; `SerializedEmissionRedactionTest` (24 tests) gates the behaviour.
Neither tripwire is a proof of exhaustive coverage and neither is described as one.

**Two findings remain OPEN on the same path, both measured and both MEDIUM.** **AR-27-04** — the
`Host:` header value and the sibling `SiteMapEntry.url` field both reach an AI backend
**un-anonymised under STRICT** on this shape, after the fix as before it, a gap between STRICT's
stated promise of host anonymisation and its shipped behaviour on a 1.0.0 release. **AR-27-05** — on
the header-map shape (`ParsedRequest` / `ParsedResponse`) the payload carries no line boundary of any
kind, so `redactIfNeeded` cannot recover a missed cookie there and `sanitizeHeaders` is the sole
control for `request_parse` / `response_parse`; a no-backstop bound rather than a live leak, and the
thing that bounds what "AR-27-01 is closed" means. Both are recorded with quoted probe output in
`.planning/phases/26-coverage-static-analysis-debt-docs/26-SECURITY.md`.

**This correction is append-only, on the same terms as the note above it.** The frontmatter
`status`, `scores` and `gaps` blocks, and `.planning/REQUIREMENTS.md`, are untouched by the phase
that closed this gap — including its `- [x] **PRIV-05**` tick, which predates the audit that refuted
it and is the milestone owner's to re-derive, not this phase's to grade. The next
`/gsd-audit-milestone` run re-derives its own verdict from the phase artifacts rather than inheriting
an edited one.

## Verdict

The milestone did what it set out to do on 11 of 12 requirements, and the cross-phase wiring holds
everywhere it was traced — gate placement, off-EDT dispatch, guarded schedulers, bounded pools, and
26-07's refactors all survive inspection against shipped source rather than SUMMARY prose.

The one gap is a narrowing, not a broken wire, and it is the characteristic failure mode of a
milestone that hardens the same class of control in more than one place across seven phases: Phase
21 fixed the cookie-name class deliberately and recorded *why*; Phase 26 added a second path three
phases later and matched the two canonical names. Each phase's own verification was correct. Only a
cross-phase check could see that the pair disagrees.
